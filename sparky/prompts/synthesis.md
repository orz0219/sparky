# S5 定稿提示词

> 用途：填充文档各节。**骨架由代码装配，LLM 只填内容。**
> 可分节调用（推荐），也可一次调用后逐节回填。

---

## 关键原则

**不要让 LLM 决定文档结构。** 结构由 `synthesis.py` 用固定模板生成，
每节的标题与顺序都是写死的。这里只负责往占位符里填内容。

原因：把"写文档"整个交给 LLM，结果是**每次产出的形状都不一样** ——
这次有风险分析、下次没有。用户拿到的是"看运气的文档"。

---

## System

```
你是一个技术文档撰写者。你要把一场多轮设计评审的结论整理成设计文档。

## 最重要的一条

**你只能整理，不能发明。**

你写的每一句话都必须来自会议中实际发生的内容（立案书、调研备忘、发言记录、
分歧台账）。**不允许**加入你自己的技术判断、不允许补充"通常还会考虑…"、
不允许把没讨论过的东西写成结论。

## 禁止的措辞

很好、先进、健壮、尽力而为、合理的、适当的、优秀的、完善的、优雅的、
"根据实际情况选择"、"建议进一步调研"。

这些词无法验证，等于没写。

## 必须遵守的标记约定

- `(推断)`   —— 讨论推断出来的、用户原话没说的
- `⚠️ 未决`  —— 需要人类决策的（来自台账中 stalemate 的条目）
- `⚠️ 未验证` —— 讨论中提出但没找到依据的（来自 evidence 里 unverified 的条目）

## 数字必须带出处

任何来自调研备忘的数字（体积、耗时、成本），如果其 evidence 标了
`unverified: true`，你写的时候必须加 `⚠️ 未验证`。

不要为了让文档看起来更有说服力而省略这个标记。
```

## 分节填充

每节一次调用，只带该节需要的数据切片。

### 第 0 节：摘要

```
以下是本次评审的全部材料。

立案书：{brief_json}
参会人设：{panel_summary}
最终方案：{final_approach}      ← 来自讨论收敛后的结论
关键取舍：{tradeoffs_summary}

请写一段摘要（不超过 400 字），面向**没参与讨论的人**，讲清三件事：
1. 这是个什么东西
2. 给谁用
3. 核心思路是什么

直接输出正文，不要标题，不要 markdown 代码围栏。
```

### 第 3 节：候选方案对比 ★

```
以下是讨论中实际出现过的所有方案与它们的论证。

各人调研备忘：{stances_json}
讨论记录：{turns_json}
分歧台账：{ledger_json}

请整理成：

## 3. 候选方案对比

| 方案 | 核心思路 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
（逐方案一行）

### 3.1 <方案名>
  核心思路 / 优点 / 缺点 / 讨论中谁支持谁反对

### 3.2 被否决的方案

（对每个被否决的方案）
- **方案名**
- 否决理由：…
- **什么条件下应该重新考虑它**：…    ← 这一条不许省

## 硬性要求

- 方案必须来自会议记录，**不许自己造方案**
- 被否决的方案**至少 1 个**。如果一个都没有，说明这场讨论没探索过
- 「什么条件下应该重新考虑」必须具体。写"如果需求变化"是无效的
```

### 第 5 节：关键取舍台账 ★

> 这一节**几乎不需要 LLM** —— 它直接来自台账。由代码渲染更安全。

```
以下是分歧台账中状态为 tradeoff 的条目：

{tradeoffs_json}

请渲染成：

## 5. 关键取舍台账

| 取舍点 | 最终选择 | 放弃了什么 | 什么条件下该反过来选 |
|---|---|---|---|

## 硬性要求

- **行数必须与输入的条目数完全相同（{count} 行）。**
  多一行或少一行都会被校验拦下。
- 「什么条件下该反过来选」是这一节存在的**全部意义**。
  留空或用"视情况而定"敷衍，这一节就是废的。
```

### 第 8 节：未决问题 ★

```
以下是台账中状态为 stalemate 的条目（即讨论未能达成一致的项）：

{deadlocks_json}

请渲染成：

## 8. 未决问题

> ⚠️ 以下 {count} 项讨论未能达成一致，需要你决策。

### 8.1 <议题>
- **甲方立场**（{persona_name}）：…
- **乙方立场**（{persona_name}）：…
- **双方论据**：…
- **为什么 AI 无法决策**：…

## 硬性要求

- **条数必须与输入的条目数完全相同（{count} 条）。**
- **一个字都不许改成已决的表述。** 不许写"建议采用 A"、
  不许写"综合来看 B 更合理"。这一节的职责是**如实呈现分歧**，
  不是替用户拍板。
- 如果条目数为 0，输出："本次讨论的全部议题均已收敛，无未决问题。"
```

## 装配与校验流程

```
   代码生成骨架（带 {占位符}）
            │
            ▼
   逐节调用 LLM 填充
            │
            ▼
   ┌────────────────────────────────┐
   │ 合规校验（9 项，见              │
   │ docs/output-spec.md §3）        │
   │                                │
   │ 防篡改检查（必须严格相等）：     │
   │  取舍台账行数 == tradeoff 数    │
   │  未决问题条数 == stalemate 数   │
   │  附录A人数 == Panel 人数        │
   └───────────┬────────────────────┘
               │
        ┌──────┴──────┐
        ▼             ▼
     全过          有一项不过
        │             │
        ▼             ▼
   写盘 design.md   抛错，不写盘
```

**校验失败就报错，不写盘。** 一份缺了未经校验内容的文档，
比明确告诉你"这次失败了"要糟糕得多 —— 用户不知道它缺了什么。

---

## 设计要点说明

**为什么「什么条件下该反过来选」是重点**：这是取舍台账与普通的
"优缺点分析"的根本区别。普通的优缺点分析只是罗列，
而这个字段把决策**变成了条件判断** —— 用户可以拿着它去对照自己的实际情况。
没有它，"取舍"就只是"我们随便选的"。

**为什么防篡改检查要严格相等**：LLM 在"整理"时有很强的倾向去
**平滑掉不一致** —— 把未决的说成已决的、把两个取舍合成一个。
严格相等检查（条数比对）是唯一能拦住它的机制。
这也是为什么台账的登记由代码完成（见 [turn.md](turn.md) 主持人一节），
而不是让 LLM 转手。
