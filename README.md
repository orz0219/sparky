# Sparky · 头脑风暴定稿机

> **给它一句话，还你一份能开工的设计文档。**

Sparky 是一个**多智能体头脑风暴**小工具。你把一个还很模糊的程序设计想法丢给它，
它会自动组建一支专家小组：每个专家从**不同的信息面**独立调研、拿出自己的观点与
优缺点，然后围绕**分歧**多轮辩论，最后产出一份详细设计文档——连同**被否决的方案
与为什么否决**。

它专门解决这一种处境：**想做个东西，但完全没有头绪。**

```console
$ python3 -m sparky "我想做一个给播客自动生成章节和文字稿的小工具，本地跑，不要云服务"
```

```
[立案] 目标=本地播客处理工具  约束=离线/无云依赖  非目标=(待确认)
[组阁] 判定需要 5 人：架构师 / 离线推理工程师 / 用户体验设计师 / 运维成本官 / 唱反调者
[调研] 5 条信息线并行取证中 …
[交锋] 第 1 轮：分歧 4 项（模型体积 vs 识别质量、增量 vs 全量、GUI vs CLI）…
[交锋] 第 2 轮：分歧剩 2 项
[收敛] 2 项未解决 → 降级为「已知取舍」，附决策条件
[定稿] .sparky/sessions/20261012-103000-podcast/design.md  ✍  约 6400 字
```

## 它到底解决什么问题

「设计一个程序」最难的不是写代码，是这四个卡点：

| 卡点 | 表现 | Sparky 的对策 |
|---|---|---|
| **不知道要考虑什么** | 只想到功能，想不到部署、成本、失败模式 | 自动从你的描述里抽取**设计维度**，每个维度配一个专家 |
| **只有一个视角** | 自己的想法反复自我确认，看不到盲区 | 强制多视角，且**必含一个唱反调角色** |
| **假共识** | 自己觉得"这样应该行"，其实没验证 | 分歧进入**显式台账**，不许口头和谐 |
| **讨论完没沉淀** | 聊得很嗨，回头一片空白 | 过程直接落成**结构化设计文档** |

## 设计上的四个关键决定

这几条是本项目的灵魂，展开见 [docs/design.md](docs/design.md) 与
[docs/adr/](docs/adr/)。

1. **人设不是从固定角色池里挑，而是按设计维度现场生成。**
   先抽取"这个设计需要考虑哪些维度"，再为每个维度造一个具体的人——
   带名字、带立场、带**明确的偏见与盲点**。太和谐的小组产不出东西。

2. **每个 Agent 看到的上下文是不同的（信息面隔离）。**
   如果所有人共享同一份材料，那就是一个人自问自答了 N 遍。Sparky 给每个 Agent
   分配独立的信息线与独立的检索预算，来源在最终文档里逐条列出。

3. **共识 = 没有未解释的反对意见，而不是"大家都同意"。**
   靠 LLM 自述"我们达成一致了"是无法验证的。Sparky 用**分歧台账**：
   每项分歧要么被解决，要么被降级为**已知取舍**（写明"什么条件下该选另一个"）。
   真正的死锁会被如实标注为**未决问题**，而不是伪造一致。

4. **过程是一等公民，全部可复现。**
   每个事件写入 `transcript.jsonl`（事件溯源），所以会话可以回放、可以续跑、
   可以事后审计"这个结论是怎么来的"。

## 快速开始

零第三方依赖，Python 3.11+ 标准库直接跑。

```bash
git clone https://github.com/orz0219/sparky.git && cd sparky

# 密钥放这儿（也可以直接 export）
echo 'DEEPSEEK_API_KEY=sk-...' >> ~/.config/llm/keys.env

# 方式一：直接跑一次，网页会实时把讨论演给你看
python3 -m sparky "你的想法，一两句话就行"

# 方式二：只开提案工作台，在网页上翻历史、发起新的
python3 -m sparky
```

跑完之后看 `.sparky/sessions/<会话>/design.md`，或者在页面上点开那份提案。

终端输出长这样：

```
[立案] 做一个本地运行的播客工具，自动产出文字稿与章节切分。
  · d1 离线可行性（用户）
  · d2 算力与模型体积（推断）
  · d3 质量与耗时取舍（推断）
  · … 共 8 个维度，其中 7 个是你没说过的
[组阁] 判定需要 4 人
  · p1 陆振声 · 端侧语音推理工程师（specialist）
      立场：只接受在断网笔记本上能完整跑通的方案…
  · p4 郑铁林 · 本地音频流水线故障复盘工程师（adversary） ★反方
[调研] 4 条信息线并发取证…
  ✓ p4：三小时双人抢话在 16GB 机器上不会 OOM——只要分块流式…
[定稿] 已写出 .sparky/sessions/20261012-113111-…/design.md（8432 字）
```

跑测试：

```bash
python3 -m unittest discover -s tests -t .
```

**想看真实产物？** [`examples/01-podcast-transcriber/`](examples/01-podcast-transcriber/)
里收了一次完整会话的全部产物：38542 字的设计文档、7 位专家的人设、
每人的独立调研备忘、28 条事件溯源日志，以及一份**诚实记录
"这次运行能证明什么、不能证明什么"**的 [观察笔记](examples/01-podcast-transcriber/notes.md)。

## 设计原则

- **零第三方依赖**：只用 Python 标准库。`urllib` 发请求、`http.server` 起服务、
  手写 SSE。少一个依赖，少十个"装不上"的理由。
- **零构建前端**：原生 HTML + CSS + JS，没有 npm、没有打包器、没有 `node_modules`。
- **过程可审计**：任何一个结论都能追溯到"谁在第几轮基于什么说的"。
- **失败就说失败**：缺密钥、连不上、模型返回格式不对——直接报错退出，
  绝不静默降级成一份看起来正常的文档。
