# 多轮讨论与共识判定协议

> 本文是本项目的灵魂。它回答一个看似简单、实则决定了整个工具成败的问题：
> **什么时候算「讨论完了」？**
>
> 上游是 [personas.md](personas.md)，下游是 [output-spec.md](output-spec.md)。

---

## 1. 为什么必须有一个显式协议

### 1.1 朴素做法错在哪

最直觉的实现是：让模型自己判断。

```
你：大家达成一致了吗？
模型：经过充分讨论，我们已经达成一致。最终方案是……
```

这个回答**永远会出现**，无论是否真的一致。原因有二：

1. LLM 有强烈的**迎合倾向**（sycophancy）。你问"同意了吗"，它倾向于说"同意了"。
2. "一致"是一个**语义模糊**的概念，模型可以合法地把"没人明确反对"解释成一致。

于是你得到一个看起来完美、实则未经验证的结论。**这比没有结论更危险** ——
它带着虚假的确定性。

### 1.2 两条设计原则

**原则一：终止条件是控制流，不是创作。**
所以收敛判定 `consensus.py` **绝不调用 LLM**，是一个纯函数。
否则：成本不可预测、结果不可复现、模型可以无限拖延。

**原则二：共识 ≠ 大家同意，共识 = 没有未解释的反对意见。**
这是本项目最重要的一句话。一项分歧只要**被解释清楚**（记录为取舍，写明
"什么条件下该反过来选"），就算收敛。人类专家评审也是这样工作的。

## 2. 一轮讨论的完整流程

```
                  ┌─────────────────────────────────────────┐
                  │ 轮次开始：固化「上轮快照」               │
                  │ snapshot = 上一轮所有 Turn（只读）       │
                  └────────────────┬────────────────────────┘
                                   │
              ┌────────────────────┼────────────────────┐
              ▼                    ▼                    ▼
        ┌──────────┐         ┌──────────┐         ┌──────────┐
        │ 人设 A   │         │ 人设 B   │   ...   │ 人设 N   │   ← N 并发
        │ 读快照   │         │ 读快照   │         │ 读快照   │
        │ 生成 Turn│         │ 生成 Turn│         │ 生成 Turn│
        └────┬─────┘         └────┬─────┘         └────┬─────┘
             └────────────────────┼────────────────────┘
                                  │  ★ 屏障：等全员结束
                                  ▼
                  ┌─────────────────────────────────────────┐
                  │ 主持人登记（串行，写台账）                │
                  │  · 新增 open 分歧                        │
                  │  · 关闭被打消的分歧（记录谁说服了谁）     │
                  │  · 检出 stalemate（连续两轮理由未变）     │
                  └────────────────┬────────────────────────┘
                                   ▼
                  ┌─────────────────────────────────────────┐
                  │ S4 收敛判定（纯函数，见 §4）             │
                  └─────────────────────────────────────────┘
```

### 2.1 两段式的硬约束

**屏障**不是性能优化，是**正确性要求**。

如果边生成边登记，先完成的人可能读到后完成者刚写入台账的条目 ——
同一轮内不同 Agent 看到的世界不一致。这种 bug 在并发下不可复现，
是最难查的一类。所以：

> **轮内只读上轮快照；写台账必须等本轮全员结束。**

### 2.2 每个 `Turn` 必须包含的回应义务

一个 `Turn` 只有"我补充一点"是**不合格**的。必须至少有一条对其他人的
明确回应：

```jsonc
{
  "round": 2,
  "persona_id": "p3",
  "responds_to": [
    {
      "disagreement_id": "x1",
      "action": "rebut",             // support | rebut | amend
      "reason": "对方引用的延迟数据来自 GPU 版本，与本地 CPU 场景不可比"
    }
  ],
  "new_points": ["建议模型改为首次使用时按需下载"],
  "opens": ["x4"],
  "closes": ["x2"],
  "stance_snapshot": {               // 用于 §4 的停滞检测
    "x1": "against",
    "x4": "for"
  }
}
```

`responds_to` 为空 → 视为弃权，记入台账，**不伪造发言**。
连续弃权 2 轮的人设在后续轮次被移出（并在文档中说明）。

## 3. 分歧台账（Ledger）

台账是**收敛判定的唯一依据**，也是最终文档「取舍台账」一节的直接来源。

### 3.1 一条分歧的完整结构

```jsonc
{
  "id": "x1",
  "topic": "离线模型是内置还是首次使用时下载",
  "parties": ["p2", "p3"],
  "status": "open",          // open | resolved | tradeoff | stalemate
  "positions": {
    "p2": "内置，保证开箱即用",
    "p3": "按需下载，避免安装包过大"
  },
  "stakes": "影响首次启动体验与安装包体积，二者互斥",
  "history": [
    { "round": 1, "summary": "p2 主张内置；p3 以安装包体积为由反对" },
    { "round": 2, "summary": "p2 让步到'首次启动时后台预下载'" }
  ],
  "resolution": null,
  "tradeoff": null
}
```

### 3.2 生命周期

```
                    ┌──────────┐
     新冲突产生 ───► │   open   │
                    └────┬─────┘
                         │
        ┌────────────────┼─────────────────┬──────────────────┐
        ▼                ▼                 ▼                  ▼
  一方被说服       双方都有理         理由两轮未变        轮次用尽
        │                │                 │                  │
        ▼                ▼                 ▼                  ▼
  ┌──────────┐    ┌────────────┐   ┌─────────────┐   ┌─────────────┐
  │ resolved │    │  tradeoff  │   │  stalemate  │   │  tradeoff   │
  │          │    │            │   │             │   │ (强制降级)  │
  └──────────┘    └────────────┘   └──────┬──────┘   └─────────────┘
  记录：谁被谁                             │
  说服、为什么                       进入 S4 强制处理
```

### 3.3 台账只增不删

分歧**永不从台账中删除**，只改状态。

理由：最终文档要写「候选方案对比（含被否决方案与理由）」，
被否决方案的信息恰恰藏在 `resolved` 的条目里。删掉台账等于销毁了
本工具相对"问一次 ChatGPT"最大的增量。

## 4. 收敛判定：一个纯函数

```python
def decide(ledger: Ledger, round: int, budget: Budget, cfg: Config) -> Decision:
    """纯函数：无 IO、无 LLM、无随机。同样的输入必然给出同样的输出。"""
```

按顺序判断，**第一个命中即返回**：

| 序 | 条件 | 返回 | 含义 |
|---|---|---|---|
| 1 | `open` 与 `stalemate` 均为空 | `done` | **真达成**（可能含 tradeoff） |
| 2 | `budget` 超限 | `force_stop(budget_exhausted)` | 如实标注未收敛 |
| 3 | `round >= cfg.max_rounds` | `force_stop(max_rounds)` | 硬上限 |
| 4 | 本轮立场快照与上轮完全相同 | `force_stop(stagnation)` | 停滞检测 |
| 5 | 只剩 `stalemate` 且无新论据 | `force_stop(deadlock)` | 死锁 |
| 6 | 其余 | `another_round(focus=[...])` | 定向加轮 |

**顺序的意义**：1 在 2/3 之前 —— 如果刚好在最后一轮达成一致，
不应该因为"轮次用尽"而误判为未收敛。

### 4.1 停滞检测的判定粒度（未决问题）

逐字比较太严（措辞必然变化），语义比较又需要模型调用（违背纯规则原则）。

**当前设计**：比较三元组

```python
(current_stance_方向, current_closes, current_opens)
```

即"各分歧上的立场方向 + 本轮关闭了哪些 + 本轮新开了哪些"。
三者全同 → 判定停滞。

> ⚠️ 这个粒度是**拍脑袋定的**，见 [design.md](design.md) §11 未决问题 2，
> 需要真实案例校准。

### 4.2 为什么 `force_stop` 不是失败

`force_stop` 意味着"没聊完但必须停"。此时：

- 会话正常结束（退出码 0）
- 所有未决项原样进入文档的「⚠️ 未决问题」一节
- 顶部输出「⚠️ 本次讨论未完全收敛，以下 N 项需要你决策」

**不把它当失败**，是因为"诚实的未完成"远比"伪装成完成"有价值。
这也符合 §1.2 的原则二。

## 5. 定向加轮（省钱且不跑题）

判定为 `another_round` 时，**不是让全员再发一轮言**，而是：

1. 从台账中挑出所有 `open` 与 `stalemate` 的条目
2. 对每条，只召集 `parties` 里的当事人
3. 每人的 prompt 里只放**该分歧的完整 history**，不放全场记录
4. 明确要求："请针对 x1，要么给出新论据，要么接受对方的方案，要么提议降级为取舍"

代价对比（以 5 人、2 项分歧为例）：

| | 全员加轮 | 定向加轮 |
|---|---|---|
| 调用次数 | 5 | 4（2 项 × 2 人） |
| 每人上下文 | 全场记录（大） | 单条分歧（小） |
| 跑题风险 | 高 | 低 |

### 5.1 新分歧的处理

定向加轮时**允许**当事人提出新分歧（说明旧分歧的解决暴露了新问题），
但新分歧会被登记，并占用后续轮次。

**上限保护**：一项目标分歧最多定向加轮 2 次。超过则强制降级为 `tradeoff`。
否则可能出现"解决了 A 冒出 B，解决了 B 又冒出 A"的无限循环。

## 6. 和谐告警（零分歧是失败信号）

**规则**：若整场讨论结束后 `len(ledger) == 0`（或全部条目都是
`resolved` 且 `history` 长度均为 1，即从没真正辩过），则：

1. 在文档**顶部**插入显著告警：

   ```markdown
   > ⚠️ **本次讨论未产生实质分歧。**
   > 这通常意味着人设构造过于同质，或问题本身约束过强导致方案唯一。
   > 本文件的结论**未经对抗性检验**，可信度存疑，建议人工复核。
   ```

2. 发出 `warning` 事件，前端显示黄色告警条
3. 退出码仍为 0（这不是程序错误，是**诊断信息**）

**为什么这么做**：把"没吵起来"从一个隐性问题变成一个**显式信号**。
用户看到告警，就知道该调整输入或强制指定人设，而不是稀里糊涂接受一份
没人反对过的方案。

## 7. 死锁怎么办

死锁 = 双方立场坚固、理由已充分交换、谁都说服不了谁。

Sparky **不假装解决它**。处理顺序：

1. 尝试降级为 `tradeoff`：主持人追问"**在什么条件下**应该选你而不是对方？"
   多数真死锁其实是**条件分歧**（"如果你在乎体积就选 A，在乎质量就选 B"），
   一旦条件被写出来，它就不再是死锁。
2. 若连条件都写不出来（真·价值观冲突），标注为 `⚠️ 未决`，附**双方原始论据**，
   交给人类决策。
3. 在文档「未决问题」一节置顶，并说明"这一项 AI 无法决策，理由如下"。

> **一条底线**：无论多难看，都不许在文档里把未决项写成已决项。
> 这个工具的价值全在"可信"二字。

## 8. 反模式（实现时不要这么做）

| 反模式 | 为什么错 |
|---|---|
| 让 LLM 判断"是否达成一致" | 迎合倾向 + 不可复现 + 可无限拖延 |
| 把"无人反对"当作一致 | 沉默可能是弃权、可能是没看懂，不等于同意 |
| 删除已解决的分歧 | 丢失"被否决方案"，而这是核心产出 |
| 全文上下文喂给每个人 | 成本 O(N²) 爆炸 + 观点同质化 |
| 轮内边生成边写台账 | 并发下同轮不同人看到不同世界，不可复现的 bug |
| 收敛失败就报错退出 | 诚实的未完成是有价值的产出，不是失败 |
| 为了"聊完"而反复加轮 | 用 max_rounds + 定向加轮上限硬控 |
| 让反方提建设性方案 | 反方会退化成第二个 specialist，对抗性消失 |
