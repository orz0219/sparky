# 人设分配机制

> 本文回答「要开几个人、都是谁、各自知道什么」。
> 上游是 [design.md](design.md) §4.2，下游是 [consensus.md](consensus.md)。

---

## 1. 要解决什么

用户给一句话，工具要自己组一支队。这一步做砸了，后面全废：

- **人太少** → 没有对抗性，退化成"一个人自问自答"。
- **人太多** → 成本是 O(N²) 涨，且发言开始互相重复，讨论空转。
- **人不对** → 全是同一种思维（比如五个都是后端工程师），照样看不到盲区。
- **人设太"正确"** → 每个人都"客观全面" → 谁都不反对谁 → 假共识。

所以这一步的目标不是"凑够 N 个人"，而是**构造出真实的立场张力**。

---

## 2. 两段式：先抽维度，后造角色

```
   用户的一句话
        │
        ▼
 ┌──────────────────────────────────────┐
 │ 第一段：抽设计维度                     │
 │  "做这个设计，需要考虑哪些方面？"       │
 │                                      │
 │  → 离线可行性 / 数据模型 / 成本曲线    │
 │    / 失败模式 / 用户体验 / 可维护性    │
 │    / 分发形态 / …                     │
 └──────────────┬───────────────────────┘
                │
                ▼
 ┌──────────────────────────────────────┐
 │ 第二段：为维度造人                     │
 │  "谁会死盯这个维度？他天生倾向什么？"   │
 │                                      │
 │  → 陈砚，离线推理工程师               │
 │    立场：能本地跑就绝不联网            │
 │    偏见：低估模型体积代价              │
 │    盲点：忽略非技术用户的操作成本       │
 └──────────────────────────────────────┘
```

**为什么不做固定角色池**（如"总是安排产品/开发/测试三个人"）：

固定角色池会把**所有问题都套进同一副框架**。一个"给播客做本地转写"的问题，
需要的是「离线推理工程师 + 存储成本官」，而不是「产品经理 + 前端 + 后端」。
维度是从问题里长出来的，角色是从维度里长出来的。

> **代价**（诚实记录）：现场生成的人设质量依赖模型能力，稳定性不如固定池。
> 缓解手段是 `personas/presets/` 里的**维度库**作为参考种子 —— 给模型一些
> "常见维度长什么样"的示例，但不强制它只能用这些。
> 见 [design.md](design.md) §10 取舍台账中「人设复用」一行。

## 3. 人数怎么定

```python
panel_size = clamp(3, 7, ceil(len(effective_dimensions) / 1.5))
```

再叠加修正：

| 条件 | 修正 | 理由 |
|---|---|---|
| `Brief.uncertainty == "high"` | +1 | 不确定性高，需要更多视角覆盖 |
| 约束里含安全 / 合规 / 隐私 | +1 | 这类约束必须有专人盯 |
| 维度数 < 3 | 取 3 | 保底，否则形不成三方博弈 |
| 修正后 > 7 | 取 7 | 上限，成本与重复的临界点 |

**为什么下限是 3**：两个人讨论会退化成"对喷"，没有第三方来打破僵局。
三个人才能形成"两方对立 + 一方能站队"的动态。

**为什么上限是 7**：上下文成本随人数平方增长（每轮每人要读上一轮所有人的发言），
且实测（见 [design.md](design.md) §11 未决问题 1）人数超过 7 后发言重复率显著上升。

**`--panel-size N` 可指定目标人数**，但它是「目标」不是硬性上限：
实际人数以**维度覆盖**为准。模型偶尔会多给一个人，此时发出
`panel_size_mismatch` 告警并以实际生成为准。

### 3.1 越界裁剪的三条规则

人数超过 7 时由 `personas._clamp_size` 裁剪，顺序固定：

1. **绝不裁掉唱反调者。** 早先的实现是"从尾部一刀切"，而模型把反方
   排在最后一位时就被切掉了，随后校验报「专家组里没有唱反调者」。
   对抗性比省一次调用重要得多。
2. **优先裁掉维度最少的非反方成员**（贡献最小的那个）。
3. **不破坏维度覆盖**：只裁那些"少了他，所有维度仍有人负责"的人。

三条约束导致**裁不动**时（剩下的每个人都是某个维度的唯一负责人），
保留超员并发出 `panel_size_over_max` 告警 —— 让小组多花一点钱，
好过制造一个没人负责的维度。

## 4. 人设的结构

每个 `Persona` 必须包含以下字段。**`bias` 和 `blind_spot` 是必须有的**，
它们是讨论产生张力的燃料：

| 字段 | 类型 | 作用 | 缺了会怎样 |
|---|---|---|---|
| `id` | str | 唯一标识，全程引用用 | 台账无法定位当事人 |
| `name` | str | 中文人名 | 模型扮演"角色A"明显比扮演"陈砚"敷衍 |
| `title` | str | 头衔，暗示其专业视角 | 发言变成无差别通用建议 |
| `role_type` | enum | `specialist` / `generalist` / `adversary` | 无法强制反方（§5） |
| `stance` | str | **他天生倾向什么** | 立场飘忽，每轮都不一样 |
| `bias` | str | **他的偏见**（故意写的） | 发言变成"客观中立"，没有张力 |
| `blind_spot` | str | **他自己看不到的** | 失去"被别人指出盲点"这一戏剧性时刻 |
| `cares_about` | list | 他评审时死盯的指标 | 发言无法落到具体数字上 |
| `dimensions` | list | 他负责哪些维度 | 维度覆盖出现空洞 |
| `info_scope` | obj | 信息面（§6） | 全员同质化 |

**关于 `bias` 与 `blind_spot` 的一个实现要点**：
`blind_spot` 不应该出现在该人设自己的 prompt 里（他不会承认自己有盲点），
而应该出现在**其他人**的 prompt 里 —— 作为"你可以从这里攻击他"的提示。
这是让讨论真的打起来的关键小技巧。

## 5. 反方强制（代码层保证）

**规则**：`Panel` 中必须至少有一个 `role_type == "adversary"`。

反方角色的职责定义与其他人不同：

| | 普通 specialist | adversary |
|---|---|---|
| 目标 | 让自己的方案胜出 | **找出方案会在哪里崩** |
| 评价标准 | 方案好不好 | 方案**怎么坏** |
| 允许的行为 | 提方案、支持、反驳 | 提反对、提失败场景、提被忽略的成本 |
| 禁止的行为 | —— | **不许提建设性替代方案**（那是别人的活） |

最后一条很反直觉但很重要：一旦反方开始提方案，他就变成了又一个 specialist，
讨论会从"对抗检验"滑向"一起完善"。**反方的价值在于不收手。**

**强制实现**：`personas.py` 在拿到 LLM 输出后校验；若无人是 adversary，
**自动追加一个**再继续。这是设计规则，不是兜底逻辑 —— 它保证的是
「没有反方就不开会」这条不变量。

## 6. 信息面分配（`InfoScope`）

信息面是每个人设的**独立资料包**。详细动机见 [design.md](design.md) §4.3。

```jsonc
"info_scope": {
  "questions": [                       // 只有他回答的追问清单
    "本地 Whisper 各尺寸模型在 M 系列芯片上的显存与实时率是多少？",
    "中文场景下量化到 int8 的质量损失有多大？"
  ],
  "search_queries": [                  // 他专属的检索词
    "whisper.cpp benchmark apple silicon",
    "whisper int8 quantization chinese WER"
  ],
  "assigned_files": [                  // 从 --context-dir 按相关性分配给他的文件
    "notes/local-asr.md"
  ],
  "budget": { "searches": 4, "tokens": 20000 }
}
```

分配原则：

1. **追问清单按维度生成**，不按人。维度定了，问题自然不同。
2. **检索词由人设自己生成**（在 S1 的第二次调用里），因为检索词取决于他的视角。
3. **本地文件按维度相关性分配**，不搞人手一份 —— 重复的材料不产生信息差。
4. **预算是硬的**：超了就停止检索，如实记录"本次检索未穷尽"。

**一条实现禁令**：S2 阶段，任何人的 `StanceMemo` **不得**进入他人的 prompt。
实现时用一个显式断言守住这条（在 `recon.py` 组装 prompt 前检查消息来源列表）。
违反它，整个工具就退化成"多开几个窗口"。

## 7. 人设模板（YAML）

维度库与人设样例在 [`sparky/personas/presets/`](../sparky/personas/presets/)，
格式设计如下（**这些文件当前只是设计样例，尚未被任何代码读取**）：

```yaml
# dimensions.yaml —— 常见设计维度库，作为 S1 的参考种子
- id: offline-feasibility
  name: 离线可行性
  triggers: ["离线", "本地", "不联网", "隐私"]
  typical_questions:
    - 模型/依赖的体积与内存峰值是多少？
    - 无网络时哪些功能会退化？
  typical_cares: ["包体大小", "首字延迟", "内存峰值"]

- id: cost-curve
  name: 成本曲线
  triggers: ["API", "云服务", "规模化", "用户量"]
  typical_questions:
    - 单次调用成本是多少？规模到 10 万用户时是多少？
    - 有没有成本随规模非线性增长的环节？
  typical_cares: ["单次成本", "月度账单", "成本拐点"]
```

用户可用 `--dimensions-file` 追加自定义维度；模板与人设都能通过文件覆盖，
这就是「用户想固定评审团」这个扩展点的入口（见 [architecture.md](architecture.md) §8）。

## 8. 常见失败与规避

| 失败现象 | 根本原因 | 规避 |
|---|---|---|
| 全程零分歧 | 人设太"客观全面" | 强制 `bias` / `blind_spot` / adversary |
| 讨论变成轮流念稿 | 各人只说自己，不回应别人 | `Turn.responds_to` 强制至少一条 |
| 观点高度雷同 | 上下文同质 | 信息面隔离（§6） |
| 都在谈同一个维度 | 维度分配重叠 | S1 校验：每个维度至少一个 owner，且 owner 不重叠 |
| 反方为了反对而反对 | `aggression` 过高 | 见 [design.md](design.md) §11 未决问题 4，暂用轮数上限兜住 |
| 人数膨胀到 7 人还在加 | 维度抽取过细 | 抽取后做一次合并：语义相近的维度合并 |

## 9. 一个完整的例子

**输入**：`我想做一个给播客自动生成章节和文字稿的小工具，本地跑，不要云服务`

**S0 抽出的维度**：

| id | 维度 | 来源 |
|---|---|---|
| d1 | 离线可行性 | user（"本地跑，不要云服务"） |
| d2 | 转写质量 | user（"文字稿"隐含） |
| d3 | 产品形态 | inferred（没说是 GUI 还是 CLI） |
| d4 | 处理时长与资源占用 | inferred |
| d5 | 分发与安装成本 | inferred |

`uncertainty = medium`，无安全约束 → `panel_size = clamp(3,7,ceil(5/1.5)) = 4`，
再因 d3 是未定的产品形态、不确定性偏高，**+1 → 5 人**。

**S1 生成的专家组**（节选）：

| 名字 | 头衔 | 类型 | 立场 | 偏见 | 盲点 |
|---|---|---|---|---|---|
| 陈砚 | 离线推理工程师 | specialist | 能本地跑就绝不联网 | 低估模型体积与内存代价 | 忽略非技术用户的操作成本 |
| 林知远 | 音频算法工程师 | specialist | 质量优先，宁可慢 | 对量化损失过度敏感 | 不关心用户等待容忍度 |
| 苏晚 | 交互设计师 | generalist | 工具必须双击就能用 | 倾向 GUI，轻视 CLI 用户 | 低估命令行用户的专业度 |
| 郑铎 | 成本与运维官 | specialist | 关注长期维护成本 | 把一次性成本看得过重 | 忽略开发期的速度价值 |
| 白弈 | 唱反调者 | **adversary** | 找它会在哪里崩 | 默认所有方案都不可靠 | （故意不设） |

注意这个组的构成：陈砚（离线）和林知远（质量）**天然对立** ——
离线意味着小模型，小模型意味着质量下降。这个对立不需要人为制造，
它是从维度冲突里**长出来的**。这就是两段式设计的效果。
