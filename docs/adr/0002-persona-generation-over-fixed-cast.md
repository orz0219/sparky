# 0002. 人设按维度现场生成，而非从固定角色池挑选

- 状态：已接受
- 日期：2026-10-12

## 背景

工具要自己决定"开几个人的会、都是谁"。

最直觉的做法是准备一个固定角色池（产品经理 / 架构师 / 前端 / 后端 / 测试 /
安全专家…），按题目从里面挑几个。

但 Sparky 要处理的是**任意领域的程序设计问题**。用户可能问"给播客做本地转写工具"，
也可能问"做一个分布式任务调度器"。这两者需要完全不同的视角：
前者需要离线推理工程师和存储成本官，后者需要一致性与容错专家。
固定角色池会把所有问题都套进同一副框架 —— 而**套框架恰恰是本工具要解决的问题**
（用户卡住的原因之一就是"只想到自己熟悉的那几个维度"）。

## 决策

**两段式生成**：

1. **先抽设计维度**：从用户描述推演出"做这个设计需要考虑哪些方面"
   （如离线可行性、数据模型、成本曲线、失败模式）
2. **再为维度造人**：每个维度配一个有名字、有 `stance`（立场）、
   有 `bias`（偏见）、有 `blind_spot`（盲点）的具体专家

配套规则：

- 人数 `panel_size = clamp(3, 7, ceil(维度数 / 1.5))`，再按不确定性/安全约束修正
- **必须有至少一个 `adversary`**，缺失则由代码自动补位
- `bias` 与 `blind_spot` 是**必填字段**，不是可选项
- `blind_spot` 不进本人的 prompt，只进**其他人**的 prompt（作为攻击提示）
- 提供 `personas/presets/dimensions.yaml` 作为参考种子，但不强制使用

## 备选方案与被否决原因

| 方案 | 否决原因 |
|---|---|
| 固定角色池（产品/开发/测试三件套） | 会把所有问题套进同一副框架，正是本工具要消除的病 |
| 用户自己指定人设 | 用户的困难就是"不知道要考虑什么"，让他指定人设等于把问题还给他 |
| 全部用通用评审员（"评审员A/B/C"，无具体人设） | 实测模型扮演"角色A"明显比扮演"陈砚"敷衍，且缺少偏见就没有张力 |
| 让 LLM 自己决定人数 | 无法约束成本，且模型倾向于开更多人显得"考虑周全" |

## 后果

**收益**：

- 维度是从**具体问题**里长出来的，不是从清单里套的
- `bias` / `blind_spot` 制造出真实的立场冲突，而不是礼貌的补充意见
- 人设之间的对立往往**天然存在**（如"离线"与"质量"互斥），
  不需要人为制造张力

**代价（必须承认）**：

1. **稳定性不如固定池**。现场生成的人设质量依赖模型能力，
   弱模型可能生成出平庸、雷同的人设。
2. **维度抽取失败会连环失败**。维度抽歪了 → 人设配歪了 → 整场讨论跑偏。
   这条链路上没有中间校验点，是当前设计的脆弱环节。
3. **人数公式的系数（`/1.5`）是拍脑袋的**，见
   [../design.md](../design.md) §11 未决问题 1，需要真实案例校准。

**触发重新考虑的条件**：

- 若实测发现人设雷同率高（如 > 50% 的会话零分歧），说明现场生成质量不够，
  应加强 `presets` 的权重或改为"固定池 + 现场补充"的混合模式
- 若用户明确表达稳定的评审团偏好（"我每次都想要一个安全专家"），
  应支持 `--personas-file` 固定评审团（架构已预留）

**推翻本 ADR 需要**：新增一篇 ADR，并附上"现场生成零分歧率过高"的实测数据。
