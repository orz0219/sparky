# 0005. 网页是提案工作台：一个页面管多份提案，而不是一次运行的查看器

- 状态：已接受
- 日期：2026-10-13

## 背景

M3 做出来的网页是**一次运行的查看器**：命令行发起一场讨论，网页把这场讨论
实时显示出来，讨论结束页面就定格。它没有"提案"这个概念 ——
没有列表、没有历史、没法在页面上发起新的。

实际用了几次之后，用户提的问题很直接：

> 我这个网页上没法看到具体的已发起提案列表及相关内容，比如：
> 1. 我历史的提案是什么样的；2. 我当前的提案是什么样的；
> 3. 我新建一个提案是什么样的。这些都没有。

三条都成立。更要紧的是第三条：**在页面上新建提案，原来的架构根本做不到** ——
流水线只存在于 `__main__.main()` 的函数体里，由命令行触发；
网页是它的一个旁观者。要支持从页面发起，必须把"谁触发一次运行"这件事
从命令行手里拿出来。

还有一条隐患：`transcript.jsonl` 从 M1 起就**完整记录了每一场讨论**
（`turn.token` 除外，见 [web-ui.md](../web-ui.md) §0.2），
但除了"当场看着"之外没有任何用处 —— 那些盘上的历史**看不到**。
事件溯源的收益只兑现了一半。

## 决策

**网页是提案工作台。** 一份「提案」在磁盘上就是一个会话目录，不另造一层。

### 1. 入口：不给想法就进工作台

```
python3 -m sparky "想法"      → 起网页 + 立刻发起这一份，等它跑完（与从前一致）
python3 -m sparky             → 只起网页，进程一直服务到 Ctrl-C
```

`--no-web` 又不给想法 → 报错退出 2：既不起网页、又没有活可干。

### 2. 编排层从 `__main__` 里抽出来

新增 `pipeline.py`，只装 S0→S5 的顺序与收口。`__main__` 与 `workspace`
都调它。**抽出来的理由不是文件太长**：如果流水线只活在 `main()` 的函数体里，
工作台就只能复制一份，两份迟早漂移 —— 而漂移的后果是
"命令行跑得好好的，网页上跑出来的文档不一样"。

### 3. `workspace.py` 管三件事：读、写、控

| 动作 | 做什么 |
|---|---|
| 读 | 扫 `--out` 目录，把会话汇总成清单与详情（**只读小文件**，不碰 transcript） |
| 写 | 在页面上发起新提案：建会话 → 起后台线程 → 跑流水线 |
| 控 | 停止、插话、Ctrl-C 收口 |

### 4. 历史提案靠**重放** transcript，不重新跑模型

详情视图消费的事件流与实时讨论**完全同一条**：正在跑走 `EventHub`，
已结束的把 `transcript.jsonl` 重放成快照。前端一行都不用改。

### 5. 运行态在内存，历史态在磁盘

只有本进程发起、且还没结束的提案才有句柄。其余一律读盘。
所以进程重启后，之前"进行中"的提案会如实标成 `stale`（进程已退出）——
**不假装它还在跑**。

### 6. `EventHub` 与 `InterjectionQueue` 从 `server.py` 挪进 `events.py`

它们本来就不含任何 HTTP 概念。工作台属于编排层，
而 `docs/architecture.md` §2 禁令 1 规定**编排层不得 import `server`**。
挪进 `events` 让那条禁令保持绝对，不必为工作台开一个例外。

## 备选方案与被否决原因

| 方案 | 否决理由 |
|---|---|
| **只在现有页面加一个只读的历史列表** | 解决不了第三条（在页面上新建）。而"看不了历史"和"建不了新的"是同一个根因：网页不认识"提案"这个实体 |
| **给每次运行开一个独立端口，各开一个页面** | 用户要自己记住哪个端口是哪份提案；端口还会互相占用（本项目坚持端口冲突就报错） |
| **页面只读 `./.sparky/sessions`，不做运行管理** | 那样"新建提案"只能跳回命令行，等于把用户赶出页面 |
| **把运行态也落盘（盘上存一份"正在跑"的句柄）** | 进程被杀之后，盘上会留下一个看起来还在跑的句柄，而实际上没有任何东西在跑。**宁可显示 `stale`，不可显示假的 `running`** |
| **列表页只列最近 N 份 / 分页** | 本机工具的提案数量是几十份量级，全列出来更简单也更诚实；真到需要分页时再加 |
| **多个提案并发跑** | **选了允许并发。** 用户点了"发起"就该开始，而不是排队等一个看不见的队列。代价（并发 LLM 请求数翻倍、终端输出交错）写进「后果」 |
| **前端渲染 Markdown** | 前端有 1200→1800 行的护栏（见 [web-ui.md](../web-ui.md) §6），而且零构建的原生 JS 里写 Markdown 渲染器没法单测。放在服务端 `markdown.py` 可以写成纯函数并单测 |

## 后果

**收益**

- 用户最想要的三件事都成立：看得见历史、看得见当前、能直接新建。
- 事件溯源的收益兑现了：任何一场历史讨论都能**逐事件重放**出来，
  与当时看到的完全一致（`turn.token` 除外，它本来就不落盘）。
- 分层没有破例：`workspace` 是编排层，`server` 只认一个 `ProposalApi`
  结构协议，测试可以直接塞假实现。
- 命令行用法**完全没变**，老习惯不用改。

**代价（必须付的）**

- **前端从 1200 行涨到约 1800 行。** 多了一整个列表视图、新建表单、
  页签、以及一份 Markdown 渲染结果的排版。护栏上调了，理由写在
  [web-ui.md](../web-ui.md) §6 —— 上调本身要写理由，否则护栏形同虚设。
- **允许多份提案并发跑。** 两场讨论同时进行时，LLM 并发请求数会翻倍，
  终端进度行也会交错。**没有做队列**：排队会让用户点了"发起"却不知道
  要等多久。真要限制，用 `--concurrency` 控制单场内部的并发度。
- **`workspace.list_proposals()` 每 3 秒被轮询一次**（只在有提案在跑时）。
  所以它只读 `meta.json` / `personas.json` / `ledger.json` / `rounds/` 这几个
  小文件，**不碰 transcript** —— 后者一场讨论就有近 100KB。
- **`meta.json` 损坏的会话在清单里显示为「损坏」而不是消失。**
  这是刻意的（见 [web-ui.md](../web-ui.md) §5 的原则：前端永不隐藏已发生的事实），
  代价是清单里可能出现一条点不开的条目。
- **单条 transcript 行解析失败会直接报错，不跳过。** 进程被强杀可能留下半行，
  此时那场讨论在页面上打不开 —— 这是**故意的**：跳过会让你看到一场
  缺了一段的历史，而你无从知道缺了什么。
- **`session_id` 直接进 URL**（形如 `#/p/20261012-142656-播客章节与文字稿工具`），
  带中文，需要百分号编码。好处是 URL 可读、可排序、可手敲；
  代价是分享出去的链接长这样。
