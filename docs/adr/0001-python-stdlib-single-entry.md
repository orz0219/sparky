# 0001. Python 标准库 + 单入口，零第三方依赖、零前端构建

- 状态：已接受
- 日期：2026-10-12

## 背景

Sparky 是一个"偶尔用一次"的小工具，不是每天跑的服务。用户的使用场景是：
突然要设计个东西、没头绪、想找人聊聊。

这个场景对**启动成本极度敏感**。一个需要"先装 Python 环境、再 `pip install`
十几个包、前端还要 `npm i && npm run build`"的工具，在"我现在就想用一下"
的情境下是失败的 —— 用户会在等待依赖安装的过程中失去耐心。

同时，本机的密钥约定是"集中在 `~/.config/llm/keys.env`，新项目零配置"，
这暗示了工具应当**拿来就跑**。

## 决策

1. **只用 Python 标准库**：`urllib.request` 发 HTTP、`http.server` 起本地服务、
   `json` / `dataclasses` / `concurrent.futures` 处理数据与并发。手写 SSE 分帧。
2. **单一入口**：`python3 -m sparky "你的想法"`。不需要 `pip install`，不需要 venv。
3. **前端零构建**：原生 HTML + CSS + JS，三个文件，无 npm、无打包器、无 CDN 外链。
4. **单文件分发（M4）**：`tools/build_single_file.py` 把包与前端资源拼成
   一个自包含的 `dist/sparky.py`，可单独拷走运行。

## 备选方案与被否决原因

| 方案 | 否决原因 |
|---|---|
| `requests` + `fastapi` + `uvicorn` | 三个依赖换来的是更短的代码，但破坏了"clone 即跑"。SSE 用标准库手写只需要几十行。 |
| asyncio + `aiohttp` | 并发场景是 IO 密集但**调用次数很少**（一轮 3–7 次），线程池完全够用。引入 asyncio 会让全部代码变成 `async`，可读性下降而收益接近于零。 |
| React + Vite 前端 | 需要 node_modules 与构建步骤。而本项目的界面复杂度（四个区域、一个 SSE 订阅）远没到需要框架的程度。 |
| Tauri 桌面应用 | 需要 Rust 工具链 + 前端构建，是候选里最重的。桌面感收益 vs 复杂度代价严重不成比例。 |
| 纯终端 TUI | 最省事，但人设卡、讨论流、分歧台账三块无法并置，多轮讨论在终端里读起来是灾难。 |

## 后果

**收益**：

- clone 下来立刻能跑，没有"装不上"这一类失败
- 依赖冲突的风险为零
- 单文件分发成为可能（用户可以直接下载一个 `.py` 文件）

**代价（必须承认）**：

1. **要自己处理 HTTP 边角**：重试、超时、SSE 分帧、连接中断都要手写。
   这是实实在在的额外代码量与出 bug 的地方。
2. **没有 HTML 模板引擎**：前端数据绑定靠手写 DOM 操作，
   界面变复杂后会开始难维护。这条约束把界面复杂度**硬性封顶**了。
3. **`http.server` 是单线程的**（需显式用 `ThreadingHTTPServer`），
   且不适合暴露到公网。本项目只监听 `127.0.0.1`，这是可接受的。

**触发重新考虑的条件**：

- 若前端代码超过约 1500 行且仍在长 —— 说明界面复杂度已经超出原生 JS 的舒适区，
  应该重新评估引入构建步骤
- 若需要多人同时访问同一会话（协作场景）—— `http.server` 不再合适

**推翻本 ADR 需要**：新增一篇 ADR 说明为什么零依赖带来的收益已经不值这些代价。
