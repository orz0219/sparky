# 定稿文档规范

> 本文规定 `design.md`（Sparky 的产出物）长什么样。
> 上游是 [consensus.md](consensus.md) 的台账。

---

## 1. 为什么结构必须固定

把"写文档"整个交给 LLM 的结果是：**每次产出形状都不一样**。
这次有风险分析、下次没有；这次有方案对比、下次直接给结论。
用户拿到的是一份"看运气的文档"。

所以：

> **骨架由代码装配，LLM 只负责填充内容。**

`synthesis.py` 先生成一个带占位符的模板，再按章节分别调用 LLM 填充
（或一次调用但用结构化输出逐节回填），最后做 **§3 的合规校验**。
校验不过 → 报错，**不生成残缺文档**。

---

## 2. 章节模板

以下是 `design.md` 的完整骨架。`★` 标记的是**本工具相对"直接问一次大模型"
的核心增量**，也是合规校验的必查项。

```markdown
# <项目名> 设计文档

> 由 Sparky 生成于 <ISO 时间> ｜ 会话 <session_id>
> 参会 <N> 人 · 讨论 <R> 轮 · 未决 <M> 项

<!-- 若零分歧，在此插入「未产生实质分歧」告警块 -->

## 0. 摘要
  一段话讲清"这是个什么东西、给谁用、核心思路是什么"。
  必须能让没参与讨论的人 30 秒读懂。

## 1. 问题与目标
  1.1 目标（可验证的表述，不写"体验好"这种）
  1.2 非目标（明确不做什么 —— 与目标同等重要）
  1.3 成功判据（怎么算做成了）

## 2. 约束与假设
  2.1 硬约束（用户明确给的，不可违背）
  2.2 假设（讨论中默认成立的前提，若假设垮了方案就垮了）
  2.3 未知项（讨论时就没搞清的）

## 3. 候选方案对比 ★
  | 方案 | 核心思路 | 优点 | 缺点 | 结论 |
  3.1 逐方案展开
  3.2 被否决的方案（必须至少一个，含否决理由与"什么条件下应重新考虑"）

## 4. 最终方案
  4.1 总体架构（含 ASCII 图或 mermaid）
  4.2 模块划分与职责
  4.3 数据模型
  4.4 对外接口 / 关键流程时序
  4.5 技术选型（选了什么、为什么）

## 5. 关键取舍台账 ★
  | 取舍点 | 最终选择 | 放弃了什么 | 什么条件下该反过来选 |
  （直接来自 Ledger 中 status=tradeoff 的条目）

## 6. 风险与失败模式
  6.1 技术风险
  6.2 产品风险
  6.3 失败模式表（什么坏了 → 表现是什么 → 怎么发现）

## 7. 里程碑与验收
  分阶段，每阶段有可检验的验收标准。
  第一个里程碑必须小到"一天内能验证核心假设"。

## 8. 未决问题 ★
  ⚠️ 需要人类决策的项，每条附双方原始论据。
  这一节**允许非空**，空反而是可疑的。

## 附录 A：参会人设
  名字 / 头衔 / 立场 / 偏见 / 盲点

## 附录 B：信息来源
  每个人设实际使用的检索词与来源链接。
  若本次未做外部检索，必须在此显式说明。

## 附录 C：讨论轮次摘要
  每轮：焦点是什么、产生了哪些分歧、谁改变了立场

## 附录 D：成本统计
  调用次数 / 输入输出 token / 估算费用
```

## 3. 合规校验表

`synthesis.py` 在写盘前逐项检查。**任何一项不过 → 抛错，不写盘。**

| 检查项 | 判据 | 不过时的后果 |
|---|---|---|
| 摘要非空且 ≤ 400 字 | 长度检查 | 报错 |
| §3 存在且方案数 ≥ 2 | 结构检查 | 报错 |
| §3 至少 1 个被否决方案 | 结构检查 | 报错 |
| §5 取舍台账行数 == `Ledger` 中 `tradeoff` 条目数 | 一致性检查 | 报错（说明 LLM 漏抄或篡改） |
| §8 未决问题条数 == `Ledger` 中 `stalemate` 条目数 | 一致性检查 | 报错 |
| §6.3 失败模式表 ≥ 3 行 | 结构检查 | 报错 |
| 附录 A 人数 == `Panel` 人数 | 一致性检查 | 报错 |
| 全文无 `TODO` / `待补充` / `...` 占位 | 正则检查 | 报错 |
| 所有 `(推断)` 标记的来源都在 `Brief` 中标为 inferred | 一致性检查 | 报错 |

**关于"一致性检查"**：这类检查是**防篡改**的关键 ——
它确保 LLM 不能凭空捏造取舍项，也不能把未决项悄悄写成已决项。

## 4. 标记约定

三种标记，含义明确、不许混用：

| 标记 | 用于 | 例 |
|---|---|---|
| `(推断)` | 讨论推断出来、用户没明说的 | 「目标平台为 macOS 与 Windows `(推断)`」 |
| `⚠️ 未决` | 需要人类决策的 | 「⚠️ 未决：是否支持多语言」 |
| `⚠️ 未验证` | 讨论中提出但没找到依据的 | 「单次转写耗时约 30 秒 `⚠️ 未验证`」 |

第四种情况也常见：**讨论未被外部检索支撑**，此时在附录 B 显式说明：

```markdown
## 附录 B：信息来源

> ⚠️ 本次讨论**未使用外部检索**，全部结论基于模型的既有知识推演。
> 涉及具体数字（模型体积、耗时、价格）的表述均需在实施前实测验证。
```

## 5. 装配方式

```
     Session 状态
          │
          ▼
  ┌───────────────────┐
  │ 装配骨架           │  代码生成带占位符的模板
  │ (纯代码，无 LLM)   │  ← 保证结构固定
  └─────────┬─────────┘
            ▼
  ┌───────────────────┐
  │ 分节填充           │  每节一次调用（或一次调用 + 结构化回填）
  │ (LLM)             │  每节的 prompt 只带该节所需的状态切片
  └─────────┬─────────┘
            ▼
  ┌───────────────────┐
  │ 合规校验           │  §3 的检查表
  └─────────┬─────────┘
            ▼
      design.md 落盘 ──► doc.ready 事件
```

**分节填充的好处**：每节只喂它需要的状态，比把全场记录一次性塞进去
省 token，也让"某一节生成失败可以单独重试"成为可能。
代价是调用次数变多 —— 见 [design.md](design.md) §10 成本相关取舍。

## 6. 一个反例（不要这样）

以下是**不合格**的产出，用来对照：

```markdown
# 播客工具设计

## 概述
这是一个很棒的播客工具，它能够自动生成章节和文字稿，用户体验非常好。
我们采用了先进的技术方案，具有很好的扩展性。

## 技术方案
使用 Python 实现。具体细节可以根据需要调整。

## 总结
总之这是一个可行且优秀的方案。
```

问题清单（每一条都对应 §3 的一个检查项）：

1. 没有非目标 → 无法判断边界
2. 没有候选方案对比 → 看不出探索过
3. 没有取舍台账 → 看不出放弃了什么
4. 没有失败模式 → 上线必然踩坑
5. 没有未决问题 → **最可疑**，要么没想清楚，要么在装懂
6. 「非常好」「很好」「先进」→ 不可验证的措辞
7. 「具体细节可以根据需要调整」→ 这不是设计文档，这是敷衍

**一句话判据**：如果这份文档换成任何一个相像的项目都成立，
那它就是废的。
