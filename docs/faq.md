# 常见问题

## 它和「直接问一次 ChatGPT」有什么区别？

一句话：**它有人反对，而且你事后能查账。**

具体差异见 [design.md](design.md) 附录 A 的对照表。最实在的三点：

1. 强制多视角 + 必含反方 → 你的盲区有机会被照到
2. 每人独立信息线 → 不是把同一份输入重复采样 N 次
3. 全事件落盘可回放 → "这个结论怎么来的"能查

---

## 为什么非要"吵起来"？大家和和气气给建议不好吗？

因为**和气的建议 = 没人反对的建议 = 没被检验过的建议**。

LLM 的默认倾向是附和。你给它别人的观点，它倾向说"这个想法很好，另外补充…"。
如果不强制对抗，N 个 Agent 只会产出 N 份措辞不同的赞成票。

所以 Sparky 把「零分歧」当作**失败信号**并显式告警
（见 [consensus.md](consensus.md) §6）。

---

## 它会不会为了反对而反对，凑出一堆假分歧？

有这个风险，当前的应对是：

- 反方被禁止提建设性替代方案（只负责找问题），避免演变成第二个 specialist
- `--max-rounds` 硬上限 + 停滞检测，防止空转
- 一项目标分歧最多定向加轮 2 次，超过强制降级为取舍

反方强度目前**没有**可调参数，见 [design.md](design.md) §11 未决问题 4。

**实测的另一种失控更值得注意**：不是反方太强，而是**分歧开得太多**。
早期版本里每位参与者每轮都会再开一项新分歧，4 轮下来总数到 50 项、12 项无解，
"真收敛"这个结果从设计上就出不来。现在有两道限制：
提示词层面把新分歧收窄到"本轮交锋直接暴露的冲突、每人每轮最多 1 项"，
代码层面另有一道总数上限。超上限的议题会列进附录 C，不会被丢掉。

---

## 为什么不用 LangChain / CrewAI / AutoGen？

因为它要解决的不是"怎么编排 Agent"，而是**"怎么定义共识"和"怎么保证信息面隔离"**。

现有框架提供的是编排骨架（消息传递、工具调用），而这两个核心问题在框架层
没有答案 —— 你仍然得自己写共识判定和信息隔离。既然核心逻辑都得自己写，
再压一层框架只会让依赖变重、行为变不可预测。

另外本项目**零第三方依赖**是有意为之：少一个依赖，少十个"装不上"的理由。

---

## 为什么是 Python 标准库？不用 `requests` / `httpx` / `fastapi`？

`urllib` 发请求、`http.server` 起服务、手写 SSE —— 都够用，且都是标准库。

代价是要自己处理一些边角（重试、SSE 分帧）。但换来的是：**clone 下来就能跑**，
不需要 `pip install`，不需要 venv，不会因为某天依赖冲突而挂掉。

---

## 支持哪些模型供应商？

任何 OpenAI 兼容的 `/chat/completions`。默认 DeepSeek 官方。
已确认可用的地址清单见 [configuration.md](configuration.md) §3。

也预留了「每个 Agent 走不同供应商」的配置结构，但 v0.1 不实现。

---

## 密钥怎么配？

```bash
# 推荐：集中管理，换 key 只改一处
echo 'DEEPSEEK_API_KEY=sk-...' >> ~/.config/llm/keys.env
```

密钥**只**从环境变量读，命令行不提供 `--api-key`（会进 shell history）。
缺密钥时启动即报错退出，不会"降级跑一次试试"。

---

## 讨论中途能插话吗？

**不能**，这是刻意的。

多轮讨论有一条约束：**每轮只读上一轮的快照**，且轮内所有 Agent 并发生成。
中途插话会破坏这条不变量，让同一轮里不同 Agent 看到不同的世界 ——
这类 bug 在并发下不可复现，代价远大于收益（见 [consensus.md](consensus.md) §2.1）。

想补充信息，请开一个新会话。

---

## 如果最后没达成一致怎么办？

**如实告诉你没达成。**

没收敛的项会原样进入文档的「⚠️ 未决问题」一节，附双方原始论据，
置顶提示"这一项 AI 无法决策"。

死锁的处理优先尝试降级为**取舍**（写明"什么条件下该反过来选"）——
多数所谓死锁其实是条件分歧。真正的价值观冲突就交给人类。

**底线**：无论多难看，都不会把未决项写成已决项。

顺带一提：**"达成了共识"和"降级为取舍"是两种不同的收敛**，文档里分得很清 ——
前者进第 3 节，后者进第 5 节（带"什么条件下该反过来选"）。

## 产出的文档质量能保证吗？

不能保证"好"，但能保证**结构完整**和**没有伪造**。

结构上：骨架由代码装配，LLM 只填内容，写盘前逐项校验
（[output-spec.md](output-spec.md) §3），不过就不写盘。

真实性上：取舍台账的条数必须与分歧台账一致、未决项条数必须与死锁数一致 ——
**LLM 无法凭空捏造或悄悄抹掉**。

至于内容本身好不好，取决于模型能力和你的输入，这部分不做承诺。

## 跑一次要多久 / 花多少钱？

实测（2026-10-12，`deepseek-flash`，4 人 3 轮）：

| 项目 | 数值 |
|---|---|
| LLM 调用 | 24 次 |
| token | 181142（其中推理 66797） |
| 耗时 | 约 4 分钟 |
| 产出 | 38461 字的设计文档 |

调用次数 = S0(1) + S1(2) + S2(人数) + S3(第 1 轮全员 + 后续轮只召集当事双方) + S5(6)。

**成本的主要风险不是人数，而是轮数**：早期版本不限分歧数时，
讨论会失控（4 轮开了 50 项分歧），既谈不完也花得多。
现在分歧总数有上限（人均 3 项），收敛是可达的 —— 上面这次就在第 3 轮自然达成了。

三个硬闸门：`--max-rounds`（默认 4）、`--budget-tokens`、`--panel-size`（上限 7）。

建议第一次先用 `--max-rounds 2` 跑一遍感受下。

## 能拿它设计代码之外的东西吗？

原则上可以 —— 它只依赖"多视角 + 分歧 + 收敛"这套结构，不依赖具体领域。
但要注意：它的输出模板（[output-spec.md](output-spec.md)）是**为程序设计**写的，
里面有"模块划分""数据模型"这类章节。用在别的领域（比如"设计一场活动"）
会出现章节不匹配。

`--personas-file` 可以固定评审团，输出模板的自定义是 [architecture.md](architecture.md) §8
列的扩展点，v0.1 不实现。
