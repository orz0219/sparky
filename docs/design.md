## 0. 一句话定义

**Sparky 把「设计一个程序」这件事，变成一场有主持人、有分歧台账、有会议纪要的专家评审会。**

输入是一句模糊的话，输出是一份可开工的设计文档。

## 1. 问题定义

### 1.1 用户处境

用户的原话是：「设计程序但没有任何头绪」。拆开看，这句话里其实是四种不同的困难：

| 编号 | 困难 | 用户脑内实际发生的事 |
|---|---|---|
| P1 | **不知道要考虑什么** | 只想到"我要一个能 X 的东西"，想不到数据模型、失败模式、部署形态、成本曲线 |
| P2 | **只有一个视角** | 一个人反复自我确认，把"我能想到的"误当成"需要考虑的全部" |
| P3 | **假共识** | "我觉得这样应该行" —— 没有任何人反对过，所以没被检验过 |
| P4 | **讨论完没沉淀** | 想了两个小时，回头打开文档还是空白 |

P1 和 P2 是**信息问题**（缺维度、缺视角）；
P3 是**验证问题**（缺少对抗）；
P4 是**结构问题**（缺少产物格式）。

Sparky 的四条对策与之一一对应，且**必须在设计上各自独立可验证**，
不能笼统地靠"多问几个模型"糊过去。

### 1.2 为什么不直接用"多开几个 ChatGPT 窗口"

朴素做法是：用户自己扮演主持人，开 N 个对话窗口，手动复制粘贴互喂。这条路在实践中
必然崩掉，原因不是麻烦，而是三个**结构性缺陷**：

1. **上下文同质**：所有窗口都拿到用户手打的同一段描述，于是 N 个回答是 N 次
   `f(同一份输入)` 的采样。这不是讨论，是重复采样。
2. **无抗辩义务**：LLM 的默认倾向是**附和**。你给它别人的观点，它会倾向说"这个想法
   很好，另外补充…"。没有机制强制它反驳。
3. **无终止条件**：什么时候算聊完了？凭感觉。而感觉没有可复现性。

Sparky 的全部设计，本质就是在补这三个洞 + 解决 P4 的产物结构。

### 1.3 成功判据

一份 Sparky 会话算成功，当且仅当满足以下全部条件（这些是**可检验的**，不是感觉）：

- [ ] **S1** 最终文档里出现至少 3 个**用户原始描述中没提到**的设计维度
      （证明 P1 被解决，而不是把用户的话换了个说法抄回来）
- [ ] **S2** 至少有 2 个 Agent 的立场**互相冲突过**，且冲突被记录
      （证明 P2/P3 被解决；如果全程零分歧，说明人设造失败了，会话标记为可疑）
- [ ] **S3** 文档含**候选方案对比**一节，且至少有一个被否决的方案连同否决理由
      （证明真的探索过而非直接跳到答案）
- [ ] **S4** 每项未解决的分歧都出现在**取舍台账**里，写明"什么条件下该反过来选"
      （证明不是和稀泥）
- [ ] **S5** 讨论全程可从 `transcript.jsonl` 回放
      （证明 P4 的沉淀是结构化的，不是把聊天记录粘成一坨）

> **注意 S2**：零分歧是**失败信号**而不是顺利信号。设计上必须让"没吵起来"这件事
> 显式暴露出来，见 [consensus.md](consensus.md) 第 6 节的「和谐告警」。

## 2. 设计目标与非目标

### 2.1 目标

| ID | 目标 | 衡量方式 |
|---|---|---|
| G1 | 一句话启动，零配置可用 | 有 `DEEPSEEK_API_KEY` 就能跑通全程 |
| G2 | 自动定人数与人设，用户不必懂提示词工程 | 用户只需输入想法本身 |
| G3 | 讨论必须产生**真实分歧**并显式记录 | 分歧台账非空且被收敛处理 |
| G4 | 产出可直接开工的详细设计文档 | 满足 [output-spec.md](output-spec.md) 的章节检查表 |
| G5 | 过程实时可见 | 浏览器里能看着它们吵 |
| G6 | 依赖极简 | 零第三方 Python 包，零前端构建 |
| G7 | 全程可复现可续跑 | 事件溯源日志 + 断点续跑 |

### 2.2 非目标（明确不做）

写清楚不做什么，比写做什么更重要：

| 非目标 | 为什么不做 |
|---|---|
| **不做代码生成** | 那是另一个工具（Claude Code / Cursor）的活。Sparky 的产物是**设计文档**，到"可以开工"为止。生成代码会把失败面扩大十倍。 |
| **不做通用聊天** | 它不是一个聊天机器人。所有对话都服务于"收敛到一个设计"。 |
| **不做长期记忆 / 跨会话人格** | 每次会议是**一次性**的。人设为本次 Brief 现场生成，不复用。 |
| **不做多用户 / 协作** | 单机单用户工具。加协作要引入账号、权限、并发一致性，与「尽量简单」直接冲突。 |
| **不做向量库 / RAG 基础设施** | 调研阶段的信息获取走「联网搜索 + 读本地文件」两条够用的路。引入向量库是过度设计。 |
| **不做模型微调 / 训练** | 纯提示词编排。 |
| **不做图形化流程编排器** | 流水线是**固定的六阶段**，不做拖拽式 workflow builder。 |

## 3. 总体架构

### 3.1 三层结构

```
┌──────────────────────────────────────────────────────────────┐
│  表现层  Presentation                                        │
│  ┌────────────────────┐   ┌──────────────────────────────┐  │
│  │ 本地网页（默认）    │   │ 终端输出（--no-web）          │  │
│  │ 气泡流 / 人设卡 /   │   │ 纯文本时间线                  │  │
│  │ 分歧台账 / 轮次轴   │   │                              │  │
│  └─────────┬──────────┘   └──────────────┬───────────────┘  │
│            └─────────── SSE / stdout ────┘                   │
├──────────────────────────────────────────────────────────────┤
│  编排层  Orchestration                                       │
│                                                              │
│   ┌────────┐  ┌─────────┐  ┌────────┐  ┌─────────┐          │
│   │ S0 立案│→│ S1 组阁 │→│ S2 调研│→│ S3 交锋 │          │
│   └────────┘  └─────────┘  └────────┘  └────┬────┘          │
│                                              ▼               │
│                                        ┌──────────┐          │
│                                        │ S4 收敛  │──┐       │
│                                        └──────────┘  │       │
│                                              ▼       │       │
│                                        ┌──────────┐  │       │
│                                        │ S5 定稿  │◀─┘       │
│                                        └──────────┘          │
│                                                              │
│   ┌────────────────────────────────────────────────────┐    │
│   │ 会话总线 events.py —— 所有阶段只通过事件通信        │    │
│   │ 会话状态 session.py —— 事件溯源持久化              │    │
│   └────────────────────────────────────────────────────┘    │
├──────────────────────────────────────────────────────────────┤
│  基础层  Infrastructure                                      │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────────────┐ │
│  │ LLM 客户端   │ │ 配置与密钥   │ │ 信息获取              │ │
│  │ llm.py       │ │ config.py    │ │ 搜索 / 读本地文件     │ │
│  │ OpenAI 兼容  │ │ keys.env     │ │ （可插拔，见 §6.4）   │ │
│  └──────────────┘ └──────────────┘ └──────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

**分层的硬约束**：编排层不认识 HTTP，表现层不认识 LLM。
两者之间**只有事件流**一种通信方式。这条约束带来三个好处：
终端和网页共用同一套编排逻辑；会话天然可录制回放；单测里可以喂假事件流。

### 3.2 六阶段流水线

| 阶段 | 模块 | 输入 | 输出 | 谁来干 |
|---|---|---|---|---|
| **S0 立案** | `brief.py` | 用户一句话 + 可选补充 | `Brief`（目标/约束/非目标/未知项） | 单次 LLM 调用 |
| **S1 组阁** | `personas.py` | `Brief` | `Panel`（3–7 个人设 + 每人信息面） | 单次 LLM 调用 + 规则校验 |
| **S2 调研** | `recon.py` | `Brief` + `Panel` | 每人一份 `StanceMemo`（观点+优点+缺点+来源） | **N 并发** |
| **S3 交锋** | `debate.py` | 上一轮发言集 | 每轮：N 份 `Turn` + 更新后的分歧台账 | **N 并发** × R 轮 |
| **S4 收敛** | `consensus.py` | 分歧台账 | 判定：达成 / 加轮 / 死锁 | **纯规则，不调 LLM** |
| **S5 定稿** | `synthesis.py` | 全程状态 | `design.md` | 单次 LLM 调用 + 模板装配 |

**为什么 S4 不调 LLM**：终止条件是控制流，不是创作。
让 LLM 决定"要不要再来一轮"会导致：成本不可预测、无法复现、模型可以无限拖延。
S4 必须是**纯函数**：`(台账, 轮数, 预算) → 决策`。

### 3.3 核心概念词汇表

实现时统一用这些词，不要在代码里造同义词：

| 术语 | 英文 / 标识符 | 含义 |
|---|---|---|
| 立案书 | `Brief` | 结构化后的问题陈述：目标、约束、非目标、未知项、设计维度 |
| 设计维度 | `Dimension` | 需要考虑的一个方面，如"离线可行性"、"数据模型"、"成本" |
| 人设 | `Persona` | 一个有名字、立场、偏见、盲点的虚拟专家 |
| 专家组 | `Panel` | 本次会议的全部人设集合 |
| 信息面 | `InfoScope` | 分配给某个人设的**独立**信息来源与检索预算 |
| 立场备忘 | `StanceMemo` | 调研产物：核心主张 + 优点 + 缺点 + 依据来源 |
| 发言 | `Turn` | 讨论中的一次发言：针对哪些议题、什么立场、什么理由 |
| 分歧 | `Disagreement` | 一条被显式记录的立场冲突，有 ID、双方、状态 |
| 分歧台账 | `Ledger` | 全会话的分歧集合，是收敛判定的唯一依据 |
| 取舍 | `Tradeoff` | 一项**不打算解决**的分歧，附"什么条件下反过来选" |
| 未决问题 | `OpenQuestion` | 死锁或超出 AI 权限的决策，如实交给人类 |

## 4. 关键设计

以下五条是本项目的灵魂。每一条都对应 §1.2 里的一个结构性缺陷。

### 4.1 S0 立案：把一句话变成结构化 Brief

不能让后续阶段直接吃用户那句口语。S0 做三件事：

1. **抽取四元组**：`目标 / 约束 / 非目标 / 未知项`。
   缺的部分标 `unknown`，**不许编**（编出来的约束会污染整场讨论）。
2. **抽取设计维度**：从描述里推断这次设计需要考虑哪些方面。
   这是解决 P1 的关键一步 —— 维度清单是**从问题出发推出来的**，
   而不是从固定清单里套的。
3. **抽取"用户没说但显然重要"的维度**，并**标注为推断**。
   → 最终文档里这些会带上 `(推断)` 标记，用户可以一眼看出哪些不是自己说的。

**失败模式**：用户输入过短（如"做一个 app"）。设计上**不追问**，而是
把一切标成 `unknown` 并把"确定产品形态"本身列为第一个未知项 ——
让专家组在讨论中收敛它，这正是工具的用武之地。

### 4.2 S1 组阁：人设按维度生成，且必须有反方

**人数怎么定**（详见 [personas.md](personas.md)）：

```
panel_size = clamp(3, 7, ceil(有效维度数 / 1.5))
```

- 下限 3：少于 3 人无法形成"三方博弈"，容易变成二元对喷。
- 上限 7：超过 7 人，每轮上下文成本是 O(N²) 增长，且发言开始重复。
- 复杂度调节：Brief 中含"高不确定性"标记时 +1，含"安全/合规"约束时 +1。

**人设必须包含的字段**（这是让讨论有张力的关键）：

| 字段 | 作用 |
|---|---|
| `name` / `title` | 有名字才像人，模型扮演效果显著更好 |
| `stance` | 他天生倾向什么（"能不引入依赖就不引入"） |
| `bias` | **他的偏见**——故意写进去的，让立场有色彩 |
| `blind_spot` | **他自己看不到的**——由别人在讨论中指出来 |
| `cares_about` | 他评审时会死盯的指标 |
| `info_scope` | §4.3 的信息面 |

**硬性规则（代码层强制，不交给 LLM 自觉）**：专家组里必须至少有一个
`role_type = "adversary"` 的人设，其职责是**攻击方案而不是完善方案**。
若 S1 的输出里没有，`personas.py` 必须自动补一个再继续。

### 4.3 S2 调研：信息面隔离（解决"假讨论"）

这是整个工具**最容易做错**的地方。常见错误实现是：把 Brief 全文 +
所有参考资料塞进每个人的 prompt，然后期待他们观点不同。
结果必然是同质化。

**Sparky 的做法**：每人拿到的是**不同的切片**。

```
                    ┌──────────────────────────┐
                    │  Brief（公共层，全员可见）│
                    │  目标 / 约束 / 非目标     │
                    └────────────┬─────────────┘
                                 │
        ┌──────────┬─────────────┼─────────────┬──────────┐
        ▼          ▼             ▼             ▼          ▼
   ┌────────┐ ┌────────┐   ┌────────┐   ┌────────┐ ┌────────┐
   │架构师  │ │离线工程│   │体验设计│   │成本运维│ │唱反调  │
   │        │ │师      │   │师      │   │官      │ │者      │
   ├────────┤ ├────────┤   ├────────┤   ├────────┤ ├────────┤
   │视角问题│ │视角问题│   │视角问题│   │视角问题│ │视角问题│
   │专属检索│ │专属检索│   │专属检索│   │专属检索│ │专属检索│
   │专属文件│ │专属文件│   │专属文件│   │专属文件│ │专属文件│
   └────────┘ └────────┘   └────────┘   └────────┘ └────────┘
        │          │             │             │          │
        └──────────┴─────────────┴─────────────┴──────────┘
                                 │
                    各自产出 StanceMemo（互不可见）
```

隔离规则：

- **视角问题不同**：每个人设拿到的是**自己那个维度**的追问清单。
- **检索不同**：各自的搜索词由自己的人设生成，检索结果**只进自己的上下文**。
- **材料不同**：`--context-dir` 传进来的本地文档，按维度相关性**分配**给不同人，
  而不是人手一份。
- **互不可见**：S2 阶段任何人的产出**不得**进入他人的 prompt（这是硬约束，
  实现时用一个显式的断言守住）。

讨论的"互相看见"只发生在 S3，且**只交换立场**，不交换各自的原始推理链
（避免上下文爆炸，也保留信息差作为张力来源）。

### 4.4 S3 交锋：分歧台账是唯一真相

每轮讨论中，每个 Agent：

1. 读**上一轮所有人的结构化发言**（不是内心推理，是发言本身）
2. 输出自己的 `Turn`，必须包含至少一条对其他人的**明确回应**：
   `{target_disagreement_id, action: support|rebut|amend, reason}`
3. 提出**新的**分歧，或**关闭**已有的分歧

主持人（`debate.py` 内的逻辑角色，不必单独占一个人设名额）负责：

- 把本轮产生的冲突登记为带 ID 的 `Disagreement`
- 把已被说服的标记为 `resolved`，并**记录是谁因为什么改变立场**（这很重要：
  "谁说服了谁"是会议纪要的核心价值）
- 检测**重复辩论**：同一分歧连续两轮双方理由未变 → 强制标记 `stalemate`

**分歧的生命周期**：

```
open ──→ resolved     （一方被说服，记录理由）
  │
  ├───→ tradeoff      （双方都有理，降级为取舍，附决策条件）
  ├───→ stalemate     （连续两轮理由无变化 → 进入 S4 强制处理）
  └───→ open          （继续辩）
```

### 4.5 S4 收敛：终止条件是纯函数

```
输入：ledger（分歧台账）、round（已进行轮数）、budget（已消耗预算）

决策（按顺序判断，第一个命中即返回）：
  1. 若 ledger 中 open 与 stalemate 均为空        → done         （真达成）
  2. 若 budget 超限                               → force_stop   （如实标注未收敛）
  3. 若 round ≥ max_rounds                        → force_stop
  4. 若本轮与上轮"立场快照"完全相同（停滞检测）    → force_stop
  5. 若只剩 stalemate 且无法再辩                  → force_stop
  6. 否则                                         → another_round（定向加轮）
```

**定向加轮**：不再让全员发言，只让**该分歧的当事双方**针对**该分歧的具体问题**
再辩一轮。这既省钱，又避免无关人等把话题带偏。

**核心立场（写进 ADR 0003）**：Sparky **不追求 100% 一致**。
它追求的是「**没有任何未被解释的反对意见**」。一项分歧只要被降级为
`tradeoff` 并写明决策条件，就算收敛。而真正的死锁**如实标注为未决问题**，
交给人类 —— 伪造一致比留下一个诚实的问号有害得多。

### 4.6 S5 定稿：文档结构由模板保证

详细规范见 [output-spec.md](output-spec.md)。要点：

- 章节是**固定的**，由代码装配骨架，LLM 只负责填充内容 ——
  不能让 LLM 决定文档结构，否则每次输出形状都不一样。
- **必含**「候选方案对比（含被否决方案与理由）」与「取舍台账」两节。
  这两节是 S3/S4 的直接产物，也是本工具相对"问一次 ChatGPT"的核心增量。
- 所有**推断**内容带 `(推断)` 标记，所有**未决**内容带 `⚠️ 未决` 标记。
- 附录列出：参会人设、各人信息来源、轮次摘要、成本统计。

## 6. 支撑设计

### 6.1 LLM 层

- 协议：**OpenAI 兼容** `POST {base_url}/chat/completions`，`stream=true` + SSE。
- 供应商与密钥：见 [configuration.md](configuration.md)。密钥只从环境变量读，
  真值集中在 `~/.config/llm/keys.env`。
- **按角色分配模型**（省钱的关键）：`--model-strong` 给组阁/收敛/定稿，
  `--model-fast` 给例行发言。默认两者相同。
- **按任务性质决定要不要推理**：转写、制表、压缩、排期这类"材料已经推理过了"
  的调用关掉推理（DeepSeek 系支持 `thinking: {"type": "disabled"}`）。
  实测同一次问答 completion token 从 188 降到 22，且避开了
  "预算全被 reasoning 吃光、正文为空"这一类失败。逐节的开关矩阵见
  [configuration.md](configuration.md) §6.1。
- 已知坑（来自本机实测，必须遵守）：
  - 部分网关（Cloudflare 前置）会拦截 `Python-urllib/x.y` 这类"脚本味" UA，
    返回 `403 + error code 1010`。**必须显式设置一个正常 User-Agent**。
  - 推理模型的输出含大段 reasoning，**必须给足 `max_tokens` 与超时**，
    否则会被截断成半句话或得到空正文。
  - `GET /models` 能通**不代表** `POST /chat/completions` 能通，两者要分开验证。
  - 中文模型会在 **JSON 结构位置**写全角逗号，`response_format: json_object`
    拦不住（它不做约束解码）。处理方式是有界重试，**绝不改写模型输出的字符**。

### 6.2 并发

同一阶段内、不同 Agent 之间**无依赖** → 用 `concurrent.futures.ThreadPoolExecutor`
并发发起（IO 密集型，线程足够，不必引入 asyncio）。默认并发度 4，可配。

**硬约束**：同一轮内各 Agent **不得读取彼此本轮的输出**。
实现上用"先全体生成、后统一登记分歧"的两段式，避免写出竞态。

### 6.3 事件溯源与续跑

所有事件以 JSONL 追加写入 `transcript.jsonl`，**先落盘再广播**。
`replay()` 能从日志重建完整状态 → 支持：
断点续跑、失败重试、事后审计、以及"这个结论谁说的"追溯。

> ⚠️ **M1 状态**：事件溯源本身已经落地（`transcript.jsonl` 逐行写、
> 并发下不撕裂），但 `replay()` 与 `--resume` 属于 M4。
> M1 已经能靠 transcript 人工追溯全过程。

> 一条来自本机踩坑经验的硬性要求：**LLM 调用的上下文快照必须在调用前落盘**，
> 不能写在调用之后。否则一旦失败，最需要排查的"这次喂了什么"恰恰没有记录。

### 6.4 信息获取（可插拔）

调研阶段的信息来源设计成**接口**，有实现就启用、没有就明确降级为"纯推演"
并在文档里如实标注：

| 来源 | 实现 | 缺失时的行为 |
|---|---|---|
| 联网搜索 | 通过 LLM 供应商的联网能力或独立搜索 API | 明确标注"本次讨论未经外部检索" |
| 本地文件 | `--context-dir` 指定目录，按维度分配 | 该人设 `assigned_files` 为空 |
| 纯模型知识 | 永远可用 | —— |

**注意**：「降级为纯推演」是**用户可见且如实标注**的，不是静默的。
这与"禁止兜底逻辑"并不矛盾 —— 信息检索是**可选增强**，而非缺失前置条件；
缺少它的后果被显式写进产物，用户知情。

## 7. 前端

见 [web-ui.md](web-ui.md)。要点：

- 单个 HTML + CSS + JS，**零构建**，由 `server.py` 用标准库 `http.server` 提供。
- 数据通道：`GET /events?session=<提案 id>`（SSE）。事件协议见 [web-ui.md](web-ui.md) §2。
- **两个视图**（M3.2）：`#/` 是**提案列表**（新建表单 + 历史与进行中的提案），
  `#/p/<id>` 是**提案详情**（讨论流 + 设计文档两个页签）。
- 详情页四块：**人设卡区**（谁在开会）、**讨论流**（实时或重放）、
  **分歧台账**（当前哪些还没谈拢）、**进展时间线**。
- 不加 `--web` 则完全不启动服务器，直接往终端打文本时间线。

**一份「提案」就是一个会话目录**，不另造数据结构。看历史提案靠
**重放 `transcript.jsonl`**，不重新调模型 —— 重放出来的事件序列与实时讨论
完全同形，所以前端一行都不用改。决策与代价见
[ADR 0005](adr/0005-proposal-workspace.md)。

## 8. 失败模式与错误处理

**总原则：失败就说失败。** 宁可直接报错退出，也不要产出一份看起来正常、
实际缺斤少两的设计文档。这个工具的价值全在"可信"，一份掺假的文档比没有更糟。

| 失败 | 处理 |
|---|---|
| 缺 API Key | 启动时**立即**报错退出，提示变量名与配置文件路径。不进入任何阶段。 |
| 网络/供应商报错 | 记录完整请求上下文（快照已先落盘）→ 抛出 → 会话标记 `failed`。 |
| 模型输出非结构化 | 要求 JSON。解析失败时**有界重试一次**（附加纠正提示并发出 `json_parse_retry` 告警）；再失败则**带两次原始输出报错**。绝不改写模型输出的字符 —— 全局替换全角标点会连字符串内容一起改掉，那是静默篡改。 |
| 输出缺必需字段 | 校验失败即报错。**不填充默认值**。 |
| 专家组无人唱反调 | 自动补一个 adversary（这是设计规则，不是兜底）。 |
| 全程零分歧 | **不报错**，但在文档显著位置输出「⚠️ 本次未产生实质分歧，结论可信度存疑」。 |
| 轮数/预算耗尽仍未收敛 | 正常结束，未决项如实标注为 ⚠️ 未决。 |
| 用户中途 Ctrl-C | 已落盘内容保留，会话标记 `interrupted`，可续跑。 |

## 9. 成本与预算

成本 = 人数 × 轮数 × 上下文长度。上下文随轮次线性增长（每轮读上一轮全部发言），
所以**总成本是 O(N × R²)** —— 这是本项目最大的成本风险，必须有硬闸门。

| 参数 | 默认 | 说明 |
|---|---|---|
| `--panel-size` | auto (3–7) | 强制指定人数 |
| `--max-rounds` | 4 | 硬上限，到点必停 |
| `--budget-tokens` | 未设 | 设了就按 token 硬停 |
| `--concurrency` | 4 | 并发度 |

启动时**先打印预估成本**（人 × 轮 × 平均上下文），让用户有机会用
`--max-rounds 2` 先跑一次试试。

## 10. 取舍台账

本项目自己也要有取舍台账 —— 不能只要求别人写。

| 取舍 | 选了 | 放弃了 | 什么条件下该反过来选 |
|---|---|---|---|
| 共识定义 | 无未解释的反对意见 | 真正 100% 一致 | 若用于高风险决策（医疗/金融），需要更强的共识门槛与人工裁定 |
| 收敛判定 | 纯规则函数 | LLM 自治判断 | 若任务类型多样到规则无法覆盖，可引入 LLM 判定 + 规则兜底校验 |
| 实现形态 | Python 单入口 + 标准库 | 全栈 Web / Tauri | 若需要多人协作或有强视觉要求，应换 Tauri，但复杂度上升一个量级 |
| 信息检索 | 可插拔、缺失即标注 | 内置完整 RAG 管道 | 若处理的领域必须依赖大量私有文档，需补齐 RAG |
| 人设复用 | 每次现场生成 | 固定角色库 | 若用户有稳定的评审团偏好（如"总是带上安全专家"），应支持人设模板固定 |
| 上下文策略 | 只交换立场，不交换推理链 | 全员共享完整上下文 | 若发现信息差导致讨论浮于表面，可放开为"共享立场 + 可点名索取依据" |
| 产出语言 | 中文（当前） | 多语言 | 若要国际化，模板与提示词需外置为资源文件 |

## 11. 未决问题

诚实列出设计定稿时仍未想清楚的地方（⚠️ 这些需要在使用中验证）：

1. **`panel_size = ceil(维度数 / 1.5)` 这个系数是拍脑袋的**，需要跑若干真实案例校准。
2. **"立场快照完全相同"** 的判定粒度未定 —— 逐字比较太严（措辞必然变），
   语义比较又需要额外模型调用（违背 S4 纯规则原则）。候选方案：比较
   `(立场方向, 关闭的分歧ID集合, 新开的分歧数)` 这个三元组。
3. **信息面隔离后，Agent 可能因为信息不足而说空话**。是否需要在 S2 后
   增加一次"信息充分性自检"？暂定：先不加，靠 S1 的 `budget` 参数控制。
4. **唱反调角色的合适强度**未知。太弱则附和，太强则为了反对而反对、
   拖长轮次。可能需要在人设里加 `aggression` 参数。
5. **多人设共用同一模型时的同质化程度**尚未实测。若同质化严重，
   需要支持"每个 Agent 走不同供应商"（架构上已预留，配置层未定）。
6. **分歧总数的上限（人均 3 项、下限 8 项）同样是拍脑袋的**（M2 实现时新增）。
   它存在的理由是实测教训：不限的话第 1 轮开 26 项、之后每轮每人再开约 1 项，
   4 轮下来 50 项、12 项无解，`done` 分支**永远不可达**。
   但这个上限设成多少才既收敛得下来、又不砍掉有价值的探索，需要真实案例校准。
   见 [consensus.md](consensus.md) 与 `debate.disagreement_cap`。
7. **`MAX_FOCUS_PER_ITEM = 2` 也未经校准**。它决定一项分歧最多被定向加轮几次；
   太小会让复杂分歧过早变成僵局，太大会拖长轮次。
8. **S3 的"立场交换"边界值得再想**：目前讨论阶段共享各人的 `core_claim`
   与前两条 `cons`，不共享 `reasoning` 与 `evidence`。这个切法未经实测检验 ——
   切得太紧会让讨论浮于表面，太松会让观点迅速趋同（见 ADR 0004）。
