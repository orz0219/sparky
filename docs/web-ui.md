## 0. 实现时确定的几件事

### 0.4 网页从「一次运行的查看器」变成「提案工作台」

M3 做出来的网页不认识"提案"：命令行发起一场讨论，页面把这场讨论显示出来，
结束就定格。**在页面上新建提案在当时是做不到的** —— 流水线只存在于
`__main__.main()` 的函数体里，网页只是它的旁观者。

M3.2 把这件事翻了过来，细节见 §8 与
[ADR 0005](adr/0005-proposal-workspace.md)。这里只记两条最容易做错的：

1. **一份「提案」= 一个会话目录。** 不另造一层数据结构。
   UI 里叫「提案」是因为用户提交的是一份想法；盘上仍是
   `meta.json` / `transcript.jsonl` 那一套。
2. **看历史提案不重新跑模型。** 后端把 `transcript.jsonl` 重放成
   **与实时讨论完全相同的事件序列**，所以前端的每一个事件处理分支
   一行都不用改。这是 M3 那套"事件是唯一通信方式"的直接收益。

### 0.1 打字机效果靠 `say` 字段，不是靠显示裸 JSON

发言的输出是**结构化 JSON**。如果直接把流式原文显示出来，
用户看到的是一段裸 JSON 被逐字敲出来：`{"say": "我反对……`。

所以做了两件事：

1. 发言的 schema 里把 `say`（这个人**说出口的话**）放在**第一位** ——
   JSON 是顺序生成的，流式前缀里最先出现的就是它；
2. 后端用 `llm.SayExtractor` **边收边抽**，只把 `say` 的值作为
   `turn.token` 广播出去。界面拿到的是干净的人话，不是 JSON 片段。

`SayExtractor` 还得处理**分片边界切在转义序列中间**的情况
（`\` 与 `n` 之间、`\u12` 与 `34` 之间）。遇到不完整就原地等下一片 ——
绝不用半个转义序列去猜，猜错会显示出一个不存在的字符。

`say` 同时是发言的**人话版本**：终端与附录 C 直接用它，
比 `amend x1、新开 1 项` 这种机器摘要可读得多（后者另存为 `actions`）。

### 0.2 `turn.token` 不落盘

一次发言能产生**上千条**增量（实测一次两句话的回答有 266 个分片）。
写进 `transcript.jsonl` 会让这份「事件溯源日志」彻底不可用 ——
它的用途是审计与回放，而逐 token 的增量对这两者都没有价值
（完整正文已经在 `turn.end` 里）。

所以事件分成两级：**临时事件**照常广播、但不写盘
（见 `events.EPHEMERAL_EVENT_TYPES`）。这不是"静默丢弃"，
而是**按用途分级**：审计日志收事件，不收增量。

副作用：新连上来的页面拿不到过去的打字机增量 —— 也不需要，
完整正文在 `turn.end` 的历史里。

### 0.3 前端按帧批量渲染

`turn.token` 是唯一的高频事件。逐个写 DOM 会卡住页面，
所以增量先进缓冲区，由 `requestAnimationFrame` 每帧统一刷一次。

## 1. 形态选择

**选了：本地网页（标准库 HTTP 服务）+ 终端纯文本兜底。**

| 候选 | 否决理由 |
|---|---|
| 纯终端 TUI | 多 Agent 多轮讨论挤在终端里，人设卡、分歧台账、时间线三者无法并置 |
| 全栈 Web（React + 构建） | 需要 npm / 打包器 / node_modules，违背零依赖 |
| Tauri 桌面应用 | 需要 Rust 工具链 + 前端构建，本项目最重的选项 |
| **本地网页 + 原生 JS** | **零构建、零依赖，且能做到实时气泡流** |

启动后自动打开 `http://127.0.0.1:8765`。
不加 `--web` 则完全不启动服务器，直接往 stdout 打文本时间线 ——
这样在 SSH 里、CI 里、以及"只想快速跑一下"时都能用。

## 2. SSE 事件协议（对外）

端点：`GET /events?session=<提案 id>`（`text/event-stream`）

```
event: turn.token
data: {"persona_id":"p3","delta":"我认为"}

event: disagreement.open
data: {"id":"x1","topic":"是否内置离线模型","parties":["p2","p3"],"status":"open",...}
```

- **`session` 是必填的。** 缺了回 400，刻意**不做"自动挑一个会话"的兜底** ——
  挑错了用户会看着别人的提案以为是自己发起的。
- 事件类型与字段**完全复用** [architecture.md](architecture.md) §5 的表，不另造一套。
- 连接建立后**先补发历史事件**（从 `transcript.jsonl` 重放），再进入实时流。
  这样中途刷新页面不会丢失已发生的讨论。
- 服务端每 15 秒发送一次 `: keepalive` 注释行防连接超时。
- 会话结束后发送 `session.end` 并主动关闭连接。

**两条硬约束**：

1. 任何事件都**不得**携带密钥、base_url 或完整 prompt。
   前端需要的是"发生了什么"，不是"内部怎么调的"。
2. **事件名不得与 `EventSource` 的 DOM 事件撞名**（`error` / `open` / `message`）。
   实测踩过：业务错误事件曾经就叫 `error`，于是前端注册的
   `addEventListener("error", …)` 会**同时**收到服务端发来的业务错误（带 `data`）
   和浏览器自己发的连接错误（不带 `data`），后者让 `JSON.parse(undefined)`
   抛异常，把真正的错误盖掉 —— 用户看到的是
   `undefined is not valid JSON`，而不是"模型不认这个输入"。
   现在业务错误叫 `session.error`，`tests/test_server.py` 有一条测试守着这条约束。

### 2.2 已结束的提案补完历史就收口

历史提案的实时队列永远不会来事件。补完快照后如果继续挂着连接，
页面会一直显示"连接中"，而那边什么都不会发生。

所以服务端在**写完快照之后**判断一次：快照里出现过 `session.end`，
或者这份提案在本进程里已经没有活的运行句柄 → 直接返回并关闭连接
（响应头带 `Connection: close`）。

前端对应地在 `onerror` 里**显式 `close()`**：`EventSource` 断开后会
自动重连，不关掉的话浏览器会一遍遍重连、一遍遍重放，
**页面上的每一段发言都会多出一份**。这不是兜底 —— 后端已经明确表示
"没有实时流了"，重连在构造上就没有意义。

### 2.1 为什么能直接复用内部事件

因为 [architecture.md](architecture.md) §2 规定编排层不认识 HTTP、
表现层不认识 LLM，两者只通过事件总线通信。
SSE 只是把内存总线上的同一种结构序列化出去。
**不需要维护两套协议** —— 这也是分层约束最直接的收益。

## 2.5 阅读体验：四个诊断与对应的修法

初版界面做出来之后，实际读一遍发现"看着难受"。量化诊断（用本机读屏工具
取坐标与字号）得到四条结论 —— **没有一条是配色问题**：

| 诊断 | 实测 | 修法 |
|---|---|---|
| **没有字号层级** | 轮次标题、人名、正文、系统消息、动作标签**全是同一字号**（倍率 1.00）。眼睛没有落点 | 建立五级字号：正文 15 / 轮次与人名 13 / 元信息 12 / 微标签 11 |
| **行长失控** | 讨论列宽约 1450px，中文一行能放 ~90 字（舒适区 35–45） | 正文限宽 **660px** |
| **主次颠倒** | 人类最关心的是"在争什么"（议程），它却被挤在 340px 角落 | 议程移进**常驻侧栏**；讨论流成为主区 |
| **噪音淹没信号** | 调研结论被渲染成 `郑维安：郑维安的演示结论：…`，看起来像发言；系统消息与人话同权 | 调研结论独立成**可折叠区**；系统消息明显更轻（12px、更淡、无背景） |

另外两条具体的难受点：

- **视线横跳**：动作标签被 flex 推到行尾（x≈2800），离发言正文隔了半个屏幕。
  改成紧跟正文下方。
- **发言用气泡框**：每段都成了同等重量的卡片，读起来像刷信息流。
  改成**左侧色条 + 无框** —— 这是"会议纪要"而不是"聊天室"。
  色条同时承担"这是谁"的识别。

还有一条交互上的发现：**插话被放进它所属的轮次里，而下一轮开始时会
自动折叠上一轮** —— 于是用户自己写的话被藏起来了。修法是在侧栏加一个
**永不折叠的"你的插话"索引**，直接回答"我插的话到底进去没有"。

### 4.1 插话：**收到即记，轮间送达**

> **这里推翻过一条决定。** 原文写的是「默认不做中途插话」，
> 理由是它会破坏"每轮只读上轮快照"的并发不变量。
> **那个约束是对的，但结论错了** —— 用户看到一场评审在进行、
> 想说一句"这个前提不对"，却被工具告知"请开新会话"，这是不可接受的。

正确的问题不是"能不能插话"，而是"**插话什么时候生效**"。

设计：用户随时可以打字，`POST /api/proposals/<id>/interject` 立即收下并广播
`client.interjection`（界面立刻显示"已记下"）；插话**在轮与轮之间**
被取空并注入下一轮的提示词，然后广播
`client.interjection.delivered`（界面改成"已在第 N 轮送达"）。

这样两边都满足了：

| | 立即打断当前轮 | **轮间送达** |
|---|---|---|
| 用户能不能随时说 | 能 | 能 |
| 破坏并发不变量 | **会** | 不会 |
| 可复现性 | 丢 | 保住 |
| 用户能否立刻看到自己的话 | 能 | 能（只是标明"还没送达"） |

提示词的措辞是刻意写死的：明说插话**优先于专家各自的偏好**
（委托人是要东西的人），**但要求专家冲突时说出来、不要默默接受**。
实测有效 —— 一次真实会话里，专家不但照做，还指出了
**委托人的两条要求互相打架**：

> p4：x7 里委托人那两条要求本来就互相打架，
> p3 的首句截断能控住长度，控不住「能直接当章节名」。

如果提示词只说"服从委托人"，这次交锋就不会发生 —— 插话会变成
"所有人立刻改口"，那比不插话更糟。

插话会写进文档**附录 C**（含送达轮次，未送达的也如实列出）——
它改变了结论，事后必须能查到"当时是谁让改的"。

### 4.2 停止同理

「停止」按钮也是**当前轮跑完才收口**，不是立刻掐断。
理由与插话完全相同。

## 5. 状态与容错

| 情况 | 前端行为 |
|---|---|
| SSE 断开，且这场讨论**没有正常收口** | 显式关掉连接（否则会自动重连并重放），顶部红条说明"发起它的进程可能已经退出"，**已落盘内容留在屏幕上** |
| 刷新页面 | 服务端先补发历史事件，界面恢复到当前状态 |
| `session.error` 事件 | 红条显示阶段与消息，保留全部历史内容（不清屏） |
| `turn.token` 洪水 | 按 `requestAnimationFrame` 批量渲染，**不**每 token 触发一次 layout |
| JS 自身异常 | `window.onerror` 捕获后在顶部显示错误条，**不留白屏** |
| 提案的 `meta.json` 损坏 | 清单里那条显示「⚠ 损坏」并写明原因，**不影响其余提案** |
| 提案是上一个进程留下的 | 状态显示「未跑完」+「发起它的进程已退出」，**不假装它还在跑** |
| `transcript.jsonl` 有一行解析不了 | 直接报错并指出行号，**不跳过** —— 跳过会让你看到一场缺了一段的历史，而你无从知道 |

**一条原则**：前端永不隐藏已发生的事实。出错也好、未收敛也好、
用户必须能看到完整信息。这和后端"失败就说失败"是同一条原则的两面。

## 6. 零构建的约束

写前端时遵守以下限制，否则"零构建"就是句空话：

- **不许用** npm、TypeScript、JSX、任何打包器、任何 CDN 外链。
- 只用原生 `<script>` / `<style>`，能用 CSS 的就不用 JS。
- 事件流手写解析（SSE 格式极简：`event:` / `data:` / 空行分隔）。
- 目标：`index.html` + `app.js` + `style.css` 三个文件，总计 **1800 行**以内
  （**三次上调，每次都有具体理由** —— 上调本身不写理由，这条护栏就形同虚设；
  `tests/test_server.py` 会盯着它）：

  | 上限 | 什么时候调的 | 理由 |
  |---|---|---|
  | 1000 | 最初 | 还没有任何 UI 的时候拍的 |
  | 1200 | M3.1 | 重做阅读体验：议程侧栏、可折叠轮次、调研结论区、插话输入框 |
  | **1800** | **M3.2** | **提案工作台：多了一整个列表视图、新建表单、页签、设计文档排版** |

  工作台这一步涨了约 500 行，全部是**新的界面**，不是把旧界面写复杂。
  真正该警惕的信号不是行数，而是"开始出现重复的样板代码" ——
  那时才该考虑拆文件或上构建，而不是提前为了行数好看去拆。
- 不引入任何字体文件与图片资源，图标用 Unicode 字符（⏹ ✅ 🔴 🟡 ⚠️）。

## 8. 提案工作台（M3.2）

> 决策与代价见 [ADR 0005](adr/0005-proposal-workspace.md)。
> 模块归属见 [architecture.md](architecture.md) §1。

### 8.1 一份「提案」就是一个会话目录

不另造数据结构。`session_id` 就是目录名，也是 URL 里的 id
（形如 `20261012-142656-播客章节与文字稿工具`，可读、可排序、可手敲；
带中文所以需要百分号编码）。

### 8.2 HTTP 接口

| 方法 | 路径 | 做什么 | 失败 |
|---|---|---|---|
| `GET` | `/` `/app.js` `/style.css` | 静态资源（白名单，不拼路径） | 缺失 → 500 并写 stderr，**不返回空白页** |
| `GET` | `/api/proposals` | 提案清单（按开始时间倒序） | — |
| `GET` | `/api/proposals/<id>` | 单份提案的详情 | 不存在 → 404 |
| `GET` | `/api/proposals/<id>/doc` | 最终文档，**渲染成 HTML** | 还没定稿 → 404 |
| `POST` | `/api/proposals` | 发起一份新提案，**立刻返回**，运行在后台线程 | 参数越界 → 400 |
| `POST` | `/api/proposals/<id>/stop` | 请求优雅停止 | 不在本进程里跑 → 409 |
| `POST` | `/api/proposals/<id>/interject` | 插话 | 没在跑 → 409；内容为空 → 400 |
| `GET` | `/events?session=<id>` | SSE 事件流 | 缺 `session` → 400；不存在 → 404 |

**`/api/*` 的响应永远是 JSON，成功和失败都一样。** 前端对每个响应都调
`r.json()`；失败时回一段纯文本，前端会在解析那一步抛异常，
于是**真正的原因被解析错误盖掉** —— 用户看到"Unexpected token"，
而不是"这份提案没在跑"。

### 8.3 清单只读小文件

清单页每 3 秒轮询一次（只在有提案在跑时），所以 `list_proposals()`
只读 `meta.json` / `personas.json` / `ledger.json` / `rounds/` 这几个小文件，
**不碰 `transcript.jsonl`** —— 后者一场讨论就有近 100KB。

### 8.4 状态归一成六种

`meta.json` 里存的是原始状态（`running` / `completed` / `interrupted` /
`failed: Xxx`），清单页要的是**能直接显示**的六种：

| 状态 | 什么时候 | 徽章 |
|---|---|---|
| `running` | 本进程里有活的运行句柄 | ● 进行中 |
| `completed` | 正常收口 | ✓ 已完成 |
| `interrupted` | 被停止 / 被 Ctrl-C | ⊘ 已中断 |
| `stale` | `meta.json` 说 `running`，但本进程没有句柄 → **上一个进程已经不在了** | ⊘ 未跑完 |
| `failed` | 失败（附异常类名） | ✗ 已失败 |
| `broken` | `meta.json` 缺失或不是合法 JSON | ⚠ 损坏 |

`stale` 是这张表里最重要的一个：**假装它还在跑（显示"进行中"）
会让用户一直等一场永远不会结束的讨论。**
