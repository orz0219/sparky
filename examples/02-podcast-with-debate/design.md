## 0. 摘要

这是一个本地运行的播客工具：输入播客音频，输出章节划分与文字稿，全程不依赖云服务，不调用任何云端语音识别或大模型 API，也不做音频上传、账号体系、云端存储与协作。目标运行环境是 8GB 内存、完全断网的笔记本，用户到手总量压在 1GB 以内，默认使用 int8 量化模型，不留云端回退路径。安装路径按目标机 3 步、权重单独拷贝 4 步设计，每一步可写成安装脚本自检。

面向不懂命令行的播客主，以及需要批量处理整季节目的使用者。

核心思路有三条。其一，章节边界与文字稿时间戳共用同一次对齐输出，章节边界表示为对齐结果里的词索引，两者偏差在定义上为 0。其二，章节边界由声学侧决定：能量跳变、谱通量、VAD 谷产出候选集并锁定时间戳，ASR 文本只对这个闭集做排序，不自由生成边界；ASR 质量差时退化为纯声学切分。其三，可编辑热词表作为第一等功能，用于收窄专有名词实体级错误率。

尚未确定的事项包括：语种、单集时长与体积、目标硬件、切分依据、是否区分说话人、时间戳精度、输出格式、使用形态、是否批量、单集耗时上限。

### 3.1 各方案展开

**方案 A：whisper.cpp/ggml int8 + 静态 ffmpeg + VAD/文本相似度切章**

核心思路：默认 small int8，medium int8 为上限；权重可校验、可单独拷贝；音频按 30–60 秒窗口分块，mmap 让权重不全部常驻内存；章节切分复用同一套 token 时间戳，不额外加载大模型；同一套对齐结果同时输出 JSON、SRT、Markdown 和章节标签。

优点：目标机完全断网时最少手动步骤为 3 步（解压离线包、放置权重、运行并选择音频），权重单独拷贝则第 4 步是 USB 拷贝（未验证）；离线运行时包约 120–200MB（未验证），Whisper small int8 权重约 250MB、medium int8 约 800MB（未验证），用户到手总量约 400MB–1GB（未验证）；8GB 内存笔记本可用 whisper.cpp/ggml int8 + mmap + 分块把峰值内存压在 6GB 以内（未验证）；章节切分用 VAD 静音 + 文本相似度不需要额外大模型，额外体积小于 50MB（未验证）；二进制 + 静态 ffmpeg + 量化权重，不引入 conda/pip 首次联网解析。

缺点：int8 small/medium 相对云端大模型的中文字错率差距约 5–15 个百分点（未验证）；8GB 内存下 medium/large 有 OOM 风险；分块边界会切坏词，需重叠窗口，转写耗时增加 10–20%；权重单独分发引入版本漂移，用户可能拷错模型、SHA256 校验失败、路径写错；无 GPU 时 CPU 转写 1 小时中文播客约 10–60 分钟（未验证）；轻量章节切分对话题渐变、插播广告的边界会切错，需要用户手动调整；默认不区分主播/嘉宾。

谁支持：p1 主张此路线，并给出体积、步骤、内存的执行路径。p3 的声学候选集 + 文本排序方案与 p1 的"章节切分复用同一套 token 时间戳、不额外加载大模型"相容。p2 的共用对齐主张与 p1 的"同一套对齐结果同时输出"相容。

谁反对：p4 认为不懂命令行的播客主会在第 3 步（ffmpeg / 模型权重缺失或 PATH 报错）退出；但 p4 同时承认，若用 PyInstaller 打成单文件、内嵌 ffmpeg、内嵌 int8 模型，macOS 和 Windows 上双击即用，这条判断整体失效。

**方案 B：声学变化点产出候选集 + ASR 文本只对闭集排序**

核心思路：声学侧（能量跳变、谱通量、VAD 谷）产出候选集并锁定时间戳，ASR 文本只对这个闭集做排序，绝不自由生成边界。

优点：章节边界时间由声学侧直接给出，与文字稿词级时间戳来自同一条对齐结果，不会出现章节和文字稿对不上；文本只做排序，候选集是闭集，ASR 质量差时最多退化成纯声学切分，不会凭空生成一个音频里不存在的边界；降低声学阈值把候选拉到 2 倍，再让文本排序砍掉假阳性，比纯声学（单阈值）或纯文本（无法产出时间戳）的单参数方案可控。

缺点：两人抢话、话题漂移但不换话轮的段落，声学变化点同样抓不到，2 小时节目可能只落 3–8 个章节，必须有兜底策略（固定时长的低置信候选、或允许用户手动打点）；要在一次解码里同时拿到 VAD、变化点、词级时间戳和文本排序特征，还多出句子嵌入或词频统计的依赖，相对纯声学链路处理耗时与音频时长的比值明显抬高，长音频峰值内存也多一份窗口缓存；文本排序引入语言依赖，中文需要分词，口语停顿词（嗯、那个、就是）会污染词汇衔接度指标，得额外做停用词和填充词过滤。

谁支持：p3 主张此路线，理由是静音谷切的是话轮不是话题，声学侧的正确角色是产出高精度候选集而非唯一依据。

谁反对：无专家直接反对该方案本身。p3 自己指出召回天花板低、RTF 与内存上升、文本排序引入语言依赖三项代价。

**方案 C：章节边界与文字稿词级时间戳共用同一次强制对齐输出**

核心思路：章节边界被表示成对齐结果里的词索引，两个字段取的是同一个数。

优点：章节边界与词级时间戳的偏差恒为 0，这是定义推论，不是估计值；把度量从整体 WER 换成专有名词实体级准确率是可执行的，同一段音频跑两次（开/关热词表），对人工标注的嘉宾名、公司名、产品名清单逐项比对，就能得到自己的差值，不依赖任何外部基准；热词表是可干预项，错误率差距不是选型的固定成本，而是可以逐期节目收敛的量；用词索引而非绝对时间点定义章节边界，日后更换对齐模型时可以整批重算章节，而不用重新人工调边界。

缺点：15–25 与 5–8 这两个百分点区间是估算，不是实测，没有任何一条已验证来源支撑；热词表把成本转给了用户，播客嘉宾名往往在录制当天才确定，没有词表的默认路径恰恰是差距最大的那条路径；共用的单次对齐是单点故障，如果对齐在中英切换点跳了，章节边界和文字稿时间戳会同时错在同一个位置，两者互相印证不了；共用文本域对齐会排掉音频域的高精度校正手段（独立的静音检测、说话人分段边界）；词级时间戳让输出文件明显变大，JSON 里每个词一条开始/结束时间，条目数从每段一条变成每词一条，体积可能翻一倍左右（估算，未实测）。

谁支持：p2 主张此路线，并指出共用对齐的偏差恒为 0 是定义推论。p1 的"章节切分复用同一套 token 时间戳"、p3 的"章节边界时间由声学侧直接给出，与文字稿词级时间戳来自同一条对齐结果"均与该主张相容。

谁反对：无专家直接反对共用对齐本身。p2 自己指出单点故障与放弃音频域校正手段两项代价，并给出反条件：若实测显示无热词表时专有名词实体级错误率差距 > 30 个百分点，或中英切换点 90 分位偏差 > 600 毫秒，则要求把章节边界改由音频域静音检测独立给出，而不再共用文本域对齐。

### 3.2 被否决的方案

**方案 D：纯静音谷检测决定章节边界**

- 否决理由：静音谷切的是话轮，不是话题。两人对谈的话轮间隔多在 0.2–0.5 s（未验证），超过 1.5 s 的静音在 2 小时里只有几十次量级（未验证），而人工标注的话题切换点有几十到上百个，两者基本不重合。纯静音谷切分对人工标注话题切换点的召回率约 10%–25%（±10 s 容忍），±2 s 容忍下低于 10%（未验证）。要把切点全用静音覆盖，阈值得压到 0.3 s，那会产出上千个假边界，精确率崩掉。
- **什么条件下应该重新考虑它**：若实测一段 2 小时无干净停顿的两人对谈，纯静音/声学变化点检测在 ±5 s 容忍下对人工标注切点的召回率达到 60% 以上（100 个标注切点命中 60 个以上），则声学侧可以独立决定章节边界，撤回文本排序这一环。

**方案 E：固定 30 s 硬切块、无重叠**

- 否决理由：没有静音可切时，边界必然落在词中间。固定 30 s 硬切块且无重叠时，跨块边界被切掉或重复的词约 1–3 个/边界；2 小时音频约 240 个边界，受影响词量估计占全片词数的 2%–5%，对应 WER 相对上升 2%–5%（未验证）。Whisper 类 ASR 模型以 30 s 音频窗口为处理单元，硬切正好卡在窗口边界上时更容易触发丢词与重复输出（未验证）。
- **什么条件下应该重新考虑它**：若中文播客实测 30 s 硬切块的边界丢词低于全片词数的 0.5%，则撤回必须重叠窗口的主张。

**方案 F：默认启用说话人分离（主播/嘉宾区分）**

- 否决理由：加入说话人分离会额外增加 1GB 以上权重和 torch 依赖，8GB 机器不适合默认启用（未验证）。pyannote.audio 的说话人分段与嵌入预训练权重默认从 Hugging Face Hub 拉取，需接受协议并持有 token，首次使用必须联网（未验证），与"全程在本地运行，不使用云服务"这一用户约束直接冲突。此外，说话人区分本就不是用户提出的需求。
- **什么条件下应该重新考虑它**：若能在两人抢话片段上做到说话人标签准确率高于 80%，且该权重随包分发、断网可得，则"最先崩在取权重"这条判断不成立，可重新评估是否默认启用。

## 4. 最终方案

### 4.1 总体架构

架构的硬边界来自立案书的两条约束：全程本地、无云服务，以及输出必须同时包含章节划分与文字稿。所有环节因此都必须是可离线分发的本地组件（p1）。

```
                        输入：播客音频文件
                                │
                                ▼
                  [1] 解码（随包静态 ffmpeg）
                                │  16kHz 单声道 PCM
                                ▼
                  [2] 分块器：30–60s 窗口 + 2s 重叠
                                │
                                ▼
                  [3] ASR：whisper.cpp / ggml int8
                        ▲       │
                        │       │  输出：同一次强制对齐结果
                        │       │  （段级文本 + 词级时间戳）
              [8] 可编辑热词表  │
                        │       │
            ┌───────────────────┴───────────────────┐
            ▼                                       ▼
  [4] 跨块合并去重（文本级）              [5] 声学候选检测
            │                              能量跳变 / 谱通量 / VAD 谷
            │                                       │
            │                                       │ 候选闭集 + 时间戳
            │                                       ▼
            │                             [6] 文本排序（只对闭集打分，
            │                                  不生成新边界；中文需分词、
            │                                  停用词与填充词过滤）
            │                                       │
            └───────────────┬───────────────────────┘
                            ▼
          [7] 章节 + 文字稿组装
              章节边界 = 同一次对齐结果中的词索引
              章节时间戳与文字稿词级时间戳取自同一数值
                            │
                            ▼
       输出：JSON / SRT / Markdown / 章节标签
```

这张图里有两个必须点明的结构性质：

- **只有一条时间轴。** 章节与文字稿都引用 [3] 产出的同一次强制对齐结果。[3] 是整个系统的时间戳单一来源。
- **章节候选来自音频域，章节排序来自文本域。** [5] 给出闭集候选并锁定时间戳，[6] 只在这个闭集内排序，不允许自由生成边界（p3）。

### 4.2 模块划分与职责

| 模块 | 负责什么 | 输入 | 输出 | 出处 |
|---|---|---|---|---|
| [1] 解码 | 把音频文件解成 PCM；不作为 Python 标准库依赖外部可执行文件 | 音频文件路径 | 16kHz 单声道 PCM | p1（二进制 + 静态 ffmpeg）；p4 指出 ffmpeg 不属于 Python 标准库，音频解码通常依赖外部可执行文件，缺失时错误写在 stderr 而非用户可读提示（未验证） |
| [2] 分块器 | 把 PCM 切成可处理的窗口，避免整段驻留内存 | PCM | 30–60s 音频块序列，相邻块 2s 重叠 | p1（按 30–60 秒窗口分块）；p3（2s 重叠窗口 + 文本级去重） |
| [3] ASR | 本地语音转文字，并产出段级文本与词级时间戳 | 音频块 + 热词表 | 同一次强制对齐结果（segments/words） | p1（whisper.cpp/ggml int8）；p2（词级时间戳来自注意力或 DTW 推导）；p2（章节与文字稿必须共用同一次强制对齐输出） |
| [4] 跨块合并去重 | 把各块的对齐结果拼成单一时间轴，处理重叠区的重复词 | 各块对齐结果 | 单一时间轴的对齐结果 | p3（重叠窗口 + 文本级去重） |
| [5] 声学候选检测 | 产出章节边界的候选闭集并锁定时间戳 | PCM | 候选点列表（来源特征 + 时间戳） | p3（能量跳变、谱通量、VAD 谷产出候选集并锁定时间戳） |
| [6] 文本排序 | 只对候选闭集做排序；中文需分词、过滤口语停顿词与填充词 | 候选闭集 + 对齐文本 | 带排序分数的候选点 | p3（ASR 文本只对这个闭集做排序，绝不自由生成边界；句子嵌入或词频统计依赖） |
| [7] 章节与输出组装 | 生成章节边界与四类产物 | 对齐结果 + 排序后的候选点 | JSON / SRT / Markdown / 章节标签 | p1（同一套对齐结果同时输出 JSON、SRT、Markdown 和章节标签） |
| [8] 热词表 | 用户可编辑的专有名词表，注入 ASR 解码 | 用户维护的词表 | 解码偏置（解码提示词、热词加权、词汇表替换） | p2（热词表必须是第一等功能而不是附加项） |

模块 [3] 的定位由 p1 与 p2 共同约束：p1 要求章节切分复用同一套 token 时间戳、不额外加载大模型；p2 要求章节边界与文字稿词级时间戳共用同一次强制对齐的输出。两者都指向「一个 ASR、一条时间轴」。

使用形态（命令行、桌面 GUI，还是被其他程序调用的库）在本轮没有形成结论：p1 的安装步骤描述里写的是「运行 CLI 或 GUI 选音频」，p4 讨论的是「作者用 PyInstaller 打成单文件、双击即用」这一路径能否成立，两者没有收敛到同一个形态。（本次讨论未覆盖）

### 4.3 数据模型

核心实体与字段如下。时间单位统一为秒；`word_index` 是全局递增的词序号，是章节与文字稿之间的连接键。

| 实体 | 字段 | 说明 | 出处 |
|---|---|---|---|
| Audio | path, sample_rate=16000, channels=1, duration_s | 16kHz 单声道是内存下界计算的基准 | p4（3 小时 16kHz 单声道 float32 含 1.728 亿个样本，约 691MB） |
| Alignment | engine, model, segments[] | 全系统唯一时间轴 | p2（共用同一次对齐输出，偏差恒为 0） |
| Segment | index, start, end, text, words[] | 段级条目 | p1（复用同一套 token 时间戳） |
| Word | index, text, start, end | 词级条目，JSON 中每个词一条 | p2（词级时间戳；条目数从每段一条变成每词一条，体积可能翻一倍左右）（未验证） |
| AcousticCandidate | id, source(energy_jump/spectral_flux/vad_valley), time_s, nearest_word_index, text_score | 候选闭集元素，先有时间戳后才有分数 | p3 |
| Chapter | index, start_word_index, start_s, end_word_index, end_s, rank_score | 边界表示为对齐结果中的词索引 | p2（章节边界若被表示成对齐结果里的词索引，两个字段取的是同一个数） |
| Hotwords | entries[] | 用户可编辑 | p2 |
| Artifacts | json, srt, markdown, chapter_tags | 四类落地产物 | p1 |

对应的 JSON 形态：

```json
{

    "path": "ep12.mp3",
    "sample_rate": 16000,
    "channels": 1,
    "duration_s": 10800

  "alignment": {

    "model": "small.int8",

        "index": 0,

        "text": "…",

          { "index": 0, "text": "…", "start": 0.0, "end": 0.32 }

  },

      "id": 0,
      "source": "spectral_flux",
      "time_s": 812.4,

      "index": 0,

    "chapter_tags": "ep12.chapters"
  }

```

三条与数据模型绑定的性质：

1. **章节时间戳与文字稿词级时间戳的偏差恒为 0，这是定义推论，不是估计值。** 章节边界若被表示成对齐结果里的词索引，两个字段取的是同一个数，不存在可累积的差值（p2，该条 evidence 标记为 `unverified: false`，置信度 high）。
2. **这个 0 偏差不等于时间轴本身准确。** 词级对齐相对音频真实位置存在绝对偏差，中英混说场景下中位偏差约 50–150 毫秒、长尾可达 300–500 毫秒，切换点附近最差（未验证）。共用的单次对齐是单点故障：对齐在中英切换点跳了，章节边界和文字稿时间戳会同时错在同一个位置，两者互相印证不了（p2）。
3. **词级时间戳让输出文件明显变大。** 条目数从每段一条变成每词一条，体积可能翻一倍左右（未验证）（p2）。

`Chapter.title` 字段保留为空：章节标题如何生成在本轮没有讨论到。（本次讨论未覆盖）

### 4.4 关键流程

#### 流程 A：长音频转写与跨块合并

1. 解码为 16kHz 单声道 PCM。**不整段读入内存**：3 小时 16kHz 单声道 float32 含 1.728 亿个样本、约 691MB 常驻，这一条足以否掉任何「整段读进内存再切块」的实现（p4，算术推导，非实测）。
2. 按 30–60 秒窗口切块，相邻块留 2 秒重叠（p1 的 30–60 秒窗口；p3 的 2 秒重叠窗口）。
3. 每块送入 whisper.cpp/ggml int8 解码，同时注入热词表偏置，得到段级文本与词级时间戳。
4. 跨块合并：对重叠区做文本级去重，得到单一时间轴（p3）。
   - 不加重叠的 30 秒硬切，每个边界被切掉或重复的词约 1–3 个（未验证）；2 小时音频约 240 个边界，受影响词量估计占全片词数 2%–5%，对应 WER 相对上升 2%–5%（未验证）。
   - 改成 2 秒重叠加文本级去重后，跨块丢词可降到接近 0，但会引入约 0.5%–2% 的重复词，且约 5%–15% 的边界需要人工核对去重结果（未验证）。
   - 另有约束：Whisper 类模型以 30 秒音频窗口为处理单元，硬切正好卡在窗口边界上时更容易触发丢词与重复输出（未验证）（p3）。
5. 分块与重叠会使转写耗时增加 10–20%（未验证）（p1）。
6. 内存路径：whisper.cpp/ggml int8 + mmap 让权重不全部常驻，配合分块，峰值可压在 6GB 以内（未验证）（p1）。

#### 流程 B：章节切分

1. **声学侧产出候选闭集。** 在 PCM 上用能量跳变、谱通量、VAD 谷检测变化点，直接锁定时间戳（p3）。声学侧单独用不够：纯静音谷切分对人工标注话题切换点的召回率约 10%–25%（±10 秒容忍），±2 秒容忍下低于 10%（未验证）；原因是静音谷切的是话轮不是话题，自发对谈的话轮间隔集中在 0.2–0.5 秒，超过 1.5 秒的静音在 2 小时对话里只有几十次量级（未验证）。
2. **文本侧只对闭集排序。** ASR 文本不自由生成边界，只对候选打分排序（p3）。中文需要分词，口语停顿词（嗯、那个、就是）会污染词汇衔接度指标，得额外做停用词和填充词过滤（p3）。
3. **边界落回唯一时间轴。** 排序结果确定边界后，边界表示为同一次强制对齐结果中的词索引；章节时间戳与文字稿词级时间戳取自同一数值，偏差恒为 0（p2，定义推论，`unverified: false`）。
4. **最坏情况可退化。** 因为候选集是闭集、文本只做排序，ASR 质量差时最多退化成纯声学切分，不会凭空生成一个音频里不存在的边界（p3）。
5. **兜底策略本轮未定论。** 两人抢话、话题漂移但不换话轮的段落，声学变化点同样抓不到，2 小时节目可能只落 3–8 个章节；p3 提出两条兜底路线——固定时长的低置信候选，或允许用户手动打点——但本轮没有在两者之间做出选择。（本次讨论未覆盖：兜底策略取哪一条）

### 4.5 技术选型

**ASR 引擎与量化：whisper.cpp / ggml，int8 量化。**
依据是硬约束：断网 + 8GB 内存 + 不留云端回退（p1）。int8 + mmap 让权重不全部常驻内存，音频按 30–60 秒窗口分块，峰值可以压在 6GB 以内（未验证）（p1）。可执行路线为 whisper.cpp/ggml int8 + 静态 ffmpeg + VAD/文本相似度切章（p1）。

**默认模型 small int8，medium int8 为上限。**
small int8 权重约 250MB，medium int8 约 800MB，large-v3 int8 约 1.5–3GB（均未验证）（p1）。8GB 内存下 medium/large 有 OOM 风险（p1）。

**不做云端回退路径。**
立案书 non_goals 已列出「不调用任何云端语音识别或大模型 API」，p1 的立场同样是「绝不留云端回退」（p1）。

**打包形态：二进制 + 静态 ffmpeg + 量化权重，不引入 conda/pip 首次联网解析。**
断网可运行率接近 100%，前提是文件校验通过（p1）。把 ffmpeg 二进制和 int8 量化模型塞进单文件包，可以把用户放弃点从第 3 步推到第 5 步（命令行参数和输出路径）（p4）。代价是外部文件导致的失败：ffmpeg 不属于 Python 标准库，音频解码通常依赖外部可执行文件，缺失时错误写在 stderr 而非用户可读提示（未验证）（p4）。

**权重可校验、可单独拷贝。**
目标机完全断网时最少手动步骤为 3 步：解压离线包、放置权重、运行并选择音频；权重单独拷贝则第 4 步是 USB 拷贝（未验证）（p1）。每一步都能写成安装脚本自检，失败直接报缺哪个文件（p1）。代价是版本漂移：用户可能拷错模型、SHA256 校验失败、路径写错，支持成本从「装完即用」变成「排障」（p1）。

**分发包体积预算：程序 120–200MB，权重 small 约 250MB / medium 约 800MB，用户到手总计约 400MB–1GB。**
以上均为未验证估算（p1）。其中运行时包（二进制、静态 ffmpeg、VAD、CLI/GUI）约 120–200MB（未验证）（p1）。这个量级可以用一个 U 盘一次拷完，不依赖任何下载（p1）。章节切分用 VAD 静音 + 文本相似度不需要额外大模型，额外体积小于 50MB（未验证）（p1）。

**不做说话人分离。**
默认不区分主播/嘉宾（p1）。两条独立理由：加入说话人分离会额外增加 1GB 以上权重和 torch 依赖，8GB 机器不适合默认启用（未验证）（p1）；pyannote.audio 的说话人分段与嵌入预训练权重默认从 Hugging Face Hub 拉取，需接受协议并持有 token，首次使用必须联网（未验证）（p4），这与本工具「全程本地」的约束直接冲突。代价是输出里没有「谁说了什么」这一列（p4），而这一列本来也不是用户提出的需求（p4）。

**章节切分走两段式：声学候选闭集 + 文本排序。**
声学侧（能量跳变、谱通量、VAD 谷）产出候选集并锁定时间戳，ASR 文本只对这个闭集做排序，绝不自由生成边界（p3）。三条依据来自 p3：时间戳同源，章节边界时间由声学侧直接给出，与文字稿词级时间戳来自同一条对齐结果；最坏情况可退化，文本只做排序，候选集是闭集；召回/精确率可分开调，降低声学阈值把候选拉到 2 倍，再让文本排序砍掉假阳性。
代价有三条（均来自 p3）：召回天花板低，两人抢话、话题漂移但不换话轮的段落声学变化点同样抓不到；相对纯声学链路，处理耗时与音频时长的比值明显抬高，长音频峰值内存也多一份窗口缓存；文本排序引入语言依赖，中文需要分词与停用词/填充词过滤，调参成本转移到文本侧。

**时间轴：单次强制对齐，章节边界表示为对齐结果中的词索引。**
章节边界与词级时间戳的偏差恒为 0，这是定义推论而非估计值（p2，`unverified: false`）。用词索引而非绝对时间点定义章节边界，意味着日后更换对齐模型时可以整批重算章节，而不用重新人工调边界（p2）。代价是共用对齐成为单点故障（p2）。共用文本域对齐还会排掉音频域的高精度校正手段（独立的静音检测、说话人分段边界）——静音中点的时间精度可能优于词级对齐，但两者不在同一时间轴上，强行共用就得放弃其中一个（p2）。

**热词表作为第一等功能。**
无热词表时，本地 ASR 的专有名词实体级错误率在中英混说播客上比云端大模型高约 15–25 个百分点，加上本地热词偏置后可收窄到 5–8 个百分点（均未验证）（p2）。因此错误率差距不是选型的固定成本，而是一个可以逐期节目收敛的量（p2）。热词偏置手段包括解码提示词、热词加权、词汇表替换，效果随词表长度与音频信噪比波动，无法给出稳定增益数值（未验证）（p2）。代价是热词表把成本转给了用户：播客嘉宾名往往在录制当天才确定，节目主不会为了跑一次转录先写词表，而没有词表的默认路径恰恰是差距最大的那条路径（p2）。

**输出四类产物：JSON、SRT、Markdown、章节标签。**
同一套对齐结果同时输出，章节边界与文字稿时间戳不会互相漂移（p1）。词级时间戳的代价见 4.3。章节标签写入音频文件的具体格式细节本轮未讨论。（本次讨论未覆盖）

**已知代价，随方案一并接受：**

- 准确率：int8 small/medium 相对云端大模型的中文字错率差距约 5–15 个百分点，对中文人名、术语、口音、重叠说话明显更弱，专有名词可能需要人工校对（未验证）（p1）。
- 耗时：无 GPU 时 CPU 转写 1 小时中文播客约 10–60 分钟（未验证）（p1）；p4 的对应量级估算是 3 小时音频需数小时到十几小时（未验证），p4 同时说明这是量级估算、无实测，可能高估 2 到 5 倍；如果用户是 Apple Silicon 或带独显的机器，这条代价基本消失（p4）。长节目批量处理不可接受（p1）。
- 幻觉：Whisper 在纯音乐段和低信噪比段会输出重复短语的幻觉字幕，可能与音频内容无关（未验证）（p4）。带 BGM 的素材上，静音检测会失效导致章节切不准（p4）。
- 章节质量：轻量章节切分不如大模型，VAD 静音 + 文本相似度对话题渐变、插播广告的边界会切错，需要用户手动调整（p1）。

**本轮未定论或未覆盖，不在此处补设计：**

- 目标运行硬件只按「8GB 内存、完全断网的笔记本」定义（p1）；Apple Silicon、带独显机器的支持范围本轮没有形成结论，p4 只指出这些机器上 CPU 耗时那条代价基本消失。（本次讨论未覆盖）
- 可接受的单集处理耗时上限。（本次讨论未覆盖）
- 是否需要批量处理整季节目。p1 只指出长节目批量处理在 CPU 上不可接受，未给出批量能力的设计。（本次讨论未覆盖）
- 默认语言设置（单语还是多语种）。p2 的论证覆盖中英混说播客这一场景，但没有给出默认语言的取舍。（本次讨论未覆盖）
- 使用形态（CLI、GUI 还是被调用的库），见 4.2。（本次讨论未覆盖）
- 章节标题的生成方式，见 4.3。（本次讨论未覆盖）

**专家给出的推翻条件（实测可改变上述选型）：**

- p1：如果实测在 8GB 断网笔记本上，medium int8 转写 2 小时中文播客峰值内存低于 7GB、字错率相对云端 large 差距小于 3 个百分点、1 小时音频 CPU 转写低于 15 分钟，就把默认模型升到 medium 并接受分发包到 1.5GB；若 VAD + 文本相似度切章与人工标注边界一致率超过 90%，可以放弃用本地小模型做话题切分的路线。
- p2：若同一批中英混说播客音频（含至少 200 个标注专有名词实体）实测显示，开启热词表后专有名词实体级错误率与云端最佳结果差距 ≤ 5 个百分点、中英切换点附近词级时间戳 90 分位偏差 < 200 毫秒、章节边界与词级时间戳在 ±300 毫秒窗口内重合率 ≥ 95%，则不再把热词表列为第一优先功能；反过来，若无热词表时差距 > 30 个百分点，或切换点 90 分位偏差 > 600 毫秒，则要求把章节边界改由音频域静音检测独立给出，不再共用文本域对齐。
- p3：如果实测 2 小时无干净停顿两人对谈，纯静音/声学变化点检测在 ±5 秒容忍下对人工标注切点召回率达到 60% 以上，则撤回文本排序这一环；如果中文播客实测 30 秒硬切块的边界丢词低于全片词数的 0.5%，则撤回必须重叠窗口的主张。
- p4：如果在 macOS（无 Homebrew）和 Windows（无 Python、无 ffmpeg）两台干净机器上，双击安装包后 30 分钟内产出第一份带时间戳的文字稿、全程无需打开终端，且 3 小时素材的章节边界与人工标注偏差在 30 秒内，同时两人抢话片段的说话人标签准确率高于 80%（该权重随包分发、断网可得），则收回「第 3 步放弃」和「最先崩在取权重」两条判断，只保留对 CPU 耗时的质疑。

## 6. 风险与失败模式

### 6.1 技术风险

**分块边界切坏词**

- 风险：长音频必须分块处理，分块边界会落在词中间。
- 触发条件：任何超过单次解码窗口的音频。p3 指出 Whisper 类 ASR 模型以 30 s 音频窗口为处理单元，硬切正好卡在窗口边界上时更容易触发丢词与重复输出（未验证）。
- 影响：p3 估算，固定 30 s 硬切块且无重叠时，跨块边界被切掉或重复的词约 1–3 个/边界；2 小时音频约 240 个边界，受影响词量估计占全片词数的 2%–5%，对应 WER 相对上升 2%–5%（未验证）。p1 估算，加重叠窗口后转写耗时增加 10–20%（未验证）。
- 缓解：p3 给出的路线是改为 2 s 重叠窗口加文本级去重，跨块丢词可降到接近 0，但会引入约 0.5%–2% 的重复词，且约 5%–15% 的边界需要人工核对去重结果（未验证）。p3 的撤回条件：若中文播客实测 30 s 硬切块的边界丢词低于全片词数的 0.5%，他撤回必须重叠窗口的主张。

**长音频内存**

- 风险：把整段音频读进内存再切块的实现会直接失败。
- 触发条件：处理数小时的单集。
- 影响：p4 给出内存下界——3 小时 16kHz 单声道 float32 音频含 1.728 亿个样本，占用约 691MB，这是处理链路的内存下界（算术推导，非实测）。p1 指出 8GB 内存下 medium/large 有 OOM 风险。
- 缓解：p1 的路线是 whisper.cpp/ggml int8 加 mmap 让权重不全部常驻内存，音频按 30–60 秒窗口分块，峰值压在 6GB 以内（未验证）。

**章节切分召回不足**

- 风险：纯静音谷检测切的是话轮不是话题，抓不到话题切换点。
- 触发条件：无干净停顿的两人对谈。p3 估算，自发对谈的话轮间隔集中在 0.2–0.5 s，超过 1.5 s 的静音在 2 小时对话里只有几十次量级（未验证）。
- 影响：p3 估算纯静音谷切分对人工标注话题切换点的召回率约 10%–25%（±10 s 容忍），±2 s 容忍下低于 10%（未验证）。2 小时节目可能只落 3–8 个章节。若把阈值压到 0.3 s 以覆盖全部切点，会产出上千个假边界，精确率崩掉。
- 缓解：p3 主张改成两段式——声学变化点（能量跳变、谱通量、VAD 谷）产出候选集并锁定时间戳，ASR 文本只对这个闭集做排序，不自由生成边界；同时需要兜底策略（固定时长的低置信候选，或允许用户手动打点）。代价是 RTF 与内存上升，且文本排序引入中文分词、口语停顿词过滤的调参成本。

**共用对齐是单点故障**

- 风险：章节边界与文字稿词级时间戳取自同一次强制对齐输出，对齐一旦漂移，两者同时错在同一位置。
- 触发条件：中英切换点附近。
- 影响：p2 指出，共用对齐的偏差在定义上恒为 0（此项置信度 high，非未验证），但两者互相印证不了，也没有第二套时间轴做 sanity check。绝对漂移方面，p2 估算中英混说场景下词级对齐相对音频真实位置的中位偏差约 50–150 毫秒、长尾可达 300–500 毫秒，切换点附近最差（未验证）。
- 缓解：p2 提出用词索引而非绝对时间点定义章节边界，日后更换对齐模型时可以整批重算章节，不用重新人工调边界。共用对齐不能消除绝对漂移，只能保证章节与文字稿错在同处。p2 的改口条件：若切换点 90 分位偏差 > 600 毫秒，他要求把章节边界改由音频域静音检测独立给出，不再共用文本域对齐；这会放弃音频域的独立静音检测、说话人分段边界等高精度校正手段。

**纯音乐与低信噪比段的幻觉字幕**

- 风险：Whisper 在纯音乐段和低信噪比段会输出重复短语的幻觉字幕，可能与音频内容无关（未验证）。
- 触发条件：带 BGM 的素材。
- 影响：文字稿出现与音频无关的内容。p4 认为这是本章节切分之前的崩点。
- 缓解：p4 指出这是算法选型问题而非工具死穴，换成基于文本嵌入的话题漂移切分可以绕开，代价是多一个嵌入模型和一次额外推理。

**说话人分离与离线约束冲突**

- 风险：本地 diarization 主流方案默认联网取权重。
- 触发条件：启用说话人区分且环境断网。
- 影响：p4 指出 pyannote.audio 的说话人分段与嵌入预训练权重默认从 Hugging Face Hub 拉取，需接受协议并持有 token，首次使用必须联网（未验证）。p1 指出加入说话人分离会额外增加 1GB 以上权重和 torch 依赖，8GB 机器不适合默认启用（未验证）。
- 缓解：p1 的方案是默认不区分主播/嘉宾，砍掉说话人分离。

**本地模型的准确率代价**

- 风险：int8 small/medium 相对云端大模型的准确率差距。
- 触发条件：中文人名、术语、口音、重叠说话、中英混说。
- 影响：p1 预计字错率差距在 5–15 个百分点（未验证）。p2 给出的是另一个度量：中英混说播客上，本地 ASR 的专有名词实体级错误率在无热词表时比云端大模型高约 15–25 个百分点，加上本地热词偏置后可收窄到 5–8 个百分点（未验证）。p2 明确说明这两个区间是估算不是实测，没有任何一条已验证来源支撑，把它当成选型依据是有风险的。
- 缓解：热词偏置（解码提示词、热词加权、词汇表替换）能降低专有名词错误率，但效果随词表长度与音频信噪比波动，无法给出稳定增益数值（未验证）。p1 的补充是专有名词可能需要人工校对。

**无 GPU 时的转写耗时**

- 风险：CPU 转写慢，长节目批量处理不可接受。
- 触发条件：无 GPU 的机器。
- 影响：p1 估算 1 小时中文播客可能 10–60 分钟（未验证）。p4 估算 3 小时音频需数小时到十几小时（未验证），并自承这条是量级估算、可能高估 2 到 5 倍；若用户是 Apple Silicon 或带独显的机器，这条代价基本消失。
- 缓解：无。

**权重单独分发引入版本漂移**

- 风险：用户可能拷错模型、SHA256 校验失败、路径写错。
- 触发条件：权重不随包分发、由用户单独拷贝。
- 影响：p1 认为支持成本从「装完即用」变成「排障」。
- 缓解：权重可校验、可单独拷贝；p1 的分发包设计是程序 120–200MB，权重 small 约 250MB / medium 约 800MB，用户到手总计约 400MB–1GB（未验证）。

**词级时间戳撑大输出文件**

- 风险：JSON 里每个词一条开始/结束时间，条目数从每段一条变成每词一条。
- 影响：p2 估算体积可能翻一倍左右（估算，未验证）。

### 6.2 产品风险

**不懂命令行的播客主在装环境阶段退出**

- 风险：p4 判断这个工具走不完——用户路径是解压、装解释器、找 ffmpeg、下模型、敲参数、找输出文件，前四步任意一步失败都只出英文报错栈，没有 GUI 兜底，用户卡在第 3 步（ffmpeg / 模型权重缺失或 PATH 报错）前后。
- 触发条件：用户自己装环境。ffmpeg 不属于 Python 标准库，音频解码通常依赖外部可执行文件，缺失时错误写在 stderr 而非用户可读提示（此条置信度 high，未验证）；不懂命令行的用户遇到英文报错栈（ffmpeg not found、No module named ...）时倾向于直接放弃而非检索解决（未验证）。
- 影响：工具在触达第一集输出之前流失用户。
- 缓解：p4 自己给出后移路径——把 ffmpeg 二进制和 int8 量化模型塞进单文件包，放弃点能从第 3 步推到第 5 步（命令行参数和输出路径）。p4 承认若作者用 PyInstaller 打成单文件、内嵌 ffmpeg、内嵌 int8 模型，macOS 和 Windows 上双击即用，他这条「第 3 步」判断整体失效，只剩参数和输出路径看不懂这种弱结论。他的收回条件：在 macOS（无 Homebrew）和 Windows（无 Python、无 ffmpeg）两台干净机器上，双击安装包后 30 分钟内产出第一份带时间戳的文字稿，全程无需打开终端。

**热词表把成本转嫁给用户**

- 风险：热词表是可干预项，但需要节目主先写词表才能收窄专有名词错误率。
- 触发条件：节目主直接跑转录，不写词表。
- 影响：p2 指出播客嘉宾名往往在录制当天才确定，节目主不会为了跑一次转录先写词表；没有词表的默认路径恰恰是差距最大的那条路径（错误率差距 15–25 个百分点，未验证）。
- 缓解：p2 主张把可编辑热词表做成第一等功能而不是附加项。他的撤回条件：若实测本地模型开启热词表后，专有名词实体级错误率与云端最佳结果的差距 ≤ 5 个百分点，他不再把热词表列为第一优先功能；若实测显示无热词表时差距 > 30 个百分点，他会进一步要求章节边界改由音频域静音检测独立给出。

**章节数过少导致交互不可用**

- 风险：两段式切分的召回天花板低，两人抢话、话题漂移但不换话轮的段落，声学变化点同样抓不到。
- 影响：p3 估算 2 小时节目可能只落 3–8 个章节，必须有兜底策略否则交互上不可用。
- 缓解：固定时长的低置信候选，或允许用户手动打点。

**多语种与时长口径未定导致风险无法收敛**

- 风险：立案书 unknowns 中的若干项直接决定上述风险是否成立：播客是单语还是多语种、单集时长与体积范围、目标运行硬件、章节切分依据、是否需要说话人区分、时间戳精度、输出格式、使用形态、是否批量处理整季、可接受的单集处理耗时上限。
- 影响：p1 的总体积估算（400MB–1GB，未验证）、p4 的 CPU 耗时代价（未验证）、说话人分离是否启用，都随这些口径变化。
- 缓解：无。这些项在本次评审中未被确定。

**说话人区分需求与离线约束的取舍**

- 风险：若后续要求输出「谁说了什么」，与全程离线的约束直接冲突。
- 影响：p4 判断 3 小时带 BGM 且两人抢话的音频，若要求说话人区分则在取权重那一步最先崩。
- 缓解：p4 自述砍掉 diarization 后这个崩点不存在，代价只是「谁说了什么」这一列没有，而这一列本来就不是用户提出的需求（立案书 non_goals 未列，unknowns 中列为待定）。

## 7. 里程碑与验收

### 7.1 M1（最小可用）

范围：在 8GB 内存、完全断网的笔记本上，用 int8 量化权重跑通一集播客的语音转文字，并输出带时间戳的文字稿。核心假设是「本地 int8 模型在目标机上能跑起来且不 OOM」，这一条必须最先被验证。

验收标准：

1. 目标机 3 步内跑通第一集：解压离线包、把权重目录放到 models/、运行 CLI 或 GUI 选音频（陆承宇）。权重单独拷贝时多一步 USB 拷贝，共 4 步。
2. 每一步都能写成安装脚本自检，失败直接报缺哪个文件（陆承宇）。
3. 到手总量压在 1GB 以内：运行时 + ffmpeg 静态 + VAD + CLI/GUI 约 120–200MB；small int8 权重约 250MB，medium int8 约 800MB；到手总计约 400MB–1GB（陆承宇）。
4. 音频按 30–60 秒窗口分块，峰值内存压在 6GB 以内（陆承宇）。
5. 断网可运行率接近 100%，前提是文件校验通过（陆承宇）。
6. 输出带时间戳的文字稿，格式为 JSON、SRT、Markdown 之一（陆承宇：同一套对齐结果同时输出 JSON、SRT、Markdown 和章节标签）。

明确不做：

- 不做章节切分（留到 M2）。
- 不做说话人区分。默认不区分主播/嘉宾；若加入 pyannote 等方案，体积和内存都会爆，8GB 机器直接出局（陆承宇）。
- 不留云端回退路径（陆承宇）。
- 不引入 conda/pip 首次联网解析（陆承宇）。

### 7.2 M2

范围：加入章节切分，采用两段式路线——声学变化点（能量跳变、谱通量、VAD 谷）产出候选集并锁定时间戳，ASR 文本只对这个闭集做排序，不自由生成边界（郑海涛）。章节边界与文字稿词级时间戳共用同一次强制对齐的输出（周婉宁）。

验收标准：

1. 章节边界与文字稿词级时间戳共用同一次对齐输出，两者偏差在定义上为 0——章节边界被表示成对齐结果里的词索引，两个字段取的是同一个数（周婉宁）。
2. 文本只做排序，候选集是闭集；ASR 质量差时最多退化成纯声学切分，不会凭空生成一个音频里不存在的边界（郑海涛）。
3. 降低声学阈值把候选拉到 2 倍，再让文本排序砍掉假阳性（郑海涛）。
4. 章节边界时间由声学侧直接给出，与文字稿词级时间戳来自同一条对齐结果（郑海涛）。
5. 中文侧做停用词和填充词过滤，处理口语停顿词（嗯、那个、就是）对词汇衔接度指标的污染（郑海涛）。
6. 提供兜底策略：固定时长的低置信候选、或允许用户手动打点（郑海涛）。

明确不做：

- 不把章节边界改由音频域静音检测独立给出——除非实测显示无热词表时专有名词实体级错误率差距 > 30 个百分点，或中英切换点 90 分位偏差 > 600 毫秒（周婉宁让步条件）。
- 不放弃共用文本域对齐去换取音频域的高精度校正手段（周婉宁）。
- 不把热词表列为第一优先功能——除非实测显示本地模型开启热词表后专有名词实体级错误率与云端最佳结果差距 ≤ 5 个百分点，且中英切换点附近词级时间戳相对人工标注的 90 分位偏差 < 200 毫秒，且章节边界与词级时间戳在 ±300 毫秒窗口内重合率 ≥ 95%（周婉宁让步条件）。

### 7.3 M3

范围：把工具推到「不懂命令行的播客主也能用」的形态，并处理长音频与批量场景。核心待验证假设是「放弃点能否从第 3 步推到第 5 步」。

验收标准：

1. 把 ffmpeg 二进制和 int8 量化模型塞进单文件包，放弃点能从第 3 步推到第 5 步（命令行参数和输出路径）（何劲松）。
2. 在 macOS（无 Homebrew）和 Windows（无 Python、无 ffmpeg）两台干净机器上，双击安装包后 30 分钟内产出第一份带时间戳的文字稿，全程无需打开终端（何劲松让步条件）。
3. 3 小时素材的章节边界与人工标注偏差在 30 秒内（何劲松让步条件）。
4. 3 小时音频的内存下界按纯算术校验：16kHz 单声道 float32 为 1.728 亿个样本，约 691MB 常驻，据此否掉任何「整段读进内存再切块」的实现（何劲松）。
5. 长播客分块边界采用重叠窗口，转写耗时增加 10–20%（陆承宇）。

明确不做：

- 不做说话人区分。两人抢话片段的说话人标签准确率高于 80% 这一条，前提是「该权重随包分发、断网可得」（何劲松让步条件）；本地 diarization 主流方案默认联网，不满足该前提则不纳入。
- 不做音频上传、账号体系、云端存储与协作（立案书 non_goals）。
- 不涉及播客录制、剪辑、降噪等音频生产环节（立案书 non_goals）。
- 不承诺长节目批量处理——无 GPU 时 CPU 转写 1 小时中文播客可能 10–60 分钟，长节目批量处理不可接受（陆承宇）。

### 待实测项（跨里程碑）

以下数字在调研备忘中标注为估算或未实测，验收时必须以实测替换，不得直接作为通过依据：

- 专有名词实体级错误率差距：无热词表时比云端大模型高约 15–25 个百分点，加本地热词偏置后可收窄到 5–8 个百分点（周婉宁，估算，未实测）。
- int8 small/medium 对中文人名、术语、口音、重叠说话的字错率差距 5–15 个百分点（陆承宇，预计）。
- 词级时间戳使 JSON 体积翻一倍左右（周婉宁，估算，未实测）。
- 3 小时音频 CPU 耗时数小时到十几小时（何劲松，量级估算，未实测，可能高估 2 到 5 倍）。
- 纯静音谷检测对人工标注话题切换点的召回率 10%–25%（郑海涛）。
- 2 小时节目可能只落 3–8 个章节（郑海涛）。
