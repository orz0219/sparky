# 示例

> ⛔ 尚未实现（M1 完成后开始积累）。

## 目的

这个工具的价值主张是"产出**详细设计文档**"。
所以最有说服力的东西是**真实的完整会话样例** ——
一句输入进去，一份文档出来，中间发生了什么全部可查。

## 计划中的内容

| 文件 | 内容 |
|---|---|
| `01-podcast-transcriber/` | 完整会话样例：输入、会话目录、最终 `design.md` |
| `02-<另一个领域>/` | 换一个领域，证明维度抽取确实是从问题长出来的 |
| `03-fixed-panel/` | 用 `--personas-file` 固定评审团的对比样例 |

每个样例目录包含：

```
0N-<名称>/
├── input.md             用户当时输入的那句话
├── design.md            最终产出的设计文档  ★ 主要看这个
├── ledger.json          分歧台账（看它怎么吵的）
├── rounds-summary.md    轮次摘要（人读的压缩版）
└── notes.md             这个样例特殊在哪、观察到了什么
```

## 三个样例要证明的三件事

1. **`01` 证明能产出一份合格的文档** —— 通过
   [output-spec.md](../docs/output-spec.md) §3 的全部 9 项检查

2. **`02` 证明维度抽取是从问题长出来的，不是套模板** ——
   两个样例的维度集合重合度应该**很低**。
   如果重合度很高，说明"现场生成维度"这个设计没有真正生效，
   应该去改 [ADR 0002](../docs/adr/0002-persona-generation-over-fixed-cast.md)

3. **`03` 证明信息面隔离确实产生了真实分歧** ——
   对比固定评审团与现场生成，看分歧质量是否有差异

## 一条诚实要求

样例**不许挑选**。"跑得最好的那三次"作为样例是在做宣传，不是做验证。

如果某个样例产出了质量差的文档，**照样收录**，并在 `notes.md` 里写清
差在哪、怀疑是哪个环节的问题。失败样例对本项目的价值远高于成功样例 ——
[design.md](../docs/design.md) §11 列的那些未决问题，
正是靠这类样例才能被解决。
