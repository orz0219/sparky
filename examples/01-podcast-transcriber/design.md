## 0. 摘要

这是一个本地运行的播客处理工具：输入音频，输出章节切分与文字稿。全部处理在本地完成，不调用云服务，无网络环境下也必须可用，运行在消费级 CPU 或单张显卡上。不做云端上传与存储，不做音频后期、播客托管与多用户协作。

使用者是处理自己播客音频的个人用户，在无独显、8–16GB 内存的机器上离线安装并运行。

核心思路：ASR 权重压到 200MB 级（int8/q5，需同时换更小骨架），以词表偏置修专有名词；两小时音频按 VAD 停顿点切块流式处理，块边界加 1.5–2 秒重叠，常驻音频内存与时长解耦；章节以句嵌入语义漂移为主信号、静音作后处理校正，章节数是输出而非调参目标；说话人分离作为 ASR 之后的后处理，复用词级时间戳；主输出为写进 MP3 的 ID3v2.3 CHAP+CTOC 帧，同一次运行顺带吐出 Podcasting 2.0 chapters JSON。

上述体积、耗时、错误率数字均来自调研备忘，其中标注未验证者尚未实测。

### 3.1 各方案展开

**200MB 级 int8/q5 小权重方案**

核心思路：把 ASR 权重压到 200MB 级（int8/q5），必要时同时换更小的模型骨架（如 small/int8 或蒸馏版），使权重能随工具一起分发。

优点：200MB 级权重能落进普通笔记本的内存预算，冷启动峰值 RSS 从 GB 级进到几百 MB 级，这是工具能不能交付的前提而不是优化项；int8/q5 的退化集中在低频词，高频常用词基本无损，整体 WER 只涨很小一截，而专有名词可以在后处理层用词表偏置、节目固定术语表来修；权重小到 200MB 之后模型可以随工具一起分发，用户离线安装、离线运行，完全满足无网络环境的约束。

缺点：int8 的伤害不均匀，整体 WER 可能只涨不到 1 个绝对百分点，但人名、机构名、中英夹杂的技术术语错误率可能是整体的好几倍，而这些正是章节标题最依赖的信号；磁盘占用不等于 RSS，1.5GB 压到 200MB 是权重差约 1.3GB，但带 Python/torch 的运行时固定开销在 1GB 上下，冷启动峰值降幅会被稀释到一半左右，用 C++ 运行时开销小、比值才接近；q5 相对 q8 的耗时方向不确定，内存带宽受限的 CPU 上 q5 更快，但反量化开销和大 batch 下的对齐问题可能让它更慢；1.5GB 到 200MB 这个跨度不是单靠量化能走完的，Whisper medium 在 fp16 约 1.5GB，单做 int8 只能到约 770MB，要到 200MB 必须同时换更小的模型骨架，两个变量混在一起出问题时无法归因。

谁支持谁反对：p2 主张此方案，并给出让步条件——若实测同一集中文+中英夹杂播客、同一骨架下 int8 相对 fp16 的专有名词与英文术语错误率上升小于 3 个百分点且整体 WER 上升小于 0.5 个百分点，就承认量化几乎白拿；若实测 q5 相对 q8 解码耗时差小于 10% 而专有名词错误率上升超过 5 个百分点，则改口为 200MB 是硬线但不该用 q5 去凑，宁可换更小骨架保 q8。p5 对此方案的立场是：若实测 int8 相对 fp16 的中文字错误率上升小于 3 个百分点且大模型 CPU 实时率实测高于 0.5（含标点与 ITN），则接受用中模型加后处理换速度。

**大模型 + 分段 + 强制对齐方案**

核心思路：放弃纯 CPU 实时可听目标，改用 int8 量化的大模型加分段与强制对齐，宁可慢十倍。

优点：把不可用风险变成可定位噪声，强制对齐后每个错字都能落到时间戳，用户可做定点修正而不是重听两小时；对笑声、静音段做幻觉检测，直接消灭 WER 根本不计分的整段编造，这是播客文字稿最致命的一类错；给出可写进验收标准的指标（分段中文字错误率、人工修正分钟数）；全本地、可批处理，不受 API 限流与隐私约束，长目录可过夜跑完。

缺点：实时率低于 1 是硬伤，两小时单集在 CPU 上要跑数小时，批量处理整个播客目录在消费级 CPU 上不现实；内存与显卡门槛抬高，大模型 fp16 权重约 3GB、int8 约 1.5–2GB，加上激活与两小时长音频的中间特征，峰值常到 4–6GB；标点恢复与数字规范化通常要再挂一个独立模型，又多一段延迟、多一份模型文件要随包分发；同一音频多次运行结果不完全一致；错字集中在最要紧的词上，节目名、嘉宾名、英文技术术语一旦错，章节标题和后续检索一起废掉。

谁支持谁反对：p5 主张此方案，并给出让步条件——若在目标机器上实测证明同一批中英混说音频下 int8 量化相对 fp16 的中文字错误率上升小于 3 个百分点且大模型 CPU 实时率实测高于 0.5（含标点与 ITN），则接受用中模型加后处理换速度；若把交付目标从逐字稿降级为章节标题加摘要，对实时率的坚持也相应放松。p2 的 200MB 级方案与本方案在权重规模上直接对立，p8 指出的 8GB 无独显机器上峰值 RSS 需低于 3GB 这一条件与本方案 4–6GB 峰值冲突。

**VAD 停顿点切块 + 1.5–2 秒重叠流式处理**

核心思路：两小时音频按 VAD 停顿点切块流式处理，只在块边界加 1.5–2 秒重叠兜底；环形缓冲只保留当前块加尾部重叠。

优点：VAD 边界让切点落在静音处，两小时音频（30 秒块约 240 块、239 个固定边界）的边界重解码从 O(块数) 降到只在少数无停顿长独白处发生，次数是个位数量级，这是可以直接计数的可验证指标；环形缓冲只需保留当前块加尾部重叠，16kHz float32 下 30 秒块约 1.9MB，两小时处理的常驻音频内存与音频时长解耦；对内存问题的排序给出明确答案——音频缓冲先吃满，且与解码结果缓存差 1–2 个数量级；重叠只有 1.5–2 秒时，边界重复文本的去重对窗口很短，合并阶段的字符串对齐成本可忽略。

缺点：VAD 多出一个模型依赖和一次对全量音频的前向扫描，两小时音频要多走一遍解码与推理，这份开销要靠省下的重解码赚回来，在安静但语速极快的播客上可能赚不回来；VAD 漏检会把词内短停顿当边界产生碎块，拉高 ASR 调用次数和调度开销，长连读段落会超出 30 秒上限仍要硬切并退回到固定窗口的边界问题；重叠区合并需要按时间戳或最长公共子串去重，这是一个新的错误源，去重做错会出现重复句或整句丢失，比边界重解码更难定位；整个结论依赖「播客里有足够静音」这一前提，垫音乐、直播未剪辑、双人抢话的音频会让 VAD 退化成随机切块；块长不均使批处理失去效率，长块和短块无法拼成同一批次，GPU 利用率下降。

谁支持谁反对：p3 主张此方案，并给出让步条件——在同一台机器、同一 ASR 模型、两小时中文播客样本上实测，若 VAD 停顿点切块的边界重解码次数不低于固定 30 秒窗口加 2 秒重叠的方案，或 VAD 全量扫描使端到端耗时反而增加 5% 以上，或样本中超过 30 秒的无停顿连续语音段占比高于 40%、VAD 边界有 30% 以上落在词内部，三者任一条成立就放弃 VAD 优先，改用固定窗口加重叠并在合并阶段去重。p7 的说话人分离方案复用词级时间戳、不需要再跑一遍独立的 VAD，与 p3 的 VAD 全量扫描存在依赖重叠。

**句嵌入语义漂移切章**

核心思路：以句嵌入的语义漂移为主信号、静音只作后处理校正，±5 秒容差下评边界 F1，章节数必须是输出而不是调参目标。

优点：话题漂移对词汇重组和口播提示词（例如「那我们接着聊」「下面说第二个问题」）敏感，而这正是人工标章节时实际看的依据；用 ±5 秒容差评 F1 可以避开「边界差两秒就判错」的假失败；验收指标可同时量化边界 F1 加上章节数偏差，过切和欠切都会在这两个数字上暴露；离线可落地，句嵌入只是前向推理，量化后权重在数十到数百 MB 量级，不依赖任何网络调用；对 ASR 错误更耐受，语义漂移比较的是句向量方向，同义改写、错字、口语重复不会像词汇重合度那样直接把深度分打碎。

缺点：附加体积与算力是实打实的代价，TextTiling 的额外权重为零，句嵌入要多占数十到数百 MB 磁盘与内存，无独显机器上两小时单集逐句编码的墙钟时间可能压不住；需要标注数据才能定阈值、最小章节长度和平滑窗口，中文播客没有现成的公开标注集，自建 30–100 集标注是真实人力开销；话题漂移对闲聊式单集和插播广告不灵，广告口播常常延续同一话题，语义上给不出边界，这类边界反而要靠音乐、音量、静音等非语义信号；标签本身带主观性，不同标注者对同一集的章节数和边界位置不会完全一致，模型 F1 的上限就此封顶；句向量在相邻句之间普遍高相似，相似度曲线偏平，峰值检测没调好时反而比 TextTiling 更容易漏切，工程实现门槛更高。

谁支持谁反对：p4 主张此方案，并给出让步条件——若在同一批 ≥30 集中文播客、±5 秒容差的人工标注上实测出 TextTiling（配合标点恢复与停用词过滤）的边界 F1 与句嵌入法差距 ≤0.03，或无独显机器上句嵌入法处理 2 小时单集的额外耗时超过 ASR 本身耗时的 2 倍（例如超过 20 分钟墙钟），就改为主推统计法加轻量监督；若实测显示「静音+音乐/音量检测」在广告与口播赞助边界上的召回比语义漂移高 0.2 以上，也接受把非语义信号从辅助信号升为并列主信号。p7 指出说话人切换点经常就是话题切换点，给切章多了一个与静音停顿互补的信号，与 p4 的语义漂移主信号形成互补。

**ID3v2.3 CHAP+CTOC 写入 MP3 作为主输出**

核心思路：把章节写进 MP3 文件本身的 ID3v2.3 CHAP+CTOC 帧，Podcasting 2.0 chapters JSON 只能作为同一次运行顺带吐出的旁挂产物。

优点：ID3v2 CHAP+CTOC 是唯一能同时被 Apple Podcasts、Overcast、VLC、foobar2000 这一类已装机的播放器读到、且不需要任何网络请求的章节载体，Podcasting 2.0 chapters JSON 只覆盖实现了 podcast namespace 的一小批客户端，覆盖面是它的子集；CHAP 的 Start/End 是 4 字节大端整数毫秒，1 小时音频的舍入上限是 0.5 毫秒，可以直接和 ffmpeg 探测出来的章节时间点做逐字节一致性校验；写入路径可以完全走命令行，ffmpeg 用 ;FFMETADATA1 的 [CHAPTER] 块配 -map_metadata 1 -codec copy 把章节并进 MP3，不重编码，成功与否直接体现在退出码上；两种输出可以从同一份内部章节模型序列化出来，章节边界、标题只算一次；章节和文字稿可以用同一个 Element ID 体系对齐。

缺点：CHAP/CTOC 只定义在 ID3v2 容器里，也就是实际只有 MP3 能就地写，输入是 M4A、FLAC、Opus 时要么整轨转码成 MP3，要么退回 m4a chapter track / cue 文件，格式分叉的维护成本落在工具身上；ID3v2.3 与 v2.4 对 CHAP 内嵌子帧 size 是否 syncsafe 的写法在各实现间不一致，写错版本会出现部分播放器读到 0 章或读到乱码章节，稳妥做法是只写 v2.3，等于主动放弃 v2.4 的 UTF-8 章节标题能力；写 ID3v2 标签是改写文件本身，原有 padding 不够时 mutagen 一类库会重写整个文件，对两小时的单集就是一次与文件等量的额外磁盘写入和数倍耗时；Podcasting 2.0 chapters JSON 单独交付对本地用户没有闭环价值；各客户端对章节的解析容错差异只能靠真机回归测试确认，本地离线环境测不了 Apple Podcasts 和 Overcast 的行为。

谁支持谁反对：p6 主张此方案，并给出让步条件——若在 Apple Podcasts（iOS 当前版）与 Overcast 上实测表明只交付 Podcasting 2.0 chapters JSON、不写 ID3 CHAP/CTOC，章节列表能正常显示且时间戳偏移小于 1 秒，同时用户接受把 JSON 托管出去，就放弃「ID3 为主输出」的立场；或者反向证据成立，用 ffmpeg 写出的 v2.3 CHAP+CTOC 在目标客户端上被忽略的比例超过 20%，也会改判，把主输出换成 m4a chapter track 加 sidecar JSON。

**纯本地说话人分离**

核心思路：两人对谈播客上做纯本地说话人分离，放在 ASR 之后做后处理，复用词级时间戳，短片段用规则吸附到最近的簇，重叠区间标成重叠而不是硬判给某一人。

优点：近场、重叠比例低的两人对谈上，miss 与 false alarm 主要由能量 VAD 决定，干净播客录音这两项很低，DER 的主要来源退化为说话人混淆，实际水平明显好于 AMI、DIHARD 这类远场重叠会议语料上的公开数字；声纹嵌入模型的参数量远小于 ASR 模型，分离环节的内存与耗时增量相对转录本身是小头，放在 ASR 之后做后处理可以复用词级时间戳，不需要再跑一遍独立的 VAD；说话人标签对章节切分有直接增益，说话人切换点经常就是话题切换点，给切章多了一个与静音停顿互补的信号；分离失败的代价是可局部化的，错的是某几个片段，不是整份文字稿。

缺点：短插话通常短于 0.5 秒，声纹嵌入在这个时长上信噪比不足，聚类会把它们归进错误的簇或自成一个伪簇，而这恰恰是听众最需要知道谁在接话的地方；抢话片段抽出的嵌入向量是两个说话人声纹的混合，与任何单一声纹都不接近，全局聚类容易过聚类成三到四人，导致整集的标签体系崩塌；额外模型与中间状态抬高峰值内存，在无显卡、8–16GB 内存的机器上，ASR 已经吃掉一大块，再叠一个分离 pipeline 有触发换页的风险，必须按块流式处理而不是整集载入；说话人人数要预先给定或自动估计，估计错会让整份文字稿的标签全错；在无网络环境下交付，模型权重必须随包分发或被用户手工放置，声纹模型的几百兆会让安装步骤多出一个容易出错的环节。

谁支持谁反对：p7 主张此方案，并给出让步条件——如果用户拿 20 集以上双人播客实测，证明在无独显、16GB 内存的目标机器上，加入声纹分离后 1 小时音频总耗时增幅超过 80%，同时 DER 高于 15%，就承认第一版应当只出带时间戳的纯文字稿，把说话人区分推到第二版；反之若实测 DER 低于 10% 且耗时增幅低于 30%，那么连「用规则吸附短片段」这个兜底都可以先不做。p3 的 VAD 方案与 p7 在「不需要再跑一遍独立 VAD」上一致。

### 3.2 被否决的方案

**大模型 + 分段 + 强制对齐方案**

- 否决理由：CPU 实时率低于 1 是硬伤，两小时单集在 CPU 上要跑数小时，批量处理整个播客目录在消费级 CPU 上不现实；内存与显卡门槛抬高，大模型 fp16 权重约 3GB、int8 约 1.5–2GB，加上激活与两小时长音频的中间特征，峰值常到 4–6GB，与 p8 提出的 8GB 无独显机器上进程峰值 RSS 低于 3GB 这一条件冲突；标点恢复与数字规范化通常要再挂一个独立模型，又多一段延迟、多一份模型文件要随包分发；同一音频多次运行结果不完全一致，用户重跑一次发现文字稿变了会怀疑工具坏了。
- **什么条件下应该重新考虑它**：在目标机器上实测证明同一批中英混说音频下 int8 量化相对 fp16 的中文字错误率上升小于 3 个百分点，且大模型 CPU 实时率实测高于 0.5（含标点与 ITN）；或者把交付目标从逐字稿降级为章节标题加摘要，此时对实时率的坚持相应放松。以上两条为 p5 明确给出的让步条件。

**固定 30 秒时钟窗口切块**

- 否决理由：两小时音频产生约 240 个块、239 个边界，每个边界都可能切断词，边界重解码次数为 O(块数)；该方案只换来 0 个句子完整性的保证。VAD 边界把这类风险集中到少数无停顿长段，边界重解码次数降到个位数量级。
- **什么条件下应该重新考虑它**：在同一台机器、同一 ASR 模型、两小时中文播客样本上实测，VAD 停顿点切块的边界重解码次数不低于固定 30 秒窗口加 2 秒重叠的方案；或 VAD 全量扫描使端到端耗时反而增加 5% 以上；或样本中超过 30 秒的无停顿连续语音段占比高于 40%、VAD 边界有 30% 以上落在词内部。三者任一条成立即改用固定窗口加重叠并在合并阶段去重。以上为 p3 明确给出的让步条件。

**TextTiling 统计切章**

- 否决理由：TextTiling 靠词汇重合度打分，在 ASR 中文口语上标点不可靠、同义改写多，深度分容易碎；ASR 输出的中文口语文本标点不可靠、同义改写与填充词多，基于词汇重合度的切分信号噪声偏大。其唯一优势是额外体积为零。
- **什么条件下应该重新考虑它**：在同一批 ≥30 集中文播客、±5 秒容差的人工标注上实测出 TextTiling（配合标点恢复与停用词过滤）的边界 F1 与句嵌入法差距 ≤0.03；或无独显机器上句嵌入法处理 2 小时单集的额外耗时超过 ASR 本身耗时的 2 倍（例如超过 20 分钟墙钟）。以上为 p4 明确给出的让步条件。

**Podcasting 2.0 chapters JSON 作为主输出**

- 否决理由：整份 chapters JSON 依赖 HTTP 托管才生效，与本地跑不联网直接冲突；RSS 里的 <podcast:chapters> 标签带 url 和 type 两个属性，其中 url 必须指向一个客户端能通过 HTTP 取到的 JSON 文件，因此整份 chapters JSON 只有在被托管之后才对客户端生效；跑出来的 chapters.json 得用户自己上传托管，否则 <podcast:chapters> 拿不到它，把它当主输出等于把工具的价值推迟到用户完成一次本来没打算做的部署；Podcasting 2.0 chapters JSON 只覆盖实现了 podcast namespace 的一小批客户端，覆盖面是 ID3v2 CHAP+CTOC 的子集。
- **什么条件下应该重新考虑它**：在 Apple Podcasts（iOS 当前版）与 Overcast 上实测表明，只交付 Podcasting 2.0 chapters JSON、不写 ID3 CHAP/CTOC，章节列表能正常显示且时间戳偏移小于 1 秒，同时用户接受把 JSON 托管出去。以上为 p6 明确给出的让步条件。

**第一版只出带时间戳的纯文字稿**

- 否决理由：多人口播的播客若不区分说话人，文字稿可读性会明显下降；同时放弃说话人切换点对章节切分的增益——说话人切换点经常就是话题切换点，给切章多了一个与静音停顿互补的信号。
- **什么条件下应该重新考虑它**：用户拿 20 集以上双人播客实测，证明在无独显、16GB 内存的目标机器上，加入声纹分离后 1 小时音频总耗时增幅超过 80%，同时 DER 高于 15%（意味着分离结果要人工逐句改正）。以上为 p7 明确给出的让步条件。

## 4. 最终方案

### 4.1 总体架构

```
                    输入音频文件（M4A / MP3 / FLAC / Opus / WAV）
                                  │
                                  ▼
                [M0] 启动自检与模型资产检查            —— p8
                     权重是否已落盘？断网时是否给出可读提示？
                                  │
                                  ▼
                [M1] 流式解码 + 重采样（环形缓冲）      —— p3, p8
                     只保留当前块 + 尾部重叠，常驻与时长解耦
                                  │
                                  ▼
                [M2] VAD 前向扫描 → 停顿点切块          —— p3
                     边界落在静音处；块尾加 1.5–2 秒重叠
                                  │
                                  ▼
                [M3] ASR 推理（量化权重，逐块解码）      —— p2, p3, p5
                     骨架与量化位宽为两个独立可配项
                                  │
                                  ▼
                [M4] 强制对齐 → 词级时间戳              —— p3, p5
                                  │
                                  ▼
                [M5] 幻觉 / 静音 / 笑声段检测            —— p5
                                  │
                                  ▼
                [M6] 标点恢复 + 数字规范化（ITN）        —— p5
                                  │
                                  ▼
                [M7] 说话人分离（带低置信兜底规则）      —— p7
                                  │
                                  ▼
                [M8] 章节切分                          —— p4, p7
                     语义漂移为主 + 静音/音乐/音量校正 + 说话人切换点
                                  │
                                  ▼
                [M9] 输出序列化                        —— p6
                     主输出：ID3v2.3 CHAP + CTOC（就地写 MP3）
                     旁挂：Podcasting 2.0 chapters JSON
                                  │
                                  ▼
                [M10] 验收统计：边界 F1（±5s 容差）+ 章节数偏差  —— p4
```

章节切分（M8）与 ASR 分块（M2）是两件事：M2 的 VAD 决定的是**推理块边界**（p3），M8 的话题漂移决定的是**章节边界**（p4），两者在本方案中不共用同一套边界。

### 4.2 模块划分与职责

| 模块 | 负责什么 | 输入 | 输出 | 出处 |
|---|---|---|---|---|
| M0 模型资产 | 保证权重在断网、无缓存时也能就位；把网络异常翻译成可读提示。主流通用库在权重从未下载且断网时会抛 urllib3 / requests 的 ConnectionError 或 URLError 长堆栈，并伴随 3–5 次指数退避重试（未验证）；TCP 被黑洞时表现为停滞数分钟、进度条停在 0%（未验证） | 安装包 / 用户手工放置的权重目录 | 可用的本地权重路径，或一条「缺模型」提示 | p8 |
| M1 解码与缓冲 | 流式读取音频、重采样到 16 kHz float32；环形缓冲只保留当前块加尾部重叠。16 kHz float32 下 30 秒块约 1.9 MB（未验证），环形缓冲约 2 MB 量级（未验证） | 音频文件 | 逐块 PCM | p3, p8 |
| M2 VAD 切块 | 对全量音频做一次前向扫描，把切点放到静音处；块尾加 1.5–2 秒重叠。VAD 模型体积在数 MB 到数十 MB 量级（未验证） | 全量音频 | 带重叠的块序列 + 块边界时间 | p3 |
| M3 ASR | 逐块推理，输出带时间戳的文本。模型以固定 30 秒输入窗口工作（未验证） | 单个音频块 | 块级识别结果 | p2, p3, p5 |
| M4 对齐 | 强制对齐，把每个字落到时间戳上，使用户可定点修正而不必重听整集 | 块级识别结果 | 词级时间戳 | p5 |
| M5 幻觉检测 | 对笑声、静音段做检测，消灭整段编造 | 词级结果 + 音频特征 | 标记为幻觉的片段 | p5 |
| M6 标点与 ITN | 独立模型做标点恢复与数字规范化；为整条流水线增加约 5%–15% 的额外耗时（未验证） | 词级结果 | 规范化文本 | p5 |
| M7 说话人分离 | 在 ASR 之后做后处理，复用词级时间戳，不另跑独立 VAD；短插话用规则吸附到最近的簇；重叠区间标为重叠而不是硬判给某一人 | 词级时间戳 + 音频 | 每段的说话人标签 | p7 |
| M8 章节切分 | 以句嵌入的语义漂移为主信号，静音/音乐/音量作后处理校正，说话人切换点作补充信号 | 句单元序列 | 内部章节模型 | p4, p7 |
| M9 输出序列化 | 从**同一份内部章节模型**序列化出主输出与旁挂产物，章节边界与标题只算一次 | 内部章节模型 | ID3v2.3 CHAP+CTOC / chapters JSON | p6 |
| M10 验收统计 | 同时报边界 F1（±5 秒容差）与章节数偏差 \|预测章数−人工章数\|/人工章数，使过切与欠切都在数字上暴露 | 预测章节 + 人工标注 | 两个指标 | p4 |

### 4.3 数据模型

**内部章节模型**（M8 产出，M9 的两种输出共同序列化自它，p6）：

| 字段 | 类型 | 说明 | 出处 |
|---|---|---|---|
| `element_id` | string | CHAP/CTOC 的 Element ID，同时作为 chapters JSON 的锚点；后续做文字稿跳转不用另建索引 | p6 |
| `start_ms` | int | 起始时间，4 字节大端整数毫秒 | p6 |
| `end_ms` | int | 结束时间，4 字节大端整数毫秒 | p6 |
| `title` | string | 章节标题 | p6 |
| `start_offset` / `end_offset` | int，可选 | CHAP 帧体中的可选 4 字节偏移字段 | p6 |

**CTOC 侧**（p6）：`element_id`、1 字节 Flags（bit0 = top-level，bit1 = ordered）、1 字节 Entry count、若干以 `$00` 结尾的子 Element ID；其后同样可嵌入子帧。CHAP 与 CTOC 必须处在同一个标签内。

**chapters JSON 侧字段**（p6）：`startTime`（秒，允许小数）、`title`、`url`（可选，语义是「与该章节相关的外部链接」，客户端不会自动请求它）、`img`（可选）。CHAP 的 `Start/End` 是整数毫秒，JSON 的 `startTime` 是浮点秒，两套精度模型不同，互换时必须显式定义取整规则（p6）。

**文字稿实体**（p3, p5, p7）：

| 字段 | 说明 | 出处 |
|---|---|---|
| `word.text` / `word.start` / `word.end` | 逐字文本与起止时间 | p5 |
| `word.speaker` | 说话人标签，分离失败时为空 | p7 |
| `word.is_overlap` | 标记抢话区间，不硬判给某一人 | p7 |
| `segment` | 合并后的句单元，供章节切分逐句编码 | p4 |

词级文本缓存的量级：一小时中文语音约 1 万字，每字带起止时间与文本按 20–40 字节计，单集约 1 MB 量级（未验证），远小于音频缓冲（p3）。

**评测实体**（p4）：人工章节边界 + 人工章数；边界比对采用 ±5 秒时间容差（p4 判定这是对齐评测的必要设置）。标注者间 F1 估计在 0.6–0.7（未验证），即模型 F1 的上限由标签一致性封顶（p4）。

### 4.4 关键流程

**流程 A：长音频流式转录（两小时级单集）**

1. M0 先检查权重是否落盘。断网且无缓存时不允许把 urllib3 长堆栈直接抛给用户（p8）。
2. M1 流式解码，不整段读入。作为对照：两小时 44.1 kHz 16-bit 单声道 PCM 约 635 MB，立体声约 1.27 GB（未验证）；整段解码为 float32 单声道再重采样到 16 kHz 时，峰值约为原始数据的 2–3 倍（未验证）（p3, p8）。
3. M2 做一次 VAD 全量扫描，把块边界放进静音处。固定 30 秒时钟窗口在两小时音频上会产生约 240 个块、239 个边界（未验证），每个边界都可能切断词；VAD 边界把这类风险集中到少数无停顿长独白处，重解码次数降到个位数量级（p3）。
4. 块尾加 1.5–2 秒重叠。中文播客每秒约 4–6 字，2 秒覆盖 8–12 字，够接住被切断的边界词，接不住 3 秒以上的无停顿连读，所以重叠只是概率兜底、给不出保证（p3）。
5. 重叠区按时间戳或最长公共子串去重。去重做错会出现重复句或整句丢失，比边界重解码更难定位（p3）。
6. M3–M6 依次完成推理、对齐、幻觉检测、标点与 ITN。
7. M7 说话人分离放在 ASR 之后，复用词级时间戳。

已知失效模式（p3，如实记录、不作为已解决问题）：VAD 漏检会把词内短停顿当边界产生碎块；长连读段落仍会超出 30 秒上限要硬切，退回固定窗口的边界问题；垫音乐、直播未剪辑、双人抢话的音频会让 VAD 退化成随机切块。

**流程 B：章节生成与写盘**

1. M8 以句单元为单位逐句编码句向量，比较语义漂移定边界。句嵌入模型在 fp32 下百 MB 级、int8 量化后数十 MB 级（未验证）；TextTiling 一类统计法额外权重为零（p4）。
2. 静音、音乐、音量信号作后处理校正。话题漂移对插播广告、口播赞助这类「话题延续但内容切换」的段落给不出边界，这类边界要靠非语义信号补齐（p4 自承这是该立场的硬伤）。说话人切换点作为与静音停顿互补的补充信号（p7）。
3. M9 从同一份内部章节模型序列化两种输出。
4. 主输出走命令行写入：ffmpeg 用 `;FFMETADATA1` 的 `[CHAPTER]` 块配 `-map_metadata 1 -codec copy -id3v2_version 3` 把章节并进 MP3，不重编码，成功与否体现在退出码上，可塞进 shell 管道和 cron（p6）。
5. 只写 ID3v2.3：v2.3 与 v2.4 对 CHAP 内嵌子帧 size 是否 syncsafe 的写法在各实现间不一致，写错版本会出现部分播放器读到 0 章或乱码章节，且没有权威校验器能提前告知；只写 v2.3 等于主动放弃 v2.4 的 UTF-8 章节标题能力（p6）。
6. 注意写标签是改写文件本身：原有 padding 不够时库会重写整个文件，两小时 MP3 会产生一次与文件体积相当的写放大（未验证），批量处理整个播客目录时这个放大很直观（p6）。

**未决分叉**（p6）：CHAP/CTOC 只定义在 ID3v2 容器里，实际只有 MP3 能就地写。输入是 M4A、FLAC、Opus 时，要么整轨转码成 MP3（长音频代价高），要么退回 m4a chapter track / cue 文件——格式分叉的维护成本落在工具身上。本次讨论给出了两条退路，未做取舍。

### 4.5 技术选型

**ASR 权重：量化是硬前提，骨架大小存在未解决分歧。**
采纳 int8/q5 量化作为必须项：200 MB 级权重能让工具随包分发、离线安装、离线运行，这是「能不能交付」的前提而非优化项（p2）。但两位专家对骨架大小的判断相反：p2 主张压到 200 MB 级（未验证），并指出 1.5 GB→200 MB 跨了量化与模型骨架两级——Whisper medium 在 fp16 约 1.5 GB（未验证），单做 int8 只能到约 770 MB（未验证），要到 200 MB 必须同时换更小的骨架；p5 主张用 int8 量化的大模型加分段与强制对齐，宁可慢十倍，其代价是 fp16 权重约 3 GB、int8 约 1.5–2 GB（未验证），峰值常到 4–6 GB（未验证）。

**设计动作：把「模型骨架」与「量化位宽」做成两个独立可配置项。** 依据是 p2 的论证——两个变量混在一起，出问题时无法归因；p2 还给出了收敛条件：若实测同一集中文加中英夹杂播客、同一骨架下 int8 相对 fp16 的专有名词与英文术语错误率上升小于 3 个百分点且整体 WER 上升小于 0.5 个百分点，则量化几乎白拿；若实测 q5 相对 q8 解码耗时差小于 10%（未验证，q5 与 q8 的耗时差估计在 10%–30% 区间，方向取决于内存带宽与反量化开销谁占主导）而专有名词错误率上升超过 5 个百分点，则 200 MB 是硬线但不该用 q5 去凑，宁可换更小骨架保 q8。p5 的对应收敛条件：若 int8 相对 fp16 的中文字错误率上升小于 3 个百分点，且大模型 CPU 实时率实测高于 0.5（含标点与 ITN），则接受中模型加后处理换速度；若交付目标从逐字稿降级为章节标题加摘要，p5 对实时率的坚持相应放松。

**磁盘不等于 RSS。** 权重减约 1.3 GB 是磁盘差，带 Python/torch 的运行时固定开销在 1 GB 上下（未验证），冷启动峰值降幅被稀释，绝不是 1.5/0.2 的 7.5 倍；用无 Python 的 C++ 运行时开销小，比值才接近（p2）。另外在 mmap 懒加载模式下，冷启动瞬时 RSS 不一定包含全部权重页，只有稳态 RSS 才反映真实占用（p2，此条非未验证项）。

**为什么必须量化而不是靠加内存。** int8 的退化集中在低频词，高频常用词基本无损，整体 WER 只涨很小一截（未验证：整体 WER 退化通常在一个绝对百分点以内）；而专有名词恰恰可以在后处理层用词表偏置、节目固定术语表来修，修复成本低于加内存（p2）。但必须同时记录风险：整体指标会掩盖真实退化，人名、机构名、中英夹杂技术术语的错误率可能是整体的好几倍（未验证），而这些正是章节标题最依赖的信号（p2）；中英夹杂播客中英文术语多为低频 token、logit 边际小，量化噪声更容易把它们翻过决策边界（未验证，p2 标为结构性推测而非实测）。

**分段策略：VAD 停顿点切块，块尾 1.5–2 秒重叠；否决固定 30 秒时钟窗口。**
理由是一个可直接计数的指标：固定窗口在两小时音频上产生约 240 个块、239 个边界（未验证），每个边界都风险切断词；VAD 边界把重解码压到少数无停顿长段，次数是个位数量级（p3）。重叠 2 秒只是概率兜底（p3）。代价已记录：VAD 多出一个模型依赖和一次对全量音频的前向扫描，这份开销要靠省下的重解码赚回来；p3 的改判条件是实测 VAD 方案端到端耗时反而增加 5% 以上，或超过 30 秒的无停顿连续语音段占比高于 40%、VAD 边界有 30% 以上落在词内部。

**内存策略：环形缓冲 + 按块流式。**
环形缓冲只保留当前块加尾部重叠，两小时处理的常驻音频内存与音频时长解耦（p3）。词级文本缓存只有 1 MB 量级（未验证），音频缓冲与解码结果缓存差 1–2 个数量级（p3）。改成流式之后，音频缓冲与解码缓存都不再是瓶颈，最大常驻项变成模型权重：本地 large 级权重在 int8 量化下约 1–3 GB 量级（未验证）（p3）。说话人分离的中间状态会抬高峰值，无显卡 8–16 GB 内存的机器上必须按块流式处理而不是整集载入（p7）。

**章节切分：以句嵌入的语义漂移为主信号，非语义信号作后处理校正。**
选语义漂移的理由：播客的转场在听众心里是话题换了而不是说话人停了，换气、喝水、口播赞助都会产生静音，静音切章等于把一次停顿当一次转场；TextTiling 靠词汇重合度打分，在 ASR 中文口语上标点不可靠、同义改写多，深度分容易碎；句嵌入对改写和识别错误更耐受（p4）。验收采用边界 F1（±5 秒容差）加章节数偏差，现实区间估计 0.5–0.7（未验证），书面文本切分基准上监督模型的边界 F1 大致在 0.6–0.8 量级（未验证）；对 60 分钟单集切 25 章相当于每章约 2.4 分钟，偏碎，常见粒度估计每集 5–15 章（未验证）（p4）。非语义信号不是可选项：广告口播常延续同一话题，语义上给不出边界，这类边界要靠音乐、音量、静音检测，p4 明确承认这是其立场的硬伤，并提出若实测「静音 + 音乐/音量检测」在广告与口播赞助边界上的召回比语义漂移高 0.2 以上，则把非语义信号从辅助升为并列主信号。

**说话人分离：做，但带规则兜底。**
在近场、重叠比例低的两人对谈上 DER 估计在 8%–15%，做得好可到 5%–8%（未验证）；对照 pyannote.audio 3.x 在 AMI 远场会议语料上的公开 DER 在 18%–19% 量级（未验证）（p7）。代价是一个 60–200 MB 的声纹嵌入模型和额外耗时：ECAPA-TDNN 类模型参数量约 15–20 M，fp32 权重约 60–80 MB，int8 量化后约 20 MB（未验证）；1 小时音频在消费级 CPU 上端到端耗时估计 1–3 分钟，GPU 上数十秒（未验证）（p7）。短插话通常短于 0.5 秒，声纹嵌入在该时长上信噪比不足，必须用规则吸附到最近的簇；抢话片段抽出的嵌入是两个说话人的混合向量，聚类容易过聚类成三到四人，导致整集标签体系崩塌——重叠区间标为重叠而不是硬判给某一人（p7）。p7 的改判条件：若 20 集以上双人播客实测显示无独显、16 GB 内存机器上加分离后 1 小时音频总耗时增幅超过 80% 且 DER 高于 15%，则第一版只出带时间戳的纯文字稿，把说话人区分推到第二版。

**输出格式：ID3v2.3 CHAP+CTOC 为主输出，chapters JSON 为旁挂。**
理由：ID3v2 CHAP+CTOC 是唯一能同时被 Apple Podcasts、Overcast、VLC、foobar2000 这一类已装机播放器读到、且不需要任何网络请求的章节载体；Podcasting 2.0 chapters JSON 只覆盖实现了 podcast namespace 的一小批客户端，覆盖面是它的子集（p6）。更关键的是生效前提：RSS 里的 `<podcast:chapters>` 标签带 url 和 type 两个属性，url 必须指向一个客户端能通过 HTTP 取到的 JSON 文件，因此整份 chapters JSON 只有在被托管之后才对客户端生效——单独交付对本地用户没有闭环价值，把它当主输出等于把工具的价值推迟到用户完成一次本来没打算做的部署（p6）。两种输出从同一份内部章节模型序列化，不会出现两份输出时间轴打架（p6）。客户端对 ID3v2.3 与 v2.4 的容错程度不一致，具体版本号和覆盖比例没有可引用的实测数据（p6）；各客户端对章节的解析容错差异只能靠真机回归测试确认，本地离线环境测不了 Apple Podcasts 和 Overcast 的行为（p6）。p6 的改判条件：若实测只交付 chapters JSON、不写 ID3 CHAP/CTOC 也能正常显示且时间戳偏移小于 1 秒，则放弃「ID3 为主输出」；若 ffmpeg 写出的 v2.3 CHAP+CTOC 在目标客户端上被忽略的比例超过 20%，则改为主输出换成 m4a chapter track 加 sidecar JSON。

**幻觉检测：作为独立环节保留。**
Whisper 在静音、笑声、音乐段会产生幻觉与重复循环，并可能整段丢词，小模型更明显（未验证）；这类整段编造是 WER 根本不计分的，但对文字稿最致命（p5）。快语速抬高的是音近字与专名错误，笑声段的错误模式不同、以整段幻觉或丢失为主，两者不能用同一个补丁解决（p5）。

**权重分发与断网提示：显式处理，不留给用户第一次运行。**
多数本地 ASR 方案首次仍要联网取权重，这与「全离线」约束是真实矛盾（p8）。动作有三：预置权重或离线导入包、流式分段解码、把 URLError 包装成可读提示（p8）。另需注意部分下载后 sha256 校验失败时报出的是 checkpoint 载入异常，用户从中无法判断是网络中断导致（未验证）（p8）。

**未覆盖项。**
交付形态（命令行、桌面界面，还是被其他工具调用的库）在本次讨论中未被定论：p6 只说明写入路径可以完全走命令行并塞进 shell 管道与 cron，p8 明确表示没有确定的交付形态就下了判断。（本次讨论未覆盖）

## 6. 风险与失败模式

### 6.1 技术风险

**风险一：量化退化被整体指标掩盖。**
触发条件：对 ASR 权重做 int8/q5 量化。int8 的伤害不均匀——整体 WER 可能只涨不到 1 个绝对百分点（未验证），但人名、机构名、中英夹杂的技术术语错误率可能是整体的好几倍（未验证），而这些正是章节标题最依赖的信号。影响：整体指标掩盖真实退化，且这类错字集中在最要紧的词上，节目名、嘉宾名、英文技术术语一旦错，章节标题和后续检索一起废掉。缓解：在后处理层用词表偏置、节目固定术语表修专有名词，修复成本远低于加内存；判据按 p2 的让步条件——同一骨架下实测 int8 相对 fp16 的专有名词与英文术语错误率上升小于 3 个百分点、且整体 WER 上升小于 0.5 个百分点，则量化几乎白拿。

**风险二：200MB 目标混了两个变量，出问题无法归因。**
触发条件：同时做量化与换模型骨架。Whisper medium 在 fp16 约 1.5GB（未验证），单做 int8 只能到 ~770MB（未验证），要到 200MB 必须同时换更小的骨架（small/int8 或蒸馏版）。影响：1.5GB 到 200MB 这个跨度不是单靠量化能走完的，两个变量混在一起，出问题时无法归因。缓解：拆开测——按 p2 的让步条件，若实测 q5 相对 q8 的解码耗时差小于 10% 而专有名词错误率上升超过 5 个百分点，则 200MB 是硬线但不该用 q5 去凑，宁可换更小骨架保 q8。

**风险三：磁盘权重缩减与峰值 RSS 缩减不等量。**
触发条件：用磁盘比值（1.5GB→200MB）去预期内存降幅。磁盘权重是压了约 1.3GB（未验证），但带 Python/torch 的运行时固定开销在 1GB 上下（未验证），冷启动峰值降幅会被稀释到一半左右，绝不是 7.5 倍。影响：内存预算估错。缓解：用 C++ 运行时（无 Python）开销小，比值才接近磁盘比值；测量上，mmap 懒加载模式下冷启动瞬时 RSS 不一定包含全部权重页，稳态 RSS 才反映真实占用，测冷启动峰值会低估。

**风险四：q5 相对 q8 的耗时方向不确定。**
触发条件：在内存带宽受限的 CPU 上解码。内存带宽受限时 q5 更快，但反量化开销和大 batch 下的对齐问题可能让它更慢；两者解码同一集播客的耗时差估计在 10%~30% 区间（未验证），方向取决于谁占主导。影响：收益浮动而精度损失是确定的。缓解：按风险二的判据实测两者解码耗时差后再定版。

**风险五：VAD 的前提不成立。**
触发条件：输入是垫音乐、直播未剪辑、双人抢话的音频。整个 VAD 切块结论依赖「播客里有足够静音」这一前提，上述素材会让 VAD 退化成随机切块。影响：切块质量坍塌。缓解：按 p3 的让步条件切换到固定窗口加重叠并在合并阶段去重——即 VAD 全量扫描使端到端耗时反而增加 5% 以上，或样本中超过 30 秒的无停顿连续语音段占比高于 40%、VAD 边界有 30% 以上落在词内部时，放弃 VAD 优先。

**风险六：VAD 漏检与长连读段落。**
触发条件：语速极快、无停顿的长独白。VAD 漏检会把词内短停顿当边界产生碎块，长连读段落会超出 30 秒上限，仍要硬切并退回到固定窗口的边界问题。影响：拉高 ASR 调用次数和调度开销。缓解：边界加 1.5-2 秒重叠兜底；但中文播客每秒约 4-6 字（未验证），2 秒覆盖 8-12 字（未验证），够接住被切断的边界词，接不住 3 秒以上的无停顿连读，重叠给不出保证，问题只是低频化而非消除。

**风险七：重叠区去重引入新的错误源。**
触发条件：合并阶段按时间戳或最长公共子串对重叠区去重。影响：去重做错会出现重复句或整句丢失，比边界重解码更难定位。缓解：重叠只有 1.5-2 秒时窗口很短，合并阶段的字符串对齐成本可忽略。

**风险八：话题漂移对广告与口播赞助给不出边界。**
触发条件：插播广告、口播赞助这类「话题延续但内容切换」的段落。广告口播常常延续同一话题，语义上给不出边界。影响：这一段的章节边界漏切。缓解：p4 承认这是该立场的硬伤，音乐、音量、静音等非语义信号在广告段上有不可替代的作用；若实测显示「静音+音乐/音量检测」在广告与口播赞助边界上的召回比语义漂移高 0.2 以上，则把非语义信号从辅助信号升为并列主信号。

**风险九：句向量相似度曲线偏平。**
触发条件：峰值检测（深度分、2D-Max 一类）没调好。相邻句之间普遍高相似，曲线偏平。影响：反而比 TextTiling 更容易漏切，工程实现门槛更高。缓解：需要标注数据来定阈值、最小章节长度和平滑窗口。

**风险十：静音、笑声、音乐段的幻觉与重复循环。**
触发条件：音频中出现静音、笑声、音乐段，小模型更明显。Whisper 在这类段落会产生幻觉与重复循环，并可能整段丢词。影响：整段编造，而 WER 根本不计分这类错误——这是播客文字稿最致命的一类错。缓解：对笑声、静音段做幻觉检测。

**风险十一：CPU 实时率低于 1。**
触发条件：在无独显的消费级 CPU 上跑完整流水线。实时率约 0.3–1.0（未验证），即每音频分钟耗 30–120 秒（未验证），纯识别部分可能到 1–2（未验证）。影响：两小时单集要跑数小时，这不是体验问题，是可用性问题；批量处理整个播客目录在消费级 CPU 上不现实。缓解：按 p5 的让步条件——实测 int8 相对 fp16 的中文字错误率上升小于 3 个百分点、且大模型 CPU 实时率实测高于 0.5（含标点与 ITN），则接受中模型加后处理换速度；或者把交付目标从逐字稿降级为章节标题加摘要。

**风险十二：标点恢复与 ITN 需要外挂模块。**
触发条件：Whisper 中文输出存在繁体字、缺少规范大小写与标点规范化的倾向。影响：多一段延迟、多一份模型文件要随包分发；常见中文标点恢复模型是独立的 BERT 级模型，为整条流水线增加约 5%–15% 的额外耗时（未验证）。缓解：按 p5 的判断，CPU 上标点与 ITN 的额外开销相对识别本身是小头，真正的成本在模型规模——优化优先级应放在模型规模而不是标点/ITN。

**风险十三：同一音频多次运行结果不一致。**
触发条件：用户重跑同一文件。影响：用户发现文字稿变了，会怀疑工具坏了。缓解：本场未给出缓解手段。

**风险十四：CHAP/CTOC 的容器只限 MP3。**
触发条件：输入是 M4A、FLAC、Opus。CHAP/CTOC 只定义在 ID3v2 容器里，实际只有 MP3 能就地写。影响：要么整轨转码成 MP3（长音频代价高），要么退回 m4a chapter track / cue 文件，格式分叉的维护成本落在工具身上。缓解：按 p6 的让步条件——若用 ffmpeg 写出的 v2.3 CHAP+CTOC 在目标客户端上被忽略的比例超过 20%，把主输出换成 m4a chapter track 加 sidecar JSON。

**风险十五：ID3v2.3 与 v2.4 的 CHAP 写法不一致。**
触发条件：写入 CHAP 内嵌子帧时，size 是否 syncsafe 在各实现间写法不同。影响：部分播放器读到 0 章或读到乱码章节，而且没有权威校验器能提前告诉你。缓解：稳妥做法是只写 v2.3，等于主动放弃 v2.4 的 UTF-8 章节标题能力。

**风险十六：写 ID3v2 标签触发整文件重写。**
触发条件：原有 padding 不足时，mutagen 一类库会重写整个文件。影响：对两小时的单集就是一次与文件等量的额外磁盘写入和数倍耗时（未验证），批量处理整个播客目录时这个放大很直观。缓解：本场未给出缓解手段。

**风险十七：客户端容错差异在本地无法验证。**
触发条件：交付前做兼容性验证。各客户端对章节的解析容错差异只能靠真机回归测试确认，本地离线环境测不了 Apple Podcasts 和 Overcast 的行为。影响：等于把一部分验证责任转嫁给发布者。缓解：只能靠真机回归测试。

**风险十八：两份输出的时间轴打架。**
触发条件：章节模型分别序列化成 CHAP 与 chapters JSON。CHAP 的 Start/End 是 4 字节大端整数毫秒，1 小时音频的舍入上限是 0.5 毫秒，可以直接和 ffmpeg 探测出来的章节时间点做逐字节一致性校验；chapters JSON 用浮点秒，校验时反而要先反解浮点误差。影响：两份输出时间轴不一致。缓解：两种输出从同一份内部章节模型序列化出来，章节边界与标题只算一次。

**风险十九：说话人分离在短插话与抢话片段上必错。**
触发条件：出现短于 0.5 秒的插话，或两名说话人重叠的抢话片段。短插话的声纹嵌入信噪比不足，会被归进错误的簇或自成一个伪簇；抢话片段抽出的嵌入向量是两个说话人声纹的混合，与任何单一声纹都不接近，全局聚类容易过聚类成三到四人，导致整集的标签体系崩塌。影响：这恰恰是听众最需要知道谁在接话的地方，是体验最差的一类错误，且需要人工重新指派。缓解：短片段必须用规则吸附到最近的簇，重叠区间标成重叠而不是硬判给某一人。

**风险二十：说话人人数估计错。**
触发条件：说话人人数要预先给定或自动估计。影响：两人被判成三人会让整份文字稿的标签全错，这种错误的修正成本远高于零散的片段错误。缓解：本场未给出缓解手段。

**风险二十一：声纹模型随包分发抬高安装门槛。**
触发条件：在无网络环境下交付。声纹嵌入模型 60–200MB（未验证），模型权重必须随包分发或被用户手工放置，安装步骤因此多出一个容易出错的环节。缓解：与 p8 提出的预置权重/离线导入包走同一动作。

**风险二十二：权重从未下载且断网。**
触发条件：权重从未落盘 + 断网。主流库会走 HTTP 重试，抛出的不是自定义提示，而是 urllib3 / requests 的 ConnectionError 或 URLError 长堆栈，并伴随 3-5 次指数退避重试（未验证）；在 TCP 连接被黑洞（无响应而非拒绝）时表现为停滞数分钟，进度条停在 0%（未验证）。影响：用户看到的是几十行 Python traceback 或一个停在 0% 的进度条，而不是一句「缺模型、请先联网下载 X」。缓解：预置权重/离线导入包；把 URLError 包装成可读提示。

**风险二十三：部分下载后校验失败被报成载入异常。**
触发条件：下载中断。部分下载后用 sha256 校验失败时报出的是 checkpoint 载入异常（如 Unable to load weights from pytorch checkpoint file），用户从中无法判断是网络中断导致。影响：错误信息指向错误的方向。缓解：本场未给出缓解手段。

**风险二十四：整段载入 + 重采样产生拷贝。**
触发条件：实现上「一次读入整段 + 重采样产生拷贝」。两小时 44.1kHz 立体声 16bit PCM 约 1.27GB（未验证），整段转 float32 单声道再重采样到 16kHz 时峰值可到原始数据的 2-3 倍（未验证）。影响：单独解码不会爆，叠上模型常驻才危险，8GB 机器上可能触发换页。缓解：流式分段解码；按 p3 的判断，改成环形缓冲后音频缓冲与解码结果缓存都不再是瓶颈，模型权重才是最大常驻项——优化优先级应据此排序。

### 6.2 产品风险

**风险一：交付形态未定，第一道坎无法判断。**
触发条件：未确定交付是命令行、桌面界面还是被其他工具调用的库。p8 的「先卡在哪一步」这个判断对交付形态敏感：命令行工具和带界面的工具，用户感知到的第一道坎完全不同。影响：无法确定该优先做权重预置、流式管线还是进度与断点续传。缓解：本场未就该形态做出决定，立案书将其列为待定项。

**风险二：章节切得不对导致的弃用。**
触发条件：用户装上了工具，但觉得章节切得不对。p8 承认自己把重心压在安装与硬件，可能低估了真正的留存因素——安装只是用过一次就跨过的门槛。影响：用户一样会弃用。缓解：本场未给出缓解手段。

**风险三：按最坏环境设计的投入回报低。**
触发条件：按 8GB 内存、无独显、断网、两小时长音频来设计。这逼迫降级路径、流式管线、进度与断点续传全部落地，工程成本明显高于「假设用户有 16GB 内存和一块显卡」的写法。影响：如果目标用户实际配置更好，这部分投入回报很低。缓解：p8 的让步条件给出了验收线——一台 8GB 无独显断网机器从零安装到两小时 44.1kHz 立体声 wav 出结果，全程无需人工干预、不出现 Python traceback、进程峰值 RSS 低于 3GB，且三处卡点都不是耗时或内存的主要贡献项时，承认卡点不在安装与硬件。

**风险四：用调章节数去刷 F1。**
触发条件：把章节数当成调参目标。章节数必须是输出而不是调参目标。影响：过切和欠切都能被单一指标掩盖。缓解：验收指标同时量化边界 F1 与章节数偏差（|预测章数-人工章数|/人工章数），过切和欠切都会在这两个数字上暴露。参照量级：60 分钟单集切 25 章即每章约 2.4 分钟（未验证），偏碎；常见播客章节粒度估计在每集 5-15 章（未验证）。

**风险五：标注人力与标注主观性封顶。**
触发条件：需要标注数据定阈值。中文播客没有现成的公开标注集，自建 30-100 集标注是真实人力开销，否则阈值只能靠拍脑袋；同时不同标注者对同一集的章节数和边界位置不会完全一致，标注者间 F1 估计在 0.6-0.7（未验证）。影响：模型 F1 的上限就此封顶，再怎么换模型也顶不上去。缓解：本场未给出缓解手段。

**风险六：章节切分的 F1 没有可复现基准。**
中文播客领域没有公开、可复现的话题漂移章节切分边界 F1 基准；0.5-0.7 是基于书面文本切分文献和口语域偏移做的估算（未验证）。影响：验收标准缺少外部锚点。缓解：用 ±5 秒时间容差评 F1，避开「边界差两秒就判错」的假失败。

**风险七：把 chapters JSON 当主输出。**
触发条件：以 Podcasting 2.0 chapters JSON 作为主交付。RSS 里的 `<podcast:chapters>` 标签带 url 和 type 两个属性，其中 url 必须指向一个客户端能通过 HTTP 取到的 JSON 文件，因此整份 chapters JSON 只有在被托管之后才对客户端生效。影响：跑出来的 chapters.json 得用户自己上传托管，否则拿不到它；把它当主输出等于把工具的价值推迟到用户完成一次本来没打算做的部署，与「不调用云服务」的约束直接冲突。缓解：chapters JSON 只能作为同一次运行顺带吐出的旁挂产物，主输出落在磁盘上、播放器打开文件即读的 ID3v2 CHAP+CTOC。

**风险八：实时率造成的批量不可用。**

### 7.1 M1（最小可用）

范围：在单台目标机器上，对单集中文播客（含中英夹杂）跑通「音频解码 → 分段 → ASR → 章节切分 → 写出 ID3v2.3 CHAP+CTOC」的完整链路，只处理一个文件，不做批量。

验收标准：

1. 在 8GB 内存、无独显、断网的机器上，从零安装到两小时 44.1kHz 立体声 wav 出结果，全程无需人工干预、不出现 Python traceback、进程峰值 RSS 低于 3GB（骆一鸣让步条件）。
2. 权重从未落盘且断网时，工具输出的是「缺模型、请先联网下载 X」这类可读提示，而不是几十行 Python traceback 或停在 0% 的进度条（骆一鸣核心主张）。
3. 音频按 VAD 停顿点切块流式处理，块边界加 1.5–2 秒重叠；两小时音频（30 秒块约 240 块、239 个固定边界）的边界重解码次数为个位数量级（何长川核心主张）。
4. 环形缓冲只保留当前块加尾部重叠，16 kHz float32 下 30 秒块约 1.9 MB，常驻音频内存与音频时长解耦（何长川核心主张）。
5. 章节以句嵌入的语义漂移为主信号、静音作后处理校正，章节数是输出而非调参目标；在 ±5 秒容差下报告边界 F1 与章节数偏差（|预测章数-人工章数|/人工章数）两个数字（温若岚核心主张）。
